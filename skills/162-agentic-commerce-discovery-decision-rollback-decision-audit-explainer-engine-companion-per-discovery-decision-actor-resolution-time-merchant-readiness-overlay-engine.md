## Common pitfalls (18 from real builds)

**Cluster A — per-discovery-decision-actor-resolution-time-merchant-readiness-overlay-router + bucket-assignment + decoder-family-router**

1. **Treating merchant-readiness-tier as a static property of the merchant rather than a streaming signal that drifts per-channel.** The Pillar B Step 1 merchant-readiness-overlay-window-bucket-assignment reads Move #124's `merchant-readiness-tier` field as if it were a per-merchant cache key. **Fix:** treat `merchant-readiness-tier` as a per-merchant × per-channel × per-stream-processing-pipeline streaming signal — emit a `merchant-readiness-tier-change` event every time Move #124's tier classifier flips a merchant from tier-N to tier-M; the Pillar B Step 1 bucket-assignment MUST subscribe to this event stream and re-bucket historical events whose tier shifted within the canonical 24-hour lookback window.

2. **Confusing the canonical `merchant-readiness-overlay-completeness-score` (0.0–1.0) with the canonical `agentic-readiness-tier` (1–5 discrete).** A merchant with completeness-score=0.74 is NOT necessarily tier-3 — tier boundaries are non-linear and channel-specific per Move #124 benchmarks. **Fix:** use Move #124's tier classifier directly as the Pillar B Step 1 bucket-assignment source; the completeness-score is a SECONDARY signal for the Pillar D industry-benchmark-engine only.

3. **Hardcoding the 5-resolution-time-merchant-readiness-overlay-window boundaries to Move #161's 5-resolution-time-cohort-LTV-overlay-window SLAs.** The cohort-LTV-overlay SLAs (sub-2s / sub-30s / sub-5min / sub-1h / sub-24h) are NOT identical to the merchant-readiness-overlay SLAs because tier-1 merchants expect sub-100ms stream-processing latency on synchronous-stream windows. **Fix:** define Move #162's 5-resolution-time-merchant-readiness-overlay-window SLAs separately per tier-1 = sub-2s / tier-2 = sub-30s / tier-3 = sub-5min / tier-4 = sub-1h / tier-5 = sub-24h; document the difference in the operator-UX dashboard's `merchant-readiness-overlay-vs-cohort-LTV-overlay-comparison` widget.

**Cluster B — per-discovery-decision-actor-resolution-time-merchant-readiness-overlay-freshness + staleness + backpressure + event-stream-emission**

4. **Window-1 (tier-1) freshness-floor regression from sub-2s to sub-5s after a Move #160 router refactor.** **Fix:** add a Move-#162-window-1-freshness-floor-canary that pages the on-call SRE the moment Move-#162's tier-1-window freshness-floor exceeds 2s p99 over a 15-minute window; gate any Move #160 router deploy that pushes tier-1 freshness above 2s p99.

5. **Window-5 (tier-5) staleness-violation false-negative because tier-5 merchants emit at most 1 event per 24h.** **Fix:** the staleness-ceiling for window-5 is 24h, but the freshness-emission floor for window-5 MUST be at least 1 event per merchant per 24h; if no event arrives within 24h, emit a synthetic `tier-5-staleness-heartbeat` event so the dashboard reflects the merchant's true state.

6. **Backpressure-floor collision between synchronous-stream + change-data-capture-stream pipelines on tier-1 merchants during peak event-storm.** **Fix:** Pillar B Step 2 backpressure computation reads each stream-processing-pipeline's queue-depth-or-rate-limiter-headroom independently and tags each event with `backpressure-source-stream-pipeline`; the canonical backpressure-floor is per-pipeline (queue-depth <100/<1k/<10k/<100k/<1M + rate-limiter-headroom >50%/>40%/>30%/>20%/>10% per window × per pipeline).

7. **Event-stream emission drop on Move-#162 → Move-#161 back-feed when the Move-#160 router is degraded.** **Fix:** the Move-#162 → Move-#161 back-feed event stream is a SEPARATE Kafka topic (`merchant-readiness-overlay-resolution-time-pressure-v1`); if Move-#160's main event-stream topic degrades, Move-#162 still emits to the back-feed topic and Move-#161 still receives per-resolution-time-merchant-readiness-overlay-pressure updates.

**Cluster C — per-discovery-decision-actor-resolution-time-merchant-readiness-overlay-fairness + coverage + versioning + decomposition**

8. **Anti-monopoly-floor violation when one merchant dominates a tier-1 window (e.g. a single $50M GMV merchant = 60% of tier-1 events).** **Fix:** the anti-monopoly-floor per-resolution-time-merchant-readiness-overlay-window × per-discovery-decision-actor-id is per-discovery-decoder-family, NOT per-merchant; if a single merchant >40% of a per-window × per-decoder-family bucket, split the merchant's events across multiple `discovery-decision-actor-id` partitions and surface a `merchant-monopoly-warning` chip on the operator-UX dashboard.

9. **Coverage-benchmark false-positive when Move-#124 merchant-readiness-tier field is absent on legacy merchants (pre-2026 onboarding).** **Fix:** Pillar C decomposition decoder-set falls back to the canonical Triple Whale Merchant Readiness band when Move-#124 field is absent; the operator-UX dashboard surfaces a `coverage-source-mix` widget showing the % of events from Move-#124 vs Triple Whale per window.

10. **Move-#162 → Move-#160 → ... → Move-#123 version-lineage drift when a Move-#124 schema-field is renamed (e.g. `merchant-readiness-tier` → `agentic-readiness-tier`).** **Fix:** Move-#162 versioning-watcher subscribes to Move-#124's schema-event-stream and re-emits historical events under BOTH the old AND new field names for the canonical 7-day migration window; the operator-UX dashboard surfaces a `versioning-drift-warning` chip whenever Move-#162 ingests a Move-#124 schema-rename event.

11. **Merchant-readiness-overlay-window × per-LTV-overlay decomposition mis-classification when a merchant's `merchant-readiness-tier` and `LTV-band` are computed by different upstream signals (Move-#124 vs Move-#154).** **Fix:** Pillar C decomposition decoder-set reads the canonical `merchant-readiness-overlay-completeness-score` and the canonical `cohort-LTV-overlay-completeness-score` as cross-validation; surface a `cross-validation-mismatch-warning` chip when the two signals disagree by >0.20 completeness-score.

**Cluster D — per-discovery-decision-actor-resolution-time-merchant-readiness-overlay-cohort + merchant-impact + rollback-decision-audit + decomposition-deep**

12. **Cohort-impact false-positive when a tier-1 merchant's events dominate the per-cohort aggregation.** **Fix:** Pillar B Step 3 aggregation-rollup is per-cohort × per-channel × per-merchant-readiness-tier; if a single tier-1 merchant >30% of per-cohort events, surface a `cohort-impact-merchant-monopoly` chip on the operator-UX dashboard.

13. **Merchant-impact regression when a tier-shift (tier-1 → tier-2) is treated as merchant-impact-positive rather than merchant-impact-negative.** **Fix:** the merchant-impact direction depends on the tier direction: tier-N → tier-M where N<M is merchant-impact-negative (regressed); N>M is merchant-impact-positive (improved); the operator-UX dashboard's merchant-impact widget MUST classify shifts by direction and surface both directions.

14. **Rollback-decision-audit false-positive when the per-resolution-time-merchant-readiness-overlay-window freshness-floor regression is mis-classified as a rollback-trigger.** **Fix:** the canonical rollback-decision-audit-engine ONLY fires a rollback-decision when (a) freshness-floor regression >2× SLA for >15min AND (b) the merchant-impact direction is negative AND (c) the per-rollback-window decision is `rollback-now`; emit a `rollback-decision-audit-no-op` chip otherwise.

15. **Merchant-readiness-overlay-decomposition-deep (Pillar C sub-decomposition (e)) over-emission when per-failure-mode granularity explodes (12 canonical discovery-failure-modes × 5 merchant-readiness-tiers × 5 windows × 12 rollback-windows × 5-stream-processing-pipelines = 18,000 cells).** **Fix:** Pillar C decomposition decoder-set emits at most 1 cell per (per-resolution-time-merchant-readiness-overlay-window × per-failure-mode × per-stream-processing-pipeline); cells where the event-count <10 within the canonical 7-day window are aggregated to `failure-mode-stream-pipeline-cluster` for the operator-UX dashboard.

**Cluster E — per-discovery-decision-actor-resolution-time-merchant-readiness-overlay-recovery-decoder-decision + rollback-window-decision + cohort-impact-decomposition + event-stream-auto-feeding-back**

16. **Recovery-decoder-decision mis-fires when the canonical 5-window rollback-window-decision is `rollback-now` but the per-cohort-impact is positive.** **Fix:** the canonical recovery-decoder-decision is `rollback-now + cohort-impact-positive = rollback-defer`; only `rollback-now + cohort-impact-negative` actually fires a rollback-decision; surface a `recovery-decoder-decision-deferred` chip on the operator-UX dashboard.

17. **Rollback-window-decision collision when a merchant-readiness-tier-shift (tier-1 → tier-2) within the canonical 1-hour window collides with a Move-#160 rollback-window-decision.** **Fix:** Move-#162's rollback-window-decision takes precedence over Move-#160's when the merchant-readiness-tier shift is the proximate cause; otherwise Move-#160 takes precedence; the operator-UX dashboard surfaces a `rollback-window-decision-source` chip showing which engine fired the decision.

18. **Event-stream-auto-feeding-back-loop-broken when Move-#124's `merchant-readiness-tier` field is dropped (Move-#124 schema evolution).** **Fix:** Pillar F back-feed emits BOTH a `merchant-readiness-tier-change` event AND a `merchant-readiness-overlay-resolution-time-pressure-change` event on every tier-shift; if Move-#124 drops the tier field, the back-feed still surfaces the resolution-time-pressure event with `merchant-readiness-tier-source: legacy-v1` so Move-#124 can fall back to the canonical Triple Whale Merchant Readiness band.
