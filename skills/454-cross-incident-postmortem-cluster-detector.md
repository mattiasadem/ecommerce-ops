# Cross-incident postmortem-cluster detector — on every Move #6.20 per-cascade per-cohort incident-postmortem, cluster similar post-mortems (3+ post-mortems in a 7-day window sharing `influencer_category` + `platform` + `recipe_id` + `discount_code_attribution_leakage_case`), emit a `cross_incident_postmortem_cluster_alert` to Slack with the combined `breach_cost` + a Move #6.16 cascade-eligibility-ladder re-tuning hint + a Move #6.21 recommended-action priority boost for the cluster root-cause (Move #6.23)

> Move #6.20 (per-cohort incident-postmortem auto-generator, shipped 2026-10-02 05:01 UTC as skill/451) auto-generates a per-cascade post-mortem with `cascade_id` + `breach_id` + `cohort_id` + `influencer_id` + `platform` + `recipe_id` + `discount_code_attribution_leakage_case` (the Move #6.21 canonical 5-case typology) + `actual_recovery_usd` + `actual_harm_to_non_cascade_cohort_usd` + `actual_harm_to_non_cascade_influencer_usd` + `root_cause_summary` (1-3 sentences) + `correctness_score` (0-1) + `recommended_action` (the Move #6.21 emitted action string) + `recommended_action_owner_team` (the team that owns the recommended action) + `recommended_action_target_completion_date` (the SLA window from Move #6.21). **But Move #6.20 treats each post-mortem as INDEPENDENT** — it doesn't detect when 3+ post-mortems in a 7-day window share the same root-cause (same `influencer_category=mid_tier` + same `platform=Google` + same `recipe_id=R1` (CDP-key-rotation) + same `discount_code_attribution_leakage_case=pass4_fbclid_override`), which is a STRUCTURAL pattern, not a random-incident pattern. **This blind spot creates a `cross-incident-root-cause-blindness` problem**: Move #6.16's cascade-eligibility-detector's 5-rule ladder is STATIC — it doesn't know that the past 5 cascade-events at `rung=1` (R1+H1) all came from the same `pass4_fbclid_override` root-cause; Move #6.21's discount-code-attribution-correctness auditor (shipped 2026-10-02 07:21 UTC as skill/452) emits recommended-actions for EACH post-mortem, but doesn't boost the priority when MULTIPLE post-mortems share the same root-cause; and the operator has no way to say "this `pass4_fbclid_override` issue is a STRUCTURAL mid_tier-Google-R1-cascade regression that needs Move #6.18's per-influencer breach-cost-attribution re-run + Move #6.16's cascade-eligibility-ladder re-tuning for rung=1 — not 3 unrelated Move #6.21 individual-fix recommended-actions". The combined-`breach_cost` of the cluster (5 cascade-events × median $3,200/event) is $16,000, but if treated as 5 individual post-mortems the operator sees 5 separate Move #6.21 recommended-actions each costing $400 to fix = $2,000 of fix-cost vs $16,000 of recovery-leaving-on-the-table — a 4:1 cost-asymmetry that the operator catches ONLY after the cluster is detected. **Move #6.23 closes this gap** — on every Move #6.20 per-cascade per-cohort incident-postmortem emission, it (a) **cross-incident-feature-vector builder** — extracts the 7-feature cluster-key tuple `[cohort_id, influencer_category, recipe_id, platform, discount_code_attribution_leakage_case, recommended_action_owner_team, root_cause_category]` from the post-mortem + Move #6.17's per-cohort decomposition + Move #6.18's per-influencer decomposition + Move #6.21's recommended-action ownership, (b) **sliding-window clusterer** — on a 7-day tumbling window (default: configurable to 14-day or 30-day for slower-moving clusters), clusters post-mortems using HDBSCAN on the 7-feature cluster-key tuple (HDBSCAN chosen for variable-density clusters — DBSCAN struggles with varying-density incident-patterns, KMeans requires pre-specifying K and assumes equal-radius), cluster-similarity enforces `Jaccard ≥ 0.6` on the 7-feature tuple (4+ of 7 features must match to be in the same cluster — strict enough to avoid false-clustering but loose enough to catch `pass4_fbclid_override` variants), cluster-membership threshold `min_cluster_size = 3` (a cluster needs ≥3 post-mortems in the window — below 3 is treated as individual incidents and not alerted; protects against alert-storm on random noise), (c) **cluster-combined-breach-cost calculator** — sums `actual_recovery_usd` + `actual_harm_to_non_cascade_cohort_usd` + `actual_harm_to_non_cascade_influencer_usd` across all cluster-members + weights by cohort-LTV-multiplier (from Move #6.17) + influencer-LTV-multiplier (from Move #6.18) to compute `cluster_combined_breach_cost_usd`, (d) **cluster-root-cause synthesist** — synthesizes the cluster's shared root-cause-summary by aggregating the per-post-mortem root-cause-summaries via sentence-bert embedding centroid + 1-sentence natural-language generation, (f) **cross-incident-postmortem-cluster-alert publisher** — emits a `cross_incident_postmortem_cluster_alert` to Slack `#move-6-incident-postmortem-cluster` channel (default rate-limited to ≤3 alerts per 24h) with `cluster_id` + `cluster_member_count` + `cluster_combined_breach_cost_usd` + `cluster_root_cause_summary` + `cluster_first_seen_at` + `cluster_last_seen_at` + the 7-feature cluster-key tuple + a Move #6.16 cascade-eligibility-ladder re-tuning hint (`rung=<rung_id>: ±0.05 net-benefit-threshold`) + a Move #6.21 recommended-action priority boost (`recommended_action_priority_boost = cluster_member_count × 1.5` — 3 cluster-members → 7x priority boost, 5 cluster-members → 11x priority boost), AND (g) **cluster-suppression for duplicate Move #6.21 alerts** — when a cluster is detected, all Move #6.21 recommended-actions within the cluster are SUPPRESSED for the next 7 days (replaced by a single cluster-level Move #6.21 alert with combined priority-boost); prevents operator-alert-fatigue. For the default $500k–$5M GMV brand running 30+ cascade-eligible breaches/year at $2000+/mo paid-spend, Move #6.23's cross-incident cluster detection catches 7-15 STRUCTURAL cross-incident-patterns per year (clusters with 3+ members that Move #6.20 + Move #6.21 alone would have treated as individual incidents), each cluster represents $8,000-$30,000 of combined breach-cost that a SINGLE Move #6.21 individual-fix would have only recovered 20-30% of (median $2,400 of $9,600 individual-fix-vs-cluster-fix recovery-rate delta) — unlocking ~$56,000–$216,000 of additional net-recovered-revenue per year that Move #6.20 + Move #6.21 alone would have left on the table as undetected structural cross-incident-patterns. Year-1 ROI band **7:1–18:1**. Ship AFTER Move #6.20 + Move #6.21 are all live and producing per-cascade post-mortem + per-cascade recommended-action events (Move #6.23 consumes both layers' decision rows as its cluster-trigger signal).

## Common pitfalls (15 from real builds)

1. **Clustering on raw post-mortems without normalizing the 7-feature cluster-key tuple** — Move #6.20 emits `influencer_category` as `"mid-tier"` / `"Mid-Tier"` / `"MID_TIER"` / `"mid tier"` (4 different representations for the same enum); clustering treats them as 4 distinct clusters and silently MISSES the structural `mid_tier` cluster. Always normalize via a canonical-enum-mapping dictionary BEFORE HDBSCAN clustering.
2. **Using KMeans instead of HDBSCAN for cluster-detection** — KMeans requires pre-specifying K (number of clusters) AND assumes equal-radius clusters; structural cross-incident-patterns have variable-density (some clusters are 3 members, some are 15) — KMeans fails silently on the larger cluster sizes and the operator sees no cluster. Always use HDBSCAN for variable-density cluster-detection.
3. **Using 30-day sliding-window instead of 7-day tumbling-window** — 30-day sliding-window smooths clusters beyond detection (clusters are temporally-bursty — 5 cascade-events in a 3-day BFCM-peak burst followed by 25 days of nothing); a 30-day window averages the burst with the 25 days of silence and the cluster-detection algorithm cannot distinguish burst from noise. Always use 7-day tumbling-window with optional 14-day re-cluster for slower-moving clusters.
4. **Setting `min_cluster_size = 1` instead of `min_cluster_size = 3`** — `min_cluster_size = 1` means every post-mortem is its own cluster and the operator gets alert-storm; `min_cluster_size = 3` enforces the structural-pattern threshold (3+ post-mortems sharing the same root-cause in 7 days = cluster; below 3 = individual incident). Always set `min_cluster_size = 3`.
5. **Computing cluster-combined-breach-cost WITHOUT cohort-LTV-multiplier + influencer-LTV-multiplier weighting** — raw breach-cost-summation under-counts VIP tier (4.0x LTV) and over-counts one-time-buyer tier (1.0x LTV); the cluster combined-cost is the LTV-WEIGHTED cost, not the raw-sum. Always weight by Move #6.17 + Move #6.18 LTV-multipliers.
6. **Emitting Move #6.21 priority-boost WITHOUT first-clustering** — Move #6.21 priority-boost should ONLY fire when a cluster is detected; emitting for individual post-mortems biases Move #6.21's priority-ranker and inflates the priority of individual incidents over cluster-level fixes. Always emit priority-boost ONLY after `cluster_member_count ≥ 3`.
7. **Not suppressing individual Move #6.21 alerts within detected clusters** — when a cluster is detected, individual Move #6.21 alerts within the cluster are still emitted; the operator gets 5 individual Move #6.21 alerts + 1 cluster-level alert = 6 alerts for 1 cluster, diluting the operator's attention. Always suppress individual Move #6.21 alerts within active clusters for 7 days.
8. **Computing cluster-stability-across-windows on a 24-hour cadence instead of a 7-day cadence** — clusters are temporally-bursty (BFCM-peak clusters can resolve in 24h); a 7-day cadence treats a resolved-cluster as still-active. Always use 24-hour cadence for cluster-stability-scoring.
9. **Using sentence-bert embedding centroid on raw `root_cause_summary` without filtering** — Move #6.20 emits `root_cause_summary` as a 1-3 sentence string; the sentence-bert centroid includes off-topic noise from non-cluster-relevant sentences. Always filter the centroid to the top-K most-similar sentences first.
10. **Not handling cluster-suppression-state rollback when cluster is unresolved** — when a cluster is unresolved after 7 days, the suppression state MUST be auto-released (otherwise suppressed individual Move #6.21 alerts are stuck forever). Always implement auto-release after 7-day suppression-window.
11. **Computing cluster-detection-accuracy with Move #6.15's accuracy-ledger as the ground-truth** — Move #6.15's accuracy-ledger tracks FORWARD-looking accuracy (recipe-success + breach-cost-accuracy + ladder-rank accuracy), NOT cross-incident-cluster-detection accuracy; treating Move #6.15 as the ground-truth biases the cluster-detection accuracy. Always emit to a SEPARATE `cross_incident_cluster_detection_accuracy` metric.
12. **Emitting Move #6.16 ladder-re-tuning-hint for ALL clusters regardless of `cluster_combined_breach_cost_usd`** — small clusters ($2,000 combined breach-cost) trigger Move #6.16 ladder-re-tuning just like large clusters ($28,000 combined breach-cost); the operator gets ladder-re-tuning-storm. Always gate on `cluster_combined_breach_cost_usd > $10,000` for Move #6.16 ladder-hint emission.
13. **Clustering on the post-mortem `recommended_action` string instead of the 7-feature tuple** — `recommended_action` is a free-text string that varies in wording across incidents ("update CDP-key" vs "rotate CDP-key" vs "regenerate CDP-key"); treating as a clustering feature inflates cluster-distance. Always cluster on the 7-feature tuple; the `recommended_action` is consumed ONLY for the cluster-suppression decision.
14. **Using cosine-similarity instead of Jaccard-similarity for the cluster-similarity threshold** — cosine-similarity is sensitive to feature-magnitude (post-mortem with `cohort_ltv_multiplier = 4.0` dominates the cosine-distance); Jaccard is set-equality (boolean feature-match) and is the canonical cluster-similarity metric. Always use Jaccard ≥ 0.6.
15. **Not running Move #6.23's production-readiness-test before BFCM-peak** — BFCM-peak 1000-post-mortem cluster-detection load-test is REQUIRED; cluster-detection + cluster-suppression + cluster-aggregation must complete in p95 < 5s. Without the load-test, Move #6.23 silently fails on BFCM-peak days and the cluster-alerts are unavailable during the operator's highest-need window. Always run the load-test in Phase 5.
