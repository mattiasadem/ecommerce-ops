# Predictive LTV + churn scoring engine

> Move #154 is the canonical **predictive-LTV + churn-scoring engine** that ships the missing decision layer between Move #6 (Triple Whale attribution) + Move #13 (cohort) + Move #100 (CDP) + Move #153 (review-gen/UGC): a Klaviyo Predictive Segments + Triple Whale Cohort LTV + Shopify Customer Segments + Mixpanel/Amplitude predictive scoring + a churn-scoring script + a winback-prioritization queue that turns anonymous cohort averages into **per-customer LTV / churn-risk / next-best-action scores** so the operator can (a) prioritize winback on the customers with the highest recovery probability (5–25% lift vs untargeted winback), (b) suppress sunset flows on high-LTV customers (saving 10–30% of deliverability damage), (c) rank loyalty tier-up candidates by LTV potential (15–30% loyalty program ROI lift), (d) flag high-value customers at churn risk for the CX team (20–40% save-rate on high-value save), (e) drive Meta + Google + TikTok + Snap + Pinterest custom-audience segmentation by LTV tier (10–25% blended CAC reduction), and (f) feed Triple Whale's cohort LTV dashboard with per-customer overlays (3:1–15:1 attribution-quality lift on cohort-LTV-projection). The canonical 5-pillar framework: Pillar A — data substrate (Klaviyo predictive segments + Triple Whale cohort LTV + Shopify customer-segments + Mixpanel/Amplitude predictive-scoring + Segment CDP predictive profiles) / Pillar B — churn-scoring engine (the canonical 6-feature RFM-style model + the 4-suppression gates + the 5-tier segmentation + the per-cohort decay rate) / Pillar C — winback + sunset + tier-up prioritization queue (the canonical "who to contact in what order" decision layer) / Pillar D — paid-audience segmentation by LTV tier (Meta + Google + TikTok + Snap + Pinterest custom-audience push) / Pillar E — Triple Whale cohort LTV overlay + measurement loop (the per-customer LTV projection that compounds Move #6 attribution).

## When to use this skill

You have:
- A Shopify (or Ikas / BigCommerce / WooCommerce / Shopware) store
- Move #6 (Triple Whale attribution) shipped — verified published ≥30d with cohort LTV dashboard producing daily LTV-by-source numbers
- Move #5 (Klaviyo + Postscript) shipped — verified published flows with ≥6-week revenue baseline
- Move #8 (loyalty program) shipped — Smile.io / Yotpo Loyalty / LoyaltyLion installed with points + tiers configured
- Move #153 (review-generation/UGC engine) shipped OR planned (the review-substrate feeds into the LTV prediction as a 30-day signal)
- ≥100 fulfilled orders/month (the threshold below which per-customer LTV scoring is too noisy to ship)
- A customer-data-layer: Shopify Customer + Klaviyo profile + Triple Whale customer OR a Segment / Rudderstack / mParticle CDP OR a Mixpanel / Amplitude / Heap / PostHog analytics layer with per-user event-stream

You do NOT have:
- A per-customer LTV score (operators run cohort-LTV aggregates that average the whale and the minnow; the canonical 2026 pattern is per-customer prediction)
- A churn-risk scoring model (operators run winback on the entire lapsed-customer cohort; the canonical pattern is winback-priority-by-churn-risk × recovery-probability × LTV-potential)
- An automated winback-prioritization queue (operators manually pick who to email/SMS; the canonical pattern is a per-day-priority-queue that ranks customers by lift-per-touch)
- LTV-tier suppression in the sunset flow (operators sunset subscribers regardless of their LTV potential; the canonical pattern is "never sunset a high-LTV customer")
- Paid-audience segmentation by LTV tier (operators push the entire email list to Meta + Google custom audiences; the canonical pattern is "high-LTV audience + mid-LTV audience + low-LTV audience + churn-risk audience")
- Per-customer LTV overlay in Triple Whale's cohort-LTV dashboard (operators look at aggregate cohort-LTV; the canonical pattern is per-customer-LTV that updates daily)

You are NOT:
- Pre-revenue (<$10k/mo) — skip; the 100-fulfilled-orders/month prereq gates this
- B2B-only with <50 consumer customers/month — predictive LTV scoring is too noisy
- Selling digital goods / SaaS — the LTV model assumes physical-fulfillment + reorder cadence; SaaS uses NRR-based LTV models (different)
- Brands with no historical order data — the RFM-style scoring needs ≥6 months of orders to compute meaningful churn probabilities

## What "best in class" looks like

A best-in-class **predictive-LTV + churn-scoring engine** for a $5M GMV DTC operator looks like 5 layers wired end-to-end with documented governance + per-customer scoring + per-cohort decay + per-channel audience-push + measurement-loop:

**Layer 1 — Data substrate (Klaviyo + Triple Whale + Shopify + analytics layer).** Per-customer-event-stream wired into (a) Klaviyo Predictive Segments (`Predicted Customer Lifetime Value` + `Predicted Gender` + `Predicted Order Time` + `Predicted Next Order Date` — Klaviyo's built-in ML models trained on the operator's 6+ months of order data) + (b) Triple Whale Cohort LTV dashboard (per-cohort LTV at 30/60/90/180-day windows + per-customer LTV export) + (c) Shopify Customer Segments (Shopify's built-in `Customer segments` with `VIP` + `Loyal customers` + `At risk` + `Need attention` + `Dormant` + `New customers` — auto-generated from 90+ days of orders) + (d) Mixpanel/Amplitude predictive-scoring (optional but recommended: `Predicted Conversion` + `Predicted Churn` + `Predicted LTV` user-properties feeding into cohorts) + (e) Segment / Rudderstack CDP `predictive_traits` (predicted LTV + predicted churn score as user-traits) + (f) a **per-customer data-merge layer** that joins (Klaviyo profile + Triple Whale cohort + Shopify customer + analytics user-id + loyalty member-id + subscription-id) into a single canonical `customer_360` row per customer per day. Output: `customer_360` table with `customer_id`, `email`, `predicted_ltv_180d`, `predicted_churn_probability_90d`, `ltv_tier` (whale/high/mid/low), `churn_risk_tier` (critical/high/medium/low), `next_best_action` (winback_priority_1/2/3/sunset/tier_up/retain).

**Layer 2 — Churn-scoring engine (the canonical 6-feature RFM-style model + 4-suppression gates + 5-tier segmentation + per-cohort decay rate).** Per-customer churn-risk scoring combining (a) **6 canonical features**: `recency_days_since_last_order` (R) + `frequency_orders_180d` (F) + `monetary_total_180d` (M) + `review_count_lifetime` (the Move #153 review-substrate signal — customers with 1+ review have 20–40% lower churn probability per Spiegel 2024 + Northwestern 2024) + `email_engagement_score` (the Klaviyo open-rate + click-rate + last-open-days signal) + `loyalty_tier` (VIP customers have 50–70% lower churn probability per Smile.io 2024) + (b) **4 suppression gates**: NEVER-churn-score a customer who (i) ordered in last 30d (active), (ii) has 5+ orders lifetime (whale — different engagement model), (iii) is in an active winback flow (already being treated), (iv) is on the do-not-suppress list (CS-team-managed). Per-cohort decay rate: a customer at `R=30/F=2/M=$80` decays at ~0.7% churn-probability per day. The canonical 5-tier segmentation: `whale` (predicted LTV $500+) + `high` (predicted LTV $200–$500) + `mid` (predicted LTV $50–$200) + `low` (predicted LTV $0–$50) + `churn_critical` (predicted LTV $0 with >70% churn probability). Per-cohort scoring: customers in the same `RFM` segment are not necessarily the same score — the per-cohort decay-rate + per-cohort LTV-trajectory multiplier refines the score. Output: per-customer `churn_score` (0–1), `ltv_tier` (whale/high/mid/low/churn_critical), `next_best_action` (winback_priority_1/2/3/sunset/tier_up/retain).

**Layer 3 — Winback + sunset + tier-up prioritization queue (the "who to contact in what order" decision layer).** Per-day-priority-queue ranking customers by `(recovery_probability × predicted_ltv × inverse_suppression_score)` so a $300-LTV customer with 80% recovery probability ranks higher than a $50-LTV customer with 95% recovery probability. The canonical 4-tier priority-queue: **Priority 1 (winback-immediate)** = high-LTV + high-churn-risk + recent-purchase (the $300-LTV customer who hasn't ordered in 90 days). Send a personalized email + SMS within 24h. **Priority 2 (winback-deferred)** = mid-LTV + medium-churn-risk (the $80-LTV customer at 75% churn-risk). Send a flow-triggered email at +7d after churn-risk threshold crossed. **Priority 3 (tier-up)** = high-LTV + low-engagement (the $400-LTV customer who never opens emails). Send a tier-up-promotion (loyalty-points-bonus + early-access) at +30d. **Priority 4 (retain)** = critical-churn-risk + high-LTV (the $500-LTV customer at 90% churn-risk). Route to CX-team Slack channel with customer context (last order, review status, email-engagement, loyalty-tier) for a personal-outreach within 24h. **Sunset suppression**: never send sunset-flow email/SMS to a `whale` or `high` LTV customer; suppress the sunset-suppression-list with `ltv_tier != 'whale' && ltv_tier != 'high'`. Output: per-day-priority-queue with per-customer `priority_tier` + `next_action` + `send_window`.

**Layer 4 — Paid-audience segmentation by LTV tier (Meta + Google + TikTok + Snap + Pinterest custom-audience push).** Per-channel custom-audience push of (a) `high_value_customers` (whale + high LTV tier, ≥$200 predicted LTV) — used as lookalike seed + retargeting audience + exclusion audience for low-value-only campaigns; (b) `mid_value_customers` (mid LTV tier, $50–$200) — used as retargeting audience; (c) `churn_risk_customers` (high-churn-probability customers regardless of tier) — used as a winback-campaign audience with creative featuring loyalty-program + new-product-launch; (d) `new_customer_seed` (first 30-day customers with high predicted LTV) — used as lookalike seed for new-customer acquisition campaigns. The canonical `Triple Whale → Meta CAPI` + `Triple Whale → Google EC` + `Triple Whale → TikTok EAPI` custom-audience-sync runs daily via Triple Whale's `audience_activations` feature OR Hightouch / Census reverse-ETL to Meta + Google + TikTok + Snap + Pinterest audience-APIs. Output: 4 custom audiences per channel × 5 channels = 20 audience-sync jobs + a `daily_audience_sync.csv` log.

**Layer 5 — Triple Whale cohort LTV overlay + measurement loop (the per-customer LTV projection that compounds Move #6 attribution).** Per-customer LTV overlay on Triple Whale's cohort-LTV dashboard: (a) the `Cohort LTV` widget gets a `Predicted vs Actual` overlay showing the difference between cohort-aggregated LTV and the per-customer predicted-LTV distribution (this surfaces the variance — a cohort with $120 average LTV might have 5 customers at $800 LTV and 30 customers at $20 LTV, which the cohort-average masks); (b) the `Top Customers` widget sorts by `predicted_ltv_180d DESC` + `actual_ltv_180d DESC` so the operator sees both the prediction AND the realization; (c) the `Channel ROI` widget gets a per-channel `LTV by LTV-tier` breakdown (e.g. `Meta drives 40% of whale-tier customers, Google drives 35%, TikTok drives 15%, organic drives 10%`) — this is the canonical signal for "should we shift Meta → TikTok spend given LTV by tier"; (d) a `Churn-risk customer LTV-at-risk` widget showing the aggregate LTV of customers at critical/high churn-risk (the total revenue-at-risk if those customers churn). The measurement loop: `predicted_ltv_180d` is updated daily + `actual_ltv_180d` is updated weekly + the model's `mean_absolute_error` (MAE) is published to the dashboard weekly so the operator sees whether the prediction is converging or drifting. Output: Triple Whale dashboard with 4 new widgets + a `predictive_ltv_health.json` export showing MAE + prediction-confidence + coverage (what % of customers have a score).

## The build (4-step, 8–16 hours for a competent operator)

### Step 1 — Enable Klaviyo Predictive Segments + Triple Whale Cohort LTV (2 hours)

1.1. In Klaviyo: navigate to `Audience → Predictive Analytics → Predictive Segments`. Enable `Predicted Customer Lifetime Value` + `Predicted Gender` + `Predicted Order Time` + `Predicted Next Order Date`. Klaviyo's ML model trains on the operator's order history — verify the model has ≥500 customers with ≥1 order each before activating. 1.2. In Triple Whale: navigate to `Customer Cohorts → Cohort LTV`. Verify the dashboard is producing daily LTV-by-source numbers + the `Top Customers` widget is populated. Enable Triple Whale's `Customer Export` to ship the per-customer LTV data to BigQuery / Snowflake / Postgres / S3. 1.3. In Shopify: navigate to `Customers → Segments`. Shopify's built-in segments (`VIP` + `Loyal customers` + `At risk` + `Need attention` + `Dormant` + `New customers`) auto-generate from 90+ days of orders. Verify each segment has ≥100 customers; smaller segments are too noisy. 1.4. (Optional, recommended at $5M+ GMV) In Mixpanel or Amplitude: enable `Predictive Scoring` (Mixpanel `Predictive Churn` + `Predicted LTV`; Amplitude `Forecast`). Train the model on 6+ months of event-stream. Verify MAE <20% before activating in production flows. 1.5. **Verify**: Klaviyo Predictive Segments shows `Active` for all 4 segments + Triple Whale Cohort LTV dashboard populates with per-customer rows + Shopify segments show ≥100 customers per segment.

### Step 2 — Build the customer-360 data merge + churn-scoring engine (4–6 hours)

2.1. Create a `customer_360` table (in BigQuery / Snowflake / Postgres / a Google Sheet for stores without a warehouse). Columns: `customer_id`, `email`, `predicted_ltv_180d` (from Klaviyo), `cohort_ltv_180d` (from Triple Whale), `loyalty_tier` (from Smile.io), `review_count_lifetime` (from Move #153 review-app), `recency_days_since_last_order`, `frequency_orders_180d`, `monetary_total_180d`, `email_open_rate_30d`, `email_click_rate_30d`, `last_open_days`, `last_order_date`. 2.2. Build the **6-feature churn-scoring model**: `churn_score = sigmoid(0.30 × recency_normalized + 0.20 × frequency_inverse_normalized + 0.15 × monetary_normalized + 0.10 × review_count_inverse_normalized + 0.10 × email_engagement_inverse_normalized + 0.15 × loyalty_tier_inverse_normalized)`. Each feature is normalized to [0, 1] using min-max scaling across the customer base. The weights are the canonical 2026 weighting per Klaviyo + Triple Whale + Spiegel 2024 benchmarks. 2.3. Apply the **4 suppression gates**: NEVER score a customer who (i) ordered in last 30d → set `churn_score = 0`; (ii) has 5+ orders lifetime → set `churn_score = 0.05` (whale-floor); (iii) is in an active winback flow → set `churn_score = 0` (already being treated); (iv) is on the do-not-suppress list → set `churn_score = 0`. 2.4. Compute the **5-tier LTV segmentation**: `whale` (predicted LTV $500+) + `high` ($200–$500) + `mid` ($50–$200) + `low` ($0–$50) + `churn_critical` ($0 with churn_score >0.70). 2.5. Compute the **`next_best_action`**: per-customer decision tree mapping `(ltv_tier × churn_score)` to `(priority_1_winback_immediate / priority_2_winback_deferred / priority_3_tier_up / priority_4_retain_personal / retain_passive / sunset)`. 2.6. Refresh the `customer_360` table daily (cron at 02:00 local lowest-traffic window). 2.7. **Verify**: `customer_360` has ≥80% of active customers with non-null `predicted_ltv_180d` + `churn_score` + `ltv_tier` + `next_best_action` populated; MAE <20% on a 14-day backtest of `actual_ltv_180d` vs `predicted_ltv_180d`.

### Step 3 — Build the prioritization queue + Klaviyo flow wiring (3–4 hours)

3.1. Create the **winback-priority queue**: per-day query that ranks customers where `next_best_action IN ('priority_1_winback_immediate', 'priority_2_winback_deferred', 'priority_3_tier_up', 'priority_4_retain_personal')` ORDER BY `(predicted_ltv_180d × (1 - churn_score)) DESC LIMIT 500`. Export to a per-day CSV that Klaviyo reads via `klaviyo:list` import OR a per-day Klaviyo segment via `POST /api/v2/lists` API. 3.2. In Klaviyo: build a **Priority-1 Winback flow** triggered by segment-membership-in-`winback_priority_1_today`. Email cadence: 1 email at +0h (`Hi [first_name], it's been a while since your last [product_category] order — we've added a special 15% off to your account: [CODE]`) + 1 SMS at +24h (`Your 15% off is waiting — [shortened-link]`) + 1 email at +7d if no purchase (`Last chance — your 15% off expires in 48h`). Suppress on `placed_order` event. 3.3. In Klaviyo: build a **Priority-3 Tier-up flow** triggered by segment-membership-in-`tier_up_priority_3_today`. Email cadence: 1 email at +0h (`You're close to [tier_name] — earn [N] more points by [date]`) + 1 SMS at +24h if no engagement. Suppress on `tier_up_achieved` event. 3.4. In Klaviyo: build a **Priority-4 Retain (CX-team) flow** triggered by segment-membership-in-`retain_priority_4_today`. Email cadence: 1 internal email to `cx-team@brand.com` with full customer context (last 5 orders + review count + email engagement + loyalty tier + predicted LTV). CX-team sends a personal outreach within 24h. Suppress on `placed_order` event OR `do_not_retain` flag. 3.5. In Klaviyo: **suppress the existing sunset flow** for `ltv_tier IN ('whale', 'high')`. Edit the sunset flow's filter to exclude the `whale_or_high_ltv_suppression` segment. 3.6. **Verify**: Priority-1 winback flow fires for test customer in 5 min + Priority-3 tier-up flow fires for test customer in 5 min + Priority-4 retain flow fires for CX-team email in 5 min + sunset flow excludes whale/high LTV customers in the suppression test.

### Step 4 — Build the paid-audience sync + Triple Whale overlay (3–4 hours)

4.1. Build the **daily custom-audience sync** for Meta + Google + TikTok + Snap + Pinterest. Use Hightouch / Census reverse-ETL OR Triple Whale's `audience_activations` feature to push 4 audiences per channel × 5 channels = 20 audience-sync jobs daily at 03:00 local. Audience definitions: (a) `high_value_customers` = `ltv_tier IN ('whale', 'high')` (≥$200 predicted LTV); (b) `mid_value_customers` = `ltv_tier = 'mid'`; (c) `churn_risk_customers` = `churn_score > 0.60` (regardless of LTV tier); (d) `new_customer_seed` = `customer_age_days < 30 AND predicted_ltv_180d > 200`. 4.2. Verify each audience-sync job with the canonical audience-size sanity check: `high_value_customers` should be 5–15% of total customers; `mid_value_customers` should be 15–30%; `churn_risk_customers` should be 10–25%; `new_customer_seed` should be 1–5%. If any audience is outside this band, the LTV model is mis-calibrated (revisit Step 2 weights). 4.3. In Triple Whale: add 4 new widgets to the cohort-LTV dashboard. (a) `Predicted vs Actual LTV` widget showing the per-customer distribution; (b) `Top Customers by Predicted LTV` widget; (c) `Channel ROI by LTV Tier` widget (Meta % of whale-tier customers + Google % + TikTok % + organic %); (d) `LTV-at-Risk` widget showing aggregate predicted LTV of customers at critical/high churn-risk. 4.4. **Verify**: Meta custom audience `high_value_customers` has 200–2000 members depending on store size + Google Customer Match `high_value_customers` has 200–2000 members + Triple Whale dashboard shows the 4 new widgets with non-empty data + a 5-sample manual LTV-vs-prediction spot-check shows MAE <20% on the prediction.

## Common pitfalls (15 from real builds)

1. **Predicting LTV on customers with <1 order — the model returns null OR a default of $0, masking the whale-vs-minnow variance.** The canonical 2026 pattern is to seed the model with `predicted_ltv_180d = (cohort_median_180d × confidence_factor)` for customers with <1 order, where `confidence_factor` is the per-store ratio of predicted-vs-actual MAE on customers with ≥1 order. Operators frequently skip the seed-value pattern, treating 1-order customers as "score=null" and dropping them from winback/sunset/suppression logic. Result: the highest-ROI subset (1-order customers with predicted high LTV) gets no treatment. **Fix:** always seed with cohort median × confidence factor for customers with <1 order.

2. **Using predicted LTV at 30-day window for winback targeting — the prediction is too noisy (MAE 20–30%) and the operator gets burned by false-positive winbacks.** The canonical 2026 pattern is predicted LTV at 180-day window (the Klaviyo `Predicted Customer Lifetime Value` is 180-day by default; Triple Whale's `Cohort LTV` is 30/60/90/180-day configurable). Operators frequently use 30-day LTV for winback because "we want to be conservative" — but the 30-day prediction has higher variance and the operator misses the whale-tier signal. **Fix:** use 180-day predicted LTV for winback targeting; use 30-day predicted LTV only for daily-budget allocation decisions where recency matters.

3. **Churn-score does NOT suppress on `placed_order` event — a customer who orders after entering the Priority-1 winback flow keeps getting winback emails.** The canonical 2026 pattern is the winback flow's filter MUST exclude customers with `placed_order` event in last 7 days (NOT just suppression on the immediate `placed_order` event — exclude for 7 days to avoid post-purchase weirdness). Operators frequently build the winback flow with only the immediate `placed_order` suppression, missing the post-purchase window. Result: customer orders + receives 3 more winback emails + feels harassed → 1-star review or unsubscribe. **Fix:** suppress winback flow on `placed_order` event in last 7 days; suppress for 30 days if the order is >$100 (high-AOV customers are more sensitive to overlap).

4. **Sunset suppression list excludes whale/high LTV — but the suppression is on the email-list level, not the per-customer profile, so a customer who upgrades from low-LTV to high-LTV stays on the sunset list.** The canonical 2026 pattern is the sunset flow's filter is `ltv_tier != 'whale' && ltv_tier != 'high'` evaluated daily against the `customer_360` table (per-customer filter, not list-level). Operators frequently use a static suppression list uploaded once and never refreshed. Result: customers who should NOT be sunsetted (because they just became a whale) still get the sunset email. **Fix:** refresh the sunset suppression filter daily against `customer_360.ltv_tier`; never use a static suppression list.

5. **Paid-audience sync runs daily but the audience-size is unmonitored — a Hightouch sync failure silently drops the audience to 0 members, killing the campaign's targeting.** The canonical 2026 pattern is a daily `audience_sync_health.json` log that records `(audience_name, audience_size, sync_status, sync_runtime_seconds)` per channel per day + a Slack alert if `audience_size < (baseline_size × 0.5)` (50% of baseline). Operators frequently assume the audience-sync "just works" — until a campaign is firing at $0 CPC and they realize the audience has been empty for 2 weeks. **Fix:** wire the daily audience-sync log + Slack alert + a weekly audience-size-trend review.

6. **Klaviyo Predictive Segments are enabled but the operator doesn't sync them to flows — the predictions sit in Klaviyo and never drive a flow action.** The canonical 2026 pattern is the predictive segment is referenced in the flow's filter condition (e.g. `where customer is in segment "Predicted High LTV"`). Operators frequently enable Predictive Segments, see the segment membership count, and assume "the system is now using LTV" — but no flow actually references the segment. **Fix:** reference the predictive segment in at least 1 flow's filter condition (cart-abandon OR welcome OR winback); verify the flow's `audience.size` includes the high-LTV subset.

7. **Mixpanel/Amplitude predictive scoring is trained on all events without excluding bot traffic — the model is contaminated by 10–30% bot events, dropping MAE by 5–15 percentage points.** The canonical 2026 pattern is bot-traffic exclusion in the model training set (filter on `user_agent != bot` OR `session_id NOT IN (bot_session_ids)`). Operators frequently train the model on raw event-stream without the bot filter. Result: the model's churn prediction is biased — bot traffic has 0% conversion-rate, contaminating the churn-probability distribution. **Fix:** filter bot traffic in the model training set; verify the model's MAE on the human-only test-set is within 5pp of the all-traffic MAE.

8. **Triple Whale Cohort LTV widget shows aggregate LTV without the per-customer distribution — operator misses the whale concentration signal.** The canonical 2026 pattern is the operator EXPORTS the per-customer LTV from Triple Whale (`Customer Export` feature) into BigQuery / Snowflake + builds a per-customer LTV distribution visualization (e.g. `histogram(predicted_ltv_180d, bins=20)` showing the 5% whale bar + the 30% minnow bar + the 65% middle). Operators frequently look at the Triple Whale Cohort LTV widget showing `$120 average` and assume that's the LTV for budget allocation. Result: the whale concentration is invisible, Meta gets allocated the same budget as TikTok despite Meta driving 60% of the whales. **Fix:** export per-customer LTV + visualize the distribution; use the per-tier channel-attribution to drive budget allocation.

9. **Next-best-action decision tree uses hardcoded thresholds (e.g. `ltv_tier = 'high' AND churn_score > 0.70 → priority_4_retain`) — but the thresholds don't account for store-specific variance.** The canonical 2026 pattern is the decision-tree thresholds are CALIBRATED to the operator's historical winback data: per-store ratio of `priority_4_retain → save_rate` AND `priority_1_winback_immediate → purchase_rate` AND `priority_3_tier_up → tier_up_rate`. Operators frequently copy the canonical thresholds from Move #154 reference without calibrating, getting 30–60% false-positive rate on priority_4 (CX-team wastes time on customers who wouldn't churn anyway). **Fix:** calibrate thresholds per-store using the first 30 days of priority-tier outcome data; re-calibrate quarterly.

10. **Churn-score includes `review_count_lifetime` (Move #153 signal) but the move is NOT YET SHIPPED — the signal is null for all customers and the model's weight is wasted.** The canonical 2026 pattern is the churn-score model has a "feature-availability gate" — if a feature is null for >50% of customers, the feature is dropped from the score until it stabilizes (or its weight is redistributed). Operators frequently build the Move #154 churn model with the Move #153 feature as a load-bearing input, but ship Move #154 BEFORE Move #153 — result: the model is missing 30% of its expected weight, MAE degrades by 5–10pp. **Fix:** ship Move #153 FIRST (or in parallel within 30 days); verify `review_count_lifetime` is populated for ≥50% of customers before including it in the Move #154 model.

11. **CX-team Priority-4 retain email contains all the customer context but no clear "what action to take" — CX agents waste time deciding what to do.** The canonical 2026 pattern is the Priority-4 retain email template includes a `Recommended Action:` block: "Suggested: [personal email template + 15% off code + free-shipping offer + loyalty-points bonus]. Reason: [predicted LTV $X, last order Y days ago, 3+ reviews = high-save-probability]." Operators frequently send the CX-team a raw data dump without the recommended-action block, and CX agents either ignore the email OR take inconsistent actions. **Fix:** include the recommended-action block in every Priority-4 retain email; track `recommended_action_taken_rate` (target: >70%).

12. **The 6-feature churn-score model uses equal weights for all features — but email-engagement and recency are 2–3× more predictive than monetary + frequency.** The canonical 2026 pattern is the weights are LEARNED from the operator's data via logistic regression on `(recency, frequency, monetary, review_count, email_engagement, loyalty_tier) → churn_within_90d` (binary target). Operators frequently copy the canonical weights from Move #154 reference without fitting the model to their data. Result: the model's MAE is 15–25% instead of the achievable 8–12%. **Fix:** fit logistic regression per-store on historical data; publish the per-store weights to the `customer_360` table.

13. **Per-customer LTV is recomputed daily but the customer sees the new LTV-tier in their Klaviyo profile before the operator can audit the change — a customer gets a Priority-1 winback email 30 minutes after their LTV-tier jumped from `mid` to `high`.** The canonical 2026 pattern is a **delayed-action queue**: the daily recompute generates `pending_actions[]` per customer, but the actions are EXECUTED on +24h (giving the operator time to audit any unexpected tier changes via a daily Slack alert with the top 10 LTV-tier-changes). Operators frequently run the recompute + the action-execution in the same cron job, getting emails sent before the operator sees the tier change. **Fix:** separate recompute (daily 02:00) from action-execution (daily 03:00) with a +24h delay queue + a daily Slack alert with top 10 tier changes.

14. **Tier-up Priority-3 flow invites customers to a tier they would naturally reach in 30–60 days — the operator over-discounts, cannibalizing the natural tier-up.** The canonical 2026 pattern is the tier-up flow ONLY invites customers whose tier is achievable in <30 days (e.g. "earn 200 more points by [date]") — NOT customers whose tier is 6+ months away (those get a generic loyalty-program-promotion, not a tier-up-specific invite). Operators frequently build the tier-up flow with no distance-to-tier check, inviting customers to the next tier regardless of achievability. Result: the operator gives 15% off + 2× loyalty points to customers who would have organically tiered up at full price in 60 days. **Fix:** add `distance_to_tier_days < 30` to the Priority-3 tier-up segment definition.

15. **Per-customer `customer_360` table is rebuilt from scratch daily, losing historical LTV-changes — the operator cannot answer "how did this customer's LTV tier change over the last 90 days."** The canonical 2026 pattern is the `customer_360` table is APPEND-ONLY with `effective_date` column, so the operator can query `ltv_tier_history` per customer per day. Operators frequently use `CREATE OR REPLACE TABLE customer_360` daily, losing the history. Result: the operator cannot answer "is our model getting better at predicting churn" (no actual-vs-predicted time-series) OR "what was this customer's LTV when they placed their last order" (lost). **Fix:** append-only `customer_360` with `effective_date` + a 90-day rolling history view.
