## Common pitfalls (18 from real builds)

**Cluster A — per-discovery-decision-actor-resolution-time-versioning-overlay-router + bucket-assignment + decoder-family-router**

1. **Treating rule-version as a static property of the rule-engine rather than a streaming signal that drifts per-deployment.** The Pillar B Step 1 versioning-overlay-window-bucket-assignment reads Move #155's `current-rule-version` field as if it were a per-rule cache key. **Fix:** treat `current-rule-version` as a per-rule × per-deployment × per-stream-processing-pipeline streaming signal — emit a `rule-version-change` event every time Move #155's rule-version classifier flips a rule from version-N to version-M; the Pillar B Step 1 bucket-assignment MUST subscribe to this event stream and re-bucket historical events whose version-status shifted within the canonical 24-hour lookback window.

2. **Confusing the canonical `agentic-commerce-versioning-overlay-completeness-score` (0.0–1.0) with the canonical `version-status` (5-state discrete).** A rule-version with completeness-score=0.74 is NOT necessarily version-deprecated — version-status boundaries are non-linear and per-deployment per Move #155 benchmarks. **Fix:** use Move #155's version-status classifier directly as the Pillar B Step 1 bucket-assignment source; the completeness-score is a SECONDARY signal for the Pillar D industry-benchmark-engine only.

3. **Hardcoding the 5-resolution-time-versioning-overlay-window boundaries to Move #162's 5-resolution-time-merchant-readiness-overlay-window SLAs.** The merchant-readiness-overlay SLAs (sub-2s / sub-30s / sub-5min / sub-1h / sub-24h) are NOT identical to the versioning-overlay SLAs because version-canonical rule-versions expect sub-100ms stream-processing latency on synchronous-stream windows. **Fix:** define Move #163's 5-resolution-time-versioning-overlay-window SLAs separately per version-canonical = sub-2s / version-current = sub-30s / version-deprecated = sub-5min / version-archived = sub-1h / version-legacy = sub-24h; document the difference in the operator-UX dashboard's `versioning-overlay-vs-merchant-readiness-overlay-comparison` widget.

**Cluster B — per-discovery-decision-actor-resolution-time-versioning-overlay-freshness + staleness + backpressure + event-stream-emission**

4. **Window-1 (version-canonical) freshness-floor regression from sub-2s to sub-5s after a Move #162 router refactor.** **Fix:** add a Move-#163-window-1-freshness-floor-canary that pages the on-call SRE the moment Move-#163's version-canonical-window freshness-floor exceeds 2s p99 over a 15-minute window; gate any Move #162 router deploy that pushes version-canonical freshness above 2s p99.

5. **Window-5 (version-legacy) staleness-violation false-negative because version-legacy rule-versions emit at most 1 event per 24h.** **Fix:** the staleness-ceiling for window-5 is 24h, but the freshness-emission floor for window-5 MUST be at least 1 event per rule-version per 24h; if no event arrives within 24h, emit a synthetic `version-legacy-staleness-heartbeat` event so the dashboard reflects the rule-version's true state.

6. **Backpressure-floor collision between synchronous-stream + change-data-capture-stream pipelines on version-canonical rule-versions during peak event-storm.** **Fix:** Pillar B Step 2 backpressure computation reads each stream-processing-pipeline's queue-depth-or-rate-limiter-headroom independently and tags each event with `backpressure-source-stream-pipeline`; the canonical backpressure-floor is per-pipeline (queue-depth <100/<1k/<10k/<100k/<1M + rate-limiter-headroom >50%/>40%/>30%/>20%/>10% per window × per pipeline).

7. **Event-stream emission drop on Move-#163 → Move-#162 back-feed when the Move-#162 router is degraded.** **Fix:** the Move-#163 → Move-#162 back-feed event stream is a SEPARATE Kafka topic (`versioning-overlay-resolution-time-pressure-v1`); if Move-#162's main event-stream topic degrades, Move-#163 still emits to the back-feed topic and Move-#162 still receives per-resolution-time-versioning-overlay-pressure updates.

**Cluster C — per-discovery-decision-actor-resolution-time-versioning-overlay-fairness + coverage + versioning + decomposition**

8. **Anti-monopoly-floor violation when one rule-version dominates a version-canonical window (e.g. a single `1.0` rule-version = 60% of version-canonical events).** **Fix:** the anti-monopoly-floor per-resolution-time-versioning-overlay-window × per-discovery-decision-actor-id is per-discovery-decoder-family, NOT per-rule-version; if a single rule-version >40% of a per-window × per-decoder-family bucket, split the rule-version's events across multiple `discovery-decision-actor-id` partitions and surface a `rule-version-monopoly-warning` chip on the operator-UX dashboard.

9. **Coverage-benchmark false-positive when Move-#155 current-rule-version field is absent on legacy rule-versions (pre-2026 rule-engines).** **Fix:** Pillar C decomposition decoder-set falls back to the canonical Semver-2.0-2026 major.minor.patch tag when Move-#155 field is absent; the operator-UX dashboard surfaces a `coverage-source-mix` widget showing the % of events from Move-#155 vs Semver-2.0-2026 per window.

10. **Move-#163 → Move-#162 → ... → Move-#123 version-lineage drift when a Move-#155 schema-field is renamed (e.g. `current-rule-version` → `active-rule-version`).** **Fix:** Move-#163 versioning-watcher subscribes to Move-#155's schema-event-stream and re-emits historical events under BOTH the old AND new field names for the canonical 7-day migration window; the operator-UX dashboard surfaces a `versioning-drift-warning` chip whenever Move-#163 ingests a Move-#155 schema-rename event.

11. **Versioning-overlay-window × per-merchant-readiness-overlay decomposition mis-classification when a rule-version's `version-status` and `merchant-readiness-tier` are computed by different upstream signals (Move-#155 vs Move-#124).** **Fix:** Pillar C decomposition decoder-set reads the canonical `agentic-commerce-versioning-overlay-completeness-score` and the canonical `merchant-readiness-overlay-completeness-score` as cross-validation; surface a `cross-validation-mismatch-warning` chip when the two signals disagree by >0.20 completeness-score.

**Cluster D — per-discovery-decision-actor-resolution-time-versioning-overlay-cohort + merchant-impact + rollback-decision-audit + decomposition-deep**

12. **Cohort-impact false-positive when a version-canonical rule-version's events dominate the per-cohort aggregation.** **Fix:** Pillar B Step 3 aggregation-rollup is per-cohort × per-channel × per-rule-version; if a single version-canonical rule-version >30% of per-cohort events, surface a `cohort-impact-rule-version-monopoly` chip on the operator-UX dashboard.

13. **Merchant-impact regression when a version-status shift (version-canonical → version-deprecated) is treated as merchant-impact-positive rather than merchant-impact-negative.** **Fix:** the merchant-impact direction depends on the version-status direction: version-N → version-M where N<M is merchant-impact-negative (regressed); N>M is merchant-impact-positive (improved); the operator-UX dashboard's merchant-impact widget MUST classify shifts by direction and surface both directions.

14. **Rollback-decision-audit false-positive when the per-resolution-time-versioning-overlay-window freshness-floor regression is mis-classified as a rollback-trigger.** **Fix:** the canonical rollback-decision-audit-engine ONLY fires a rollback-decision when (a) freshness-floor regression >2× SLA for >15min AND (b) the merchant-impact direction is negative AND (c) the per-rollback-window decision is `rollback-now`; emit a `rollback-decision-audit-no-op` chip otherwise.

15. **Versioning-overlay-decomposition-deep (Pillar C sub-decomposition (e)) over-emission when per-failure-mode granularity explodes (12 canonical discovery-failure-modes × 5 version-status × 5 windows × 12 rollback-windows × 5-stream-processing-pipelines = 18,000 cells).** **Fix:** Pillar C decomposition decoder-set emits at most 1 cell per (per-resolution-time-versioning-overlay-window × per-failure-mode × per-stream-processing-pipeline); cells where the event-count <10 within the canonical 7-day window are aggregated to `failure-mode-stream-pipeline-cluster` for the operator-UX dashboard.

**Cluster E — per-discovery-decision-actor-resolution-time-versioning-overlay-recovery-decoder-decision + rollback-window-decision + cohort-impact-decomposition + event-stream-auto-feeding-back**

16. **Recovery-decoder-decision mis-fires when the canonical 5-window rollback-window-decision is `rollback-now` but the per-cohort-impact is positive.** **Fix:** the canonical recovery-decoder-decision is `rollback-now + cohort-impact-positive = rollback-defer`; only `rollback-now + cohort-impact-negative` actually fires a rollback-decision; surface a `recovery-decoder-decision-deferred` chip on the operator-UX dashboard.

17. **Rollback-window-decision collision when a rule-version-status shift (version-canonical → version-deprecated) within the canonical 1-hour window collides with a Move-#162 rollback-window-decision.** **Fix:** Move-#163's rollback-window-decision takes precedence over Move-#162's when the rule-version-status shift is the proximate cause; otherwise Move-#162 takes precedence; the operator-UX dashboard surfaces a `rollback-window-decision-source` chip showing which engine fired the decision.

18. **Event-stream-auto-feeding-back-loop-broken when Move-#155's `current-rule-version` field is dropped (Move-#155 schema evolution).** **Fix:** Pillar F back-feed emits BOTH a `current-rule-version-change` event AND a `versioning-overlay-resolution-time-pressure-change` event on every version-status shift; if Move-#155 drops the rule-version field, the back-feed still surfaces the versioning-overlay-pressure event with `current-rule-version-source: legacy-v1` so Move-#155 can fall back to the canonical Semver-2.0-2026 major.minor.patch tag.
