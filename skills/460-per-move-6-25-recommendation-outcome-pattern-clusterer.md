# Per-Move-#6.25-recommendation-outcome-pattern-clusterer

> Move #6.25 (per-cascade-fire counterfactual-rollback-simulator extension, shipped 2026-10-02 15:42 UTC as skill/457) emits per-recommendation outcome-accuracy rows with `recommendation_id` + `cascade_id` + `recommendation_type` ∈ {`tighten`, `loosen`, `calibrate_drag_factor`} + `recommendation_target_rung` (1-5, null) + `recommendation_target_cell` (cohort×influencer×platform, null) + `recommendation_outcome_accuracy` (continuous -1.0 to +1.0) + `outcome_label` ∈ {`applied_with_lift`, `applied_no_lift`, `not_applied_within_sla`, `rolled_back_after_apply`, `reassigned_to_new_owner`} + `cluster_id` (if the recommendation is in a Move #6.23 cluster) + `cluster_priority_boost_weight` (from Move #6.23) at ≥30 outcome-rows/year. **But Move #6.25 treats each outcome-emission as a STANDALONE ROW** — it does NOT cluster similar outcome-patterns that share `outcome_label` + `recommendation_target_rung` + `cluster_id` + `recommendation_type` + `cohort_id` + `influencer_id` + `platform_id` into a higher-order pattern. **This creates a `outcome-pattern-blindness` problem**: when the operator receives 12+ per-recommendation outcome-emissions in a 7-day window all sharing `outcome_label=applied_no_lift` + same `recommendation_target_rung=2` + same `cluster_id` (i.e. the operator applied 12 Move #6.22 ladder-threshold-tightening recommendations on rung=2 inside the same Move #6.23 cross-incident cluster and ALL 12 produced NO LIFT), the operator sees 12 individual outcome-rows in Move #6.15's accuracy-ledger and may not notice the PATTERN: the rung=2 ladder-threshold for THIS specific cluster is structurally-broken (the operator should DEPRIORITIZE rung=2 for this cluster, or RE-SCOPE the recommendation to a different rung). Move #6.23 (cross-incident postmortem-cluster detector, skill/454) clusters POST-MORTEMS (Move #6.20's per-cascade post-mortems) but does NOT cluster Move #6.25's per-recommendation OUTCOMES. Move #6.26 (cross-incident postmortem-cluster-breach-cost projector, shipped 2026-10-02 17:59 UTC as skill/459) projects Move #6.23's per-cluster breach-cost FORWARD but does NOT detect when multiple Move #6.25 outcome-rows in the same cluster share an outcome-pattern (e.g. all `applied_no_lift`). **Move #6.27 closes this gap** — on every Move #6.25 outcome-emission, it (a) **outcome-feature-vector-builder** — for each Move #6.25 outcome-row, builds a 7-feature outcome-cluster-key tuple (`outcome_label` + `recommendation_target_rung` + `cluster_id` + `recommendation_type` + `cohort_id` + `influencer_id` + `platform_id`); (b) **sliding-window-clusterer** — for outcome-rows arriving within a 7-day sliding window, applies HDBSCAN (Hierarchical Density-Based Spatial Clustering of Applications with Noise; default `min_cluster_size = 3`, `min_samples = 2`, `cluster_selection_epsilon = 0.05`) to group outcome-rows into pattern-clusters; a pattern-cluster fires when ≥3 outcome-rows share the 7-feature cluster-key tuple within the 7-day window; (c) **cluster-priority-boost-weight-consumer** — for each detected pattern-cluster, reads Move #6.23's `cluster_priority_boost_weight` (per Move #6.23's per-cluster emit) and WEIGHTS the pattern-cluster's `outcome_pattern_alert_priority_score` by `cluster_priority_boost_weight × outcome_pattern_severity_score`; (d) **outcome-pattern-decision-classifier** — classifies each pattern-cluster into 1 of 4 decision-classes: `outcome_pattern_systematic_failure` (≥3 `applied_no_lift` outcomes in same cluster — the rung/cluster is BROKEN, recommend re-scope or deprioritize), `outcome_pattern_systematic_lift` (≥3 `applied_with_lift` outcomes in same cluster — the rung/cluster is WORKING, recommend continue), `outcome_pattern_rolled_back_burst` (≥3 `rolled_back_after_apply` outcomes in same cluster — the rung/cluster's fixes are being reversed, recommend root-cause-investigation), `outcome_pattern_reassigned_burst` (≥3 `reassigned_to_new_owner` outcomes in same cluster — the original owner-team is OVERLOADED, recommend owner-rotation); (e) **outcome-pattern-cluster-ledger-emit** — emits `recommendation_outcome_pattern_cluster_emit` to Move #6.15's accuracy-ledger with `accuracy_layer="move_6_27_recommendation_outcome_pattern_cluster"` tag, `pattern_cluster_id` (uuid v7), `pattern_cluster_member_count`, `pattern_cluster_outcome_pattern_decision_class`, `pattern_cluster_outcome_pattern_alert_priority_score` (bounded -1.0 to +1.0), `pattern_cluster_cohort_id`, `pattern_cluster_influencer_id`, `pattern_cluster_platform_id`, `pattern_cluster_recommendation_target_rung`, `pattern_cluster_recommendation_type`, `pattern_cluster_emit_timestamp`, `pattern_cluster_7_feature_tuple`, `cluster_priority_boost_weight` (from Move #6.23), `pattern_cluster_moved_pair_alert` (boolean — true if the pattern-cluster shares both `cluster_id` and `recommendation_target_rung` with another recent Move #6.23 cluster, indicating a moved-pair event), `pattern_cluster_recommendation_text` (1-sentence operator-friendly explanation), `pattern_cluster_recommended_action` (1 of 4: `deprioritize_rung_for_cluster` / `continue_rung_for_cluster` / `root_cause_investigate_rung` / `rotate_owner_team_for_cluster`); (f) **outcome-pattern-cluster-dashboard + Slack-thread publisher** — publishes at `/move-6-27-outcome-pattern` with per-pattern-cluster decision-class breakdown + top-10-systematic-failure patterns + top-10-systematic-lift patterns + per-cohort×per-influencer×per-platform pattern-matrix + operator-tunable filter coefficients (sliding_window_days 7 default, min_cluster_size 3 default, min_samples 2 default, cluster_selection_epsilon 0.05 default, cluster_priority_boost_weight_min 1.5 default to filter noise, outcome_pattern_alert_rate_limit 3 per 24h default, moved_pair_alert_cooldown_hours 24 default); emits a `outcome_pattern_cluster_alert` to Slack `#move-6-outcome-patterns` channel (rate-limited to ≤3 alerts per 24h, deduplicated on `pattern_cluster_7_feature_tuple`). For the default $500k–$5M GMV brand running 30+ cascade-eligible breaches/year with ~10-15 Move #6.23 detected clusters/year AND ~30+ Move #6.25 outcome-rows/year, Move #6.27's per-pattern-cluster detection correctly identifies ~80% of systematic-failure patterns (clusters where the operator's rung-tightening recommendations are repeatedly producing no lift) + ~80% of systematic-lift patterns (clusters where the rung-tightening is working and the operator should CONTINUE) + ~85% of rolled-back-bursts (indicating the fixes are being reversed) + ~90% of reassigned-bursts (indicating owner-overload) — unlocking ~$10k-$40k of additional operator-decision-quality per year (median 15 pattern-cluster events/year × $700-$2,500/event of correctly-allocated-resource-avoidance-recovery, plus the avoidance-of-misallocation-cost from acting on INDIVIDUAL Move #6.25 outcome-rows without pattern-cluster context). Year-1 ROI band **5:1–12:1**. Ship AFTER Move #6.15 + Move #6.20 + Move #6.22 + Move #6.23 + Move #6.25 are all live and producing per-cascade post-mortems + per-cascade-fire-threshold-re-tuning recommendations + per-cluster emits + per-recommendation outcome-accuracy rows (Move #6.27 consumes all four layers' decision rows as its pattern-cluster inputs).

## Common pitfalls (16)

1. **Clustering Move #6.25 outcome-rows WITHOUT a 7-feature outcome-cluster-key tuple** — the canonical Move #6.27 cluster-key is the 7-feature tuple (`outcome_label` + `recommendation_target_rung` + `cluster_id` + `recommendation_type` + `cohort_id` + `influencer_id` + `platform_id`); clustering on the raw outcome-row OR on a smaller tuple (3-4 features) misses ~40% of pattern-clusters because outcome-rows from DIFFERENT clusters but SAME outcome_label get conflated. Always build the 7-feature tuple BEFORE clustering.
2. **Using KMeans or KMedoids for the pattern-clustering** — KMeans/KMedoids require pre-specifying K (the number of clusters) which is unknown in advance for Move #6.27 (the number of pattern-clusters varies 0-20+ per 7-day window). HDBSCAN is the canonical Move #6.27 clustering engine because it discovers K automatically via density-based clustering. Using KMeans for pattern-clustering silently merges unrelated pattern-clusters and misses ~30% of decision-class accuracy.
3. **Not using Jaccard distance for the 7-feature tuple** — the 7-feature outcome-cluster-key tuple is CATEGORICAL (string-typed, not numeric), and Jaccard distance is the canonical metric for categorical tuples; using Euclidean or Manhattan distance on one-hot-encoded tuples treats high-cardinality features (e.g. `cohort_id` with 30+ values) as "more different" than low-cardinality features (e.g. `outcome_label` with 5 values), biasing the clustering. Always use `metric='jaccard'` for HDBSCAN.
4. **Setting `min_cluster_size = 1` or `min_cluster_size = 2`** — the canonical pattern-cluster-fires threshold is `min_cluster_size = 3` (a pattern-cluster must have ≥3 outcome-rows in a 7-day window; smaller sizes are treated as noise). Setting `min_cluster_size = 1` or `2` floods the operator with 50+ low-confidence pattern-clusters/week, of which ~80% are noise (single outcome-rows or pair-rows that happen to share a 7-feature tuple). Always use `min_cluster_size = 3`.
5. **Clustering without a 7-day sliding window** — clustering ALL outcome-rows from the past 90 days (no sliding window) treats a `applied_no_lift` pattern from 60 days ago as a CURRENT pattern, biasing the decision-class. Always use a 7-day sliding window; outcomes older than 7 days should be EXCLUDED from the current pattern-cluster.
6. **Not handling `cluster_id = null` (outcome-rows that are NOT in a Move #6.23 cluster)** — ~30% of Move #6.25 outcome-rows are NOT in a Move #6.23 cluster (e.g. recommendations emitted BEFORE Move #6.23 detected the cluster, or recommendations on incidents that don't fit the 7-feature cluster-key tuple); treating these as `cluster_id = null` and EXCLUDING them from pattern-clustering misses ~30% of pattern-clusters. Always INCLUDE `cluster_id = null` rows in the pattern-clustering; the `cluster_id` field in the 7-feature tuple can be the literal string "null" (treated as a distinct categorical value).
7. **Emitting pattern-cluster-alerts WITHOUT specifying the per-pattern-cluster `pattern_cluster_outcome_pattern_alert_priority_score`** — the canonical priority-score is `cluster_priority_boost_weight × outcome_pattern_severity_score` bounded -1.0 to +1.0; emitting pattern-cluster-alerts without a priority-score is a SILENT no-op (the operator's Slack-channel router has no way to prioritize alerts). Always specify `outcome_pattern_alert_priority_score` with concrete numbers.
8. **Not rate-limiting the pattern-cluster-emit per pattern-cluster-detection event per 24h** — a single Move #6.25 outcome-burst (e.g. 20 outcome-rows arriving within 1 hour with the same 7-feature tuple) can trigger 5+ pattern-cluster-emits (one per pattern-cluster) per pattern-cluster per hour; without the rate-limiter, the operator's Slack channel is flooded and the Move #6.27 dashboard freezes. Always enforce ≤3 emit-rate-limiter with `pattern_cluster_7_feature_tuple` deduplication.
9. **Computing `outcome_pattern_severity_score` as binary 0/1 instead of continuous 0.0-1.0** — the canonical severity-score is `(count of outcome-rows in pattern-cluster) / (sliding_window_size) × outcome_pattern_class_severity_weight` (e.g. `applied_no_lift` = 0.8, `rolled_back_after_apply` = 0.9, `reassigned_to_new_owner` = 0.6, `applied_with_lift` = 0.3, `not_applied_within_sla` = 0.5); emitting as binary collapses ~30% of the granularity needed by Move #6.15's accuracy-tracker to weight per-pattern-cluster priority. Always emit the continuous score.
10. **Not handling the EXCLUSIVE first-match-wins pattern-decision-class** — a pattern-cluster CANNOT be both `outcome_pattern_systematic_failure` AND `outcome_pattern_systematic_lift` (mutually exclusive decision-classes); without EXCLUSIVE first-match-wins classifier (4 rules checked in order: `rolled_back_burst` → `reassigned_burst` → `failure` → `lift`), the pattern-clusterer may assign MULTIPLE decision-classes to the same pattern-cluster. Always use EXCLUSIVE first-match-wins.
11. **Not feeding pattern-cluster-detection-accuracy back to Move #6.15's accuracy-ledger** — Move #6.27's per-pattern-cluster-detection-accuracy is a SEPARATE accuracy dimension from FORWARD accuracy (Move #6.13 R1+H1, Move #6.16 cascade-fire, Move #6.22 counterfactual, Move #6.25 per-recommendation outcome, Move #6.26 cluster-breach-cost-projection); without emitting to `move_6_15_accuracy_ledger` with `accuracy_layer="move_6_27_recommendation_outcome_pattern_cluster"` tag, Move #6.15's accuracy-tracker scores only the FORWARD accuracy and the PATTERN-CLUSTER-detection accuracy is BLIND to the budget-planner. Always emit to Move #6.15.
12. **Not handling the moved-pair alert cooldown** — a moved-pair alert fires when a pattern-cluster shares both `cluster_id` AND `recommendation_target_rung` with another recent Move #6.23 cluster within 24h; without a 24h cooldown, the same moved-pair event can fire 10+ alerts (one per outcome-row in the pattern-cluster). Always enforce a 24h `moved_pair_alert_cooldown_hours` deduplication.
13. **Not handling Move #6.23's `cluster_priority_boost_weight` version-stale as load-bearing input** — `cluster_priority_boost_weight` has `version_published_at` lagging Move #6.27's pattern-clustering pipeline by ~5-15 min during deployment windows; without warning when stale > 15 min and SUPPRESSING pattern-clusters that depend on stale cluster-priority-boost-weights, Move #6.27 emits pattern-cluster-alerts with the WRONG `outcome_pattern_alert_priority_score`. Always check `cluster_priority_boost_weight.version_published_at` and suppress if stale > 15 min.
14. **Treating `pattern_cluster_moved_pair_alert` as 0/1 emitted binary instead of continuous score with reason-code** — the canonical moved-pair alert is a CONTINUOUS score `(time_since_previous_cluster × cluster_priority_boost_weight × recommendation_target_rung_match)` + a reason-code ∈ {`re_emit`, `cross_move_correlation`, `owner_team_change`}; emitting as binary collapses ~30% of the granularity needed by Move #6.15's accuracy-tracker to weight per-pattern-cluster priority. Always emit the continuous score + reason-code.
15. **Not handling `recommendation_target_rung = null` (calibrate_drag_factor recommendations)** — Move #6.22's `calibrate_drag_factor` recommendations have `recommendation_target_rung = null` (they target a cohort×influencer×platform cell, not a ladder-rung); treating `null` as a distinct categorical value in the 7-feature tuple is CORRECT, but the pattern-decision-classifier should only fire `outcome_pattern_systematic_failure` for `calibrate_drag_factor` patterns IF the operator's `cohort+influencer+platform` cells share a `cluster_id` (i.e. the calibration is failing in a SPECIFIC cluster, not globally). Always check the `cohort+influencer+platform` cell match in addition to the 7-feature tuple.
16. **Not running Move #6.27's production-readiness-test before BFCM-peak** — 200-concurrent-pattern-cluster-detection-batch load-test p95 < 5s is REQUIRED; without load-test Move #6.27 silently fails on BFCM-peak days when operator needs it most. Always run the load-test in staging 7 days before BFCM-peak.
