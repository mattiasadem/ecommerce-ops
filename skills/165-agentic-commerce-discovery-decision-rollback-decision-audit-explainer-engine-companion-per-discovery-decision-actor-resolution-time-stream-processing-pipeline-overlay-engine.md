## Common pitfalls (18 from real builds)

**Cluster A — per-discovery-decision-actor-resolution-time-stream-processing-pipeline-overlay-router + bucket-assignment + decoder-family-router**

1. **Treating stream-processing-pipeline-classifier as a static property of the stream-processing-pipeline-engine rather than a streaming signal that drifts per-rollback-execution.** The Pillar B Step 1 stream-processing-pipeline-overlay-window-bucket-assignment reads UCP/ACP-stream-processing-pipeline-overlay-window-2026 `stream-processing-pipeline-classifier` field as if it were a per-rollback cache key. **Fix:** treat `stream-processing-pipeline-classifier` as a per-rollback × per-stream-processing-pipeline-execution × per-rollback-decision-status streaming signal — emit a `stream-processing-pipeline-classifier-change` event every time UCP/ACP-2026 the stream-processing-pipeline-classifier flips a rollback from `synchronous-stream` to `change-data-capture-stream` to `micro-batch-stream` to `scheduled-batch-stream` to `historical-batch-stream`; the Pillar B Step 1 bucket-assignment MUST subscribe to this event stream and re-bucket historical events whose stream-processing-pipeline shifted within the canonical 24-hour lookback window.

2. **Confusing the canonical `agentic-commerce-stream-processing-pipeline-overlay-completeness-score` (0.0–1.0) with the canonical `stream-processing-pipeline-classifier` (5-state discrete).** A rollback-decision with completeness-score=0.74 is NOT necessarily micro-batch-stream — stream-processing-pipeline boundaries are non-linear and per-rollback-execution per Confluent-Kafka-Stream-Processing-2026 + Materialise-CDC-Stream-Processing-2026 + Move #155 benchmarks. **Fix:** use UCP/ACP-stream-processing-pipeline-overlay-window-2026 `stream-processing-pipeline-classifier` directly as the Pillar B Step 1 bucket-assignment source; the completeness-score is a SECONDARY signal for the Pillar D industry-benchmark-engine only.

3. **Hardcoding the 5-stream-processing-pipeline-overlay-window boundaries to Move #164's 5-resolution-time-rollback-overlay-window SLAs.** The rollback-overlay SLAs (sub-2s / sub-30s / sub-5min / sub-1h / sub-24h) are NOT identical to the stream-processing-pipeline-overlay SLAs because synchronous-stream pipelines expect sub-100ms-p50 stream-processing latency on synchronous-stream windows. **Fix:** define Move #165's 5-stream-processing-pipeline-overlay-window SLAs separately per synchronous-stream = sub-500ms-p99 / change-data-capture-stream = sub-5min-p99 / micro-batch-stream = sub-30min-p99 / scheduled-batch-stream = sub-4h-p99 / historical-batch-stream = sub-7day-p99; document the difference in the operator-UX dashboard's `stream-processing-pipeline-overlay-vs-rollback-overlay-comparison` widget.

**Cluster B — per-discovery-decision-actor-resolution-time-stream-processing-pipeline-overlay-freshness + staleness + backpressure + event-stream-emission**

4. **Window-1 (synchronous-stream) freshness-floor regression from sub-500ms to sub-2s after a Move #164 router refactor.** **Fix:** add a Move-#165-window-1-freshness-floor-canary that pages the on-call SRE the moment Move-#165's synchronous-stream-window freshness-floor exceeds 500ms p99 over a 15-minute window; gate any Move #164 router deploy that pushes synchronous-stream freshness above 500ms p99.

5. **Window-5 (historical-batch-stream) staleness-violation false-negative because historical-batch-stream rollbacks emit at most 1 event per 24h.** **Fix:** the staleness-ceiling for window-5 is 24h, but the freshness-emission floor for window-5 MUST be at least 1 event per rollback-decision per 24h; if no event arrives within 24h, emit a synthetic `historical-batch-stream-staleness-heartbeat` event so the dashboard reflects the rollback-decision's true state.

6. **Backpressure-floor collision between synchronous-stream + change-data-capture-stream pipelines on synchronous-stream rollbacks during peak event-storm.** **Fix:** Pillar B Step 2 backpressure computation reads each stream-processing-pipeline's queue-depth-or-rate-limiter-headroom independently and tags each event with `backpressure-source-stream-processing-pipeline`; the canonical backpressure-floor is per-pipeline (synchronous-stream: queue-depth <50 / change-data-capture-stream: queue-depth <500 / micro-batch-stream: queue-depth <5,000 / scheduled-batch-stream: queue-depth <50,000 / historical-batch-stream: queue-depth <500,000 + rate-limiter-headroom >60%/>50%/>40%/>30%/>20% per window × per pipeline).

7. **Event-stream emission drop on Move-#165 → Move-#164 back-feed when the Move-#164 router is degraded.** **Fix:** the Move-#165 → Move-#164 back-feed event stream is a SEPARATE Kafka topic (`stream-processing-pipeline-overlay-resolution-time-pressure-v1`); if Move-#164's main event-stream topic degrades, Move-#165 still emits to the back-feed topic and Move-#164 still receives per-stream-processing-pipeline-overlay-pressure updates.

8. **Anti-monopoly-floor violation when one stream-processing-pipeline-classifier dominates a synchronous-stream window (e.g. a single `synchronous-stream` stream-processing-pipeline = 60% of synchronous-stream events).** **Fix:** the anti-monopoly-floor per-stream-processing-pipeline-overlay-window × per-discovery-decision-actor-id is per-discovery-decoder-family, NOT per-stream-processing-pipeline-classifier; if a single stream-processing-pipeline-classifier >40% of a per-window × per-decoder-family bucket, split the stream-processing-pipeline's events across multiple `discovery-decision-actor-id` partitions and surface a `stream-processing-pipeline-classifier-monopoly-warning` chip on the operator-UX dashboard.

**Cluster D — per-discovery-decision-actor-resolution-time-stream-processing-pipeline-overlay-cohort + merchant-impact + rollback-decision-audit + decomposition-deep**

12. **Cohort-impact false-positive when a synchronous-stream rollback-decision's events dominate the per-cohort aggregation.** **Fix:** Pillar B Step 3 aggregation-rollup is per-cohort × per-channel × per-stream-processing-pipeline-classifier; if a single synchronous-stream rollback-decision >30% of per-cohort events, surface a `cohort-impact-stream-processing-pipeline-monopoly` chip on the operator-UX dashboard.

13. **Merchant-impact regression when a stream-processing-pipeline-classifier shift (synchronous-stream → change-data-capture-stream) is treated as merchant-impact-positive rather than merchant-impact-negative.** **Fix:** the merchant-impact direction depends on the stream-processing-pipeline direction: synchronous-stream → change-data-capture-stream is merchant-impact-negative (delayed acknowledgment suggests earlier upstream latency); change-data-capture-stream → micro-batch-stream is merchant-impact-negative (further batching increases latency); micro-batch-stream → scheduled-batch-stream is merchant-impact-positive (process completed in scheduled-batch window); scheduled-batch-stream → historical-batch-stream is merchant-impact-positive (process completed in historical-batch window); the operator-UX dashboard's merchant-impact widget MUST classify shifts by direction and surface both directions.

14. **Rollback-decision-audit false-positive when the per-stream-processing-pipeline-overlay-window freshness-floor regression is mis-classified as a rollback-trigger.** **Fix:** the canonical rollback-decision-audit-engine ONLY fires a rollback-decision when (a) freshness-floor regression >2× SLA for >15min AND (b) the merchant-impact direction is negative AND (c) the per-rollback-window decision is `rollback-now`; emit a `rollback-decision-audit-no-op` chip otherwise.

15. **Stream-processing-pipeline-overlay-decomposition-deep (Pillar C sub-decomposition (e)) over-emission when per-failure-mode granularity explodes (12 canonical discovery-failure-modes × 5 stream-processing-pipeline-classifier × 5 windows × 12 rollback-windows × 5-stream-processing-pipelines = 18,000 cells).** **Fix:** Pillar C decomposition decoder-set emits at most 1 cell per (per-stream-processing-pipeline-overlay-window × per-failure-mode × per-stream-processing-pipeline); cells where the event-count <10 within the canonical 7-day window are aggregated to `failure-mode-stream-processing-pipeline-cluster` for the operator-UX dashboard.
