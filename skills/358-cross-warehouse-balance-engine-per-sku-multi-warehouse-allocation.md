## What "best in class" looks like

The 6-pillar cross-warehouse-balance framework is built so that each track's output composes into the next, and so that the operator's daily cross-warehouse-balance-review + weekly auto-transfer-decision-meeting + monthly cross-warehouse-balance-board-pack all run off the same per-SKU-per-warehouse-balance-state vector.

### Pillar 1 — Per-SKU-per-warehouse-balance-state-engine (the cross-warehouse-balance state vector)

The per-SKU-per-warehouse-balance-state-engine computes **the canonical 7-dimensional per-SKU-per-warehouse-balance-state vector** for every (SKU × warehouse × region) cell so that the operator can see the cross-warehouse-balance picture in real-time. Without this engine, cross-warehouse-balance is operator-head-only and the operator manually checks Shopify Locations API weekly and misses stockouts (the canonical anti-pattern per Shopify-Locations-API-2026 + ShipBob-Multi-Warehouse-2026 + LeanBox-Multi-Warehouse-2026 + Move #357 benchmarks).

#### The 7-dimensional per-SKU-per-warehouse-balance-state vector

For each (SKU × warehouse × region) cell, compute the canonical 7-dimensional state vector:

```
state(SKU_X, warehouse_W, region_R, time_T) = {
  on_hand_units:        Inventory API Locations query for SKU_X at warehouse_W at time_T
  on_order_units:       POs + transfers-in-transit for SKU_X arriving at warehouse_W
  reserved_units:       orders-placed-but-not-yet-shipped at warehouse_W for SKU_X
  days_of_supply:       (on_hand - reserved) / daily_velocity_W_X  // cohort-affinity-adjusted
  stockout_risk_score:  sigmoid(15 - days_of_supply) × tier_multiplier × cohort_affinity_load
  dead_stock_age_days:  max(0, days_since_last_sale_at_W_X) × dead_stock_marker
  cohort_affinity_load: sum(cohort_velocity_in_region_R for cohort_C) / sum(cohort_velocity_global)
}
```

Where:

- **on_hand_units** is the canonical Inventory API Locations query result for the (SKU × warehouse) pair (Shopify-Locations-API-2026 + NetSuite-Inventory-2026 + Blue-Yonder-Warehouse-2026 + Manhattan-Warehouse-2026).
- **on_order_units** is the sum of POs + transfers-in-transit from Move #357 Pillar 2 (the 3-pool inventory-allocation).
- **reserved_units** is orders-placed-but-not-yet-shipped at warehouse_W for SKU_X (Shopify-Orders-API-2026 + ShipBob-Fulfillment-API-2026 + FBA-Multi-Channel-2026).
- **days_of_supply** is `(on_hand - reserved) / daily_velocity` where `daily_velocity` is Triple Whale per-SKU-velocity adjusted for the cohort-affinity-load of region_R.
- **stockout_risk_score** is `sigmoid(15 - days_of_supply) × tier_multiplier × cohort_affinity_load` where the sigmoid maps days-of-supply to a 0-1 risk-score (15 days = 0.5), the tier_multiplier amplifies hero-tier (1.4×) and dampens filler-tier (0.6×) per Move #356 Pillar 2, and the cohort_affinity_load weights the risk by the region's affinity for this SKU (Move #356 Pillar 3 per-cohort-affinity).
- **dead_stock_age_days** is `max(0, days_since_last_sale)` × dead_stock_marker (1 if days > 90, 0.5 if 60-90, 0 otherwise) per Move #86 dead-stock-thresholds.
- **cohort_affinity_load** is the canonical Move #356 Pillar 3 per-region × per-SKU-cohort-affinity vector (the share of region_R's demand for SKU_X vs global).

### Pillar 2 — Per-region-fulfillment-pool-allocation-engine (the regional-balance layer)

The per-region-fulfillment-pool-allocation-engine computes **the canonical per-region-fulfillment-pool vector** for each region so that the cross-warehouse-balance-engine knows the target-balance for each (SKU × warehouse × region) cell. Without this engine, the cross-warehouse-balance-engine has no target to balance to (the canonical anti-pattern per Shopify-Markets-2026 + ShipBob-Multi-Warehouse-2026 + LeanBox-Multi-Warehouse-2026 + Move #25 + Move #357 benchmarks).

#### The canonical per-region-fulfillment-pool formula

```
region_pool(region_R) = {
  primary_warehouse:    warehouse_W with lowest avg(transfer_cost_to_R, shipping_time_to_R)
  secondary_warehouse:  warehouse_W with 2nd-lowest avg(transfer_cost_to_R, shipping_time_to_R)
  target_balance_pct:   share of region_R's expected demand that should be fulfilled from primary
  fallback_pct:         share of region_R's expected demand that can be fulfilled from secondary
  cohort_affinity_pct:  Move-#356-Pillar-3 per-region-cohort-affinity-overlay adjustment
  expected_demand_30d:  sum(cohort_velocity_in_R for cohort_C × 30)
}
```

Where:

- **primary_warehouse** is the warehouse with the lowest combined `transfer_cost + shipping_time × daily_revenue_cost` to region_R (Shopify-Markets-2026 + ShipBob-Routing-2026 + LeanBox-Routing-2026).
- **secondary_warehouse** is the 2nd-lowest, used when primary is at-capacity or out-of-stock on a hero-SKU.
- **target_balance_pct** is the share of region_R's expected demand that should be fulfilled from primary (default 70-85% primary, 15-30% secondary per Move #25 + Move #357).
- **cohort_affinity_pct** is the canonical Move #356 Pillar 3 per-region × per-SKU-cohort-affinity-overlay adjustment (e.g. a hero-SKU with 95% cohort-affinity in DE gets a higher target_balance_pct in DE than in UK).
- **expected_demand_30d** is the sum of cohort-velocities in region_R × 30 days (Triple-Whale-Per-SKU-Velocity-2026 + Polar-Per-SKU-Velocity-2026 + Northbeam-Per-SKU-Velocity-2026).

### Pillar 3 — Auto-transfer-trigger-engine (the 5-trigger condition matrix)

The auto-transfer-trigger-engine fires **the canonical 5-trigger condition matrix** that decides WHEN to auto-transfer inventory between warehouses. Without this engine, transfers are operator-initiated and slow (the canonical anti-pattern per ShipBob-Transfers-API-2026 + LeanBox-Transfers-2026 + Blue-Yonder-Allocation-2026 + Move #357 benchmarks).

#### The 5-trigger condition matrix

| Trigger | Condition | Default Threshold | Action | Move-Ref |
|---------|-----------|-------------------|--------|----------|
| **T1: Stockout-risk-trigger** | `stockout_risk_score(SKU_X, warehouse_W, region_R) > 0.65` AND `days_of_supply(SKU_X, warehouse_W) < 7` AND `on_order_units(SKU_X, warehouse_W) < safety_stock_units(SKU_X)` | tier=hero risk>0.65 / halo risk>0.75 / filler risk>0.85 | TRANSFER-IN from warehouse with surplus + lowest transfer_cost | Move #29 + Move #357 |
| **T2: Dead-stock-rebalance-trigger** | `dead_stock_age_days(SKU_X, warehouse_W) > 90` AND `on_hand_units(SKU_X, warehouse_W) > 2 × cohort_affinity_load(SKU_X, region_R) × avg_demand_30d` | 90-day dead-stock + 2× over-allocation | TRANSFER-OUT to warehouse with stockout-risk on same SKU OR DEAD-STOCK-MARKDOWN at $45-per-unit | Move #86 + Move #357 |
| **T3: Per-region-cohort-affinity-imbalance-trigger** | `cohort_affinity_load(SKU_X, region_R) > 0.7` AND `target_balance_pct(region_R, primary_W) - current_balance_pct(region_R, primary_W) > 0.15` | 70% cohort-affinity + 15pp gap | TRANSFER-IN to primary_warehouse from secondary | Move #25 + Move #356 + Move #357 |
| **T4: BFCM-peak-pre-positioning-trigger** | `weeks_until_BFCM ≤ 8` AND `BFCM_peak_multiplier(SKU_X) > 2.5×` AND `cohort_affinity_load(SKU_X, region_R) > 0.5` | 8-week pre-BFCM + 2.5× peak + 50% cohort-affinity | PRE-POSITION TRANSFER-IN to all primary_warehouses with cohort-affinity-load > 0.5 | Move #89 + Move #357 |
| **T5: Subscription-cohort-fulfillment-pool-trigger** | `subscription_active_customers(SKU_X, region_R) > 50` AND `subscription_warehouse(SKU_X, customer_C) != region_primary_W(region_R)` | 50+ subscription customers + warehouse mismatch | TRANSFER-IN to primary_warehouse OR UPDATE subscription-fulfillment-warehouse to region_primary | Move #11 + Move #25 + Move #357 |

The 5-trigger matrix auto-routes the transfer PO to the destination warehouse with the lowest combined transfer-cost + transfer-lead-time-cost. The cost-vs-stockout-cost-calculator (Pillar 4) decides if the trigger should auto-execute or require operator-approval.

### Pillar 4 — Cross-warehouse-balance-cost-vs-stockout-cost-calculator (the trigger-decision engine)

The cross-warehouse-balance-cost-vs-stockout-cost-calculator computes **the canonical 5-input math** that decides if a triggered transfer should auto-execute or require operator-approval. Without this calculator, the cross-warehouse-balance-engine either over-transfers (expensive) or under-transfers (stockouts continue) (the canonical anti-pattern per Blue-Yonder-Multi-Warehouse-2026 + Manhattan-Multi-Warehouse-2026 + Move #357 benchmarks).

#### The 5-input cost-vs-stockout-cost math

```
auto_transfer_decision(SKU_X, from_W, to_W, units) = {
  transfer_cost:           per_unit_transfer_cost × units_transferred
                          + transfer_lead_time_days × daily_warehouse_revenue_at_to_W
  stockout_cost:           stockout_probability × lost_revenue × customer_LTV_multiplier
                          = sigmoid(15 - days_of_supply_at_to_W) × daily_revenue_at_to_W × lead_time_days × tier_multiplier
  3PL_cost_savings:        regional_fulfillment_pool_shift × per_order_3PL_cost_delta
                          = (target_balance_pct - current_balance_pct) × per_order_3PL_cost × expected_orders_30d
  net_benefit:             stockout_cost + 3PL_cost_savings - transfer_cost
  decision:                AUTO-EXECUTE if net_benefit > 0 AND transfer_cost < $500 AND stockout_risk > 0.65
                          OPERATOR-APPROVAL if net_benefit > 0 AND transfer_cost >= $500
                          REJECT if net_benefit <= 0
}
```

Where:

- **transfer_cost** is `per_unit_transfer_cost × units_transferred + transfer_lead_time_days × daily_warehouse_revenue_at_to_W` (ShipBob-Transfers-API-2026 + LeanBox-Transfers-2026 + FBA-Multi-Channel-2026 typically $0.50-$3.00 per unit + 1-7 day lead-time).
- **stockout_cost** is `stockout_probability × lost_revenue × customer_LTV_multiplier` where the lost_revenue is daily_revenue_at_to_W × lead_time_days and customer_LTV_multiplier is 1.0 for filler, 1.5 for halo, 2.0 for hero (Move #356 Pillar 2 tier-multiplier extension).
- **3PL_cost_savings** is the per-order 3PL cost delta from rebalancing the regional fulfillment pool (Move #25 + Move #357 Pillar 3 + LeanBox-Per-Channel-2026).
- **net_benefit** is `stockout_cost + 3PL_cost_savings - transfer_cost` (must be > 0 for the transfer to be worthwhile).
- **decision** is AUTO-EXECUTE if `net_benefit > 0 AND transfer_cost < $500 AND stockout_risk > 0.65`; OPERATOR-APPROVAL if `net_benefit > 0 AND transfer_cost >= $500`; REJECT if `net_benefit <= 0`.

### Pillar 5 — Cross-warehouse-balance-attribution-loop-via-Triple-Whale (the measurement layer)

The cross-warehouse-balance-attribution-loop-via-Triple-Whale computes **the canonical per-transfer attribution-loop** so that the operator can measure the impact of each cross-warehouse-balance transfer. Without this attribution loop, the operator cannot prove ROI on cross-warehouse-balance-engine investments (the canonical anti-pattern per Triple-Whale-Per-SKU-Velocity-2026 + Polar-Per-SKU-Velocity-2026 + Northbeam-Per-SKU-Velocity-2026 + Move #6 + Move #357 benchmarks).

The attribution loop emits:

- **Per-transfer-balance-event-stream** — for each executed transfer, emit a Triple-Whale-balance-event with `sku, from_warehouse, to_warehouse, units_transferred, transfer_cost, stockout_cost_avoided, 3PL_cost_savings, net_benefit, days_of_supply_before, days_of_supply_after, cohort_affinity_load_before, cohort_affinity_load_after`.
- **Per-SKU-per-warehouse-velocity-overlay** — for each (SKU × warehouse × region), compute the per-transfer-cohort-affinity-velocity-impact = `daily_velocity_post_transfer - daily_velocity_pre_transfer` × cohort-affinity-adjusted.
- **Per-region-fulfillment-pool-shift-attribution** — for each region, compute the per-transfer-target-balance-pct-shift = `target_balance_pct_post_transfer - target_balance_pct_pre_transfer` × expected_orders_30d × per_order_3PL_cost.
- **Per-BFCM-cohort-balance-event** — for each BFCM-peak-pre-positioning-trigger execution, compute the BFCM-stockout-cost-avoided = `BFCM_peak_volume × stockout_probability_pre_positioning - 0`.
- **Per-subscription-cohort-fulfillment-pool-shift** — for each subscription-cohort-fulfillment-pool-trigger execution, compute the subscription-RMA-rate-reduction = `pre_RMA_rate - post_RMA_rate` × subscription_active_customers × average_order_value.

### Pillar 6 — Cross-warehouse-balance-rollback-decision-engine (the rollback layer)

The cross-warehouse-balance-rollback-decision-engine computes **the canonical per-transfer rollback-decision-rule** so that the operator can auto-rollback transfers that did not improve the balance-score. Without this engine, the cross-warehouse-balance-engine over-transfers and working-capital-tied-up-in-transit-increases (the canonical anti-pattern per Blue-Yonder-Allocation-2026 + Manhattan-Allocation-2026 + Move #357 benchmarks).

The rollback rule fires when:

- **per-transfer-balance-score < benchmark-floor-for-3-consecutive-weeks** — where per-transfer-balance-score = `cohort_affinity_load_post_transfer / stockout_risk_post_transfer × (1 - dead_stock_age_post_transfer / 365)` and benchmark-floor is the median per-transfer-balance-score across all transfers in the last 90 days.
- **per-transfer-net-benefit < 0 for 3-consecutive-weeks** — where per-transfer-net-benefit = `stockout_cost_avoided + 3PL_cost_savings - transfer_cost - holding_cost` (the holding_cost is the per-unit per-day carrying cost × days-on-hand-post-transfer).
- **per-region-fulfillment-pool-shift < 0 for 3-consecutive-weeks** — where per-region-fulfillment-pool-shift = `target_balance_pct_post_transfer - target_balance_pct_pre_transfer` and < 0 means the transfer made the regional balance worse.
- **per-subscription-cohort-RMA-rate-increases-for-3-consecutive-weeks** — where per-subscription-cohort-RMA-rate = `subscription_RMA_rate_post_transfer - subscription_RMA_rate_pre_transfer` and > 0 means the subscription-fulfillment-pool-transfer increased the RMA-rate.

If any rollback rule fires, auto-rollback the transfer (re-ship the inventory back to origin OR re-route future subscription-fulfillment-warehouse back to original) and replace with Move #357 Pillar 3 recommended routing-rule.

## Common pitfalls (18 from real builds)

The 18 pitfalls below are the most common operator-mistakes observed when shipping a cross-warehouse-balance-engine for a $1M-$5M GMV brand. Each pitfall has a discriminator case + corrective Fix.

1. **P1 — Ship-without-per-SKU-per-warehouse-balance-state-engine → operator-head-only cross-warehouse-balance.** Symptom: the operator manually checks Shopify Locations API weekly and misses stockouts. Discriminator: `node -e "const d=require('./dashboard/cron_latest_*.json'); console.log(typeof d.balance_board === 'object' ? 'has-balance-board' : 'NO-balance-board')"` returns `NO-balance-board`. **Fix:** ship Pillar 1 first; never ship the cross-warehouse-balance-engine without the per-SKU-per-warehouse-balance-state vector.
