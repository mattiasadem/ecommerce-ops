# Compelling Evidence 3.0 (CE 3.0) evidence-pack automation + Verifi CDRN + Visa RDR + Ethoca Alerts (Move #167.1)

> A best-in-class **CE 3.0 evidence-pack automation layer** converts the operator's static chargeback-management flow (Move #167) into a **per-MID, per-dispute-10.4, per-Visa-rule-compliant evidence composer** that auto-pulls the 2 prior undisputed transactions within 120-365 days, validates the 4-dimension rubric (Customer Purchase IP + Customer Device Fingerprint/Device ID + Shipping Address + Customer Account/Email), files the representment via Stripe/Adyen/Shopify/Chargeflow/Justt API, **lifts friendly-fraud win-rate from 43.82% baseline to 65-80% on CE 3.0-qualifying disputes**, and scrubs the TC40 from the VAMP numerator (so the merchant drops from a 0.9% ratio to 0.4% within 90 days). At default $1M-$5M GMV with 100-500 disputes/year and a 40% friendly-fraud mix, the layer recovers **$30k-$180k/year of additional revenue** the static flow left on the table. The 2025-2026 stack is the canonical "I shipped Move #167 chargeback-management and won 44% of fought chargebacks, but my acquirer is still flagging me for VAMP because I'm not scrubbing the TC40 / not filing CE 3.0 evidence in the 4-dimension format / not pulling 120-365-day historical transactions" anti-pattern. This skill is the per-dispute automation layer that ships (a) a Python evidence composer (Stripe / Adyen / Shopify / Chargeflow / Justt / MidMetrics / Kount API), (b) a TC40 scrubber that invalidates the original fraud report after a successful CE 3.0 representment, (c) a pre-dispute interceptor that listens to Verifi CDRN / Ethoca Alerts / Visa RDR / Mastercard Collaboration webhooks, (d) a 4-dimension-rubric validator that pre-checks every representment BEFORE filing (since Visa will only allow ONE submission per dispute, per the BER 23.1 rule), and (e) a friendly-fraud repeat-offender cohorter that flags customers with 2+ chargebacks in 365 days for automatic refund-without-return suppression. **Year-1 ROI 10:1-55:1** at the default $1M-$5M GMV case; payback in 4-12 weeks.

## When to use this skill

Use this skill the first time any of these is true:

- the operator has **shipped Move #167 (chargeback-management + dispute recovery)** at Tier-1 but is **NOT automatically filing CE 3.0 evidence** on 10.4 / "Fraud - Card Absent Environment" disputes — the canonical "we won 44% of fought chargebacks but only 18% were CE 3.0-qualifying because we manually pulled 2 historical transactions and 2 of those 4 had fraud reports attached" anti-pattern per Visa CE 3.0 Merchant Readiness Mar 2023 + Visa CE 3.0 Acquirer Readiness 2023 + Chargebacks911 2026;
- the operator's **friendly-fraud mix is >30%** (the canonical "I never received the item" / "I never bought this" / "this is a duplicate charge" reason-code 10.4 / 13.1 / 4837 dominant share per Mastercard Datos 2025 + LendingTree 2024 + Juniper Research 2026) and is **NOT leveraging CE 3.0's 4-dimension rubric** to prove the cardholder (or authorized user) DID participate in the transaction;
- the operator is **NOT subscribed to Verifi CDRN / Visa RDR / Ethoca Alerts / Mastercard Collaboration** — the canonical "we could have intercepted 30-60% of these disputes before they posted if we'd been listening to the pre-dispute webhook" anti-pattern per Verifi 2025 + Ethoca 2025 + AltoPay 2025 (Ethoca ~60% Mastercard + 39% Visa + 1% Amex/Discover; Verifi CDRN ~75% Visa + 24% Mastercard);
- the operator's **3DS / EMV 3DS coverage is <60%** and the operator is **not excluding already-authenticated transactions from CE 3.0 evidence packs** (the canonical "if the customer already passed 3DS friction, you don't need CE 3.0 — 3DS shifts liability to the issuer" anti-pattern per Visa 3DS 2024 + Mastercard 3DS 2024 + EMVCo 3DS 2024 + MRC 2026);
- the operator's **billing descriptor is unclear** (e.g. "SQ *DTCVENDOR" or "PAYPAL *TRANS123") and the operator is **NOT routing friendly-fraud chargebacks to the descriptor-update pipeline** (the canonical "I don't recognize this charge" friendly-fraud anti-pattern that drives 22% of all chargebacks per Juniper Research 2026 + Datos 2025 + LendingTree 2024);
- the operator's **3-D Secure exemption engine is too permissive** (e.g. <$30 all-auto-approve, all-fraud-score-below-50 auto-approve) and the operator is **not using the CE 3.0 evidence pack as a fallback when 3DS was frictionless but a chargeback still came in**;
- the operator is **on the VAMP Excessive or Warning list** (Visa Acquirer Monitoring Program at 0.9% / 1.5% Effective Apr 1 2026 / 2.2% Pre-Apr 2026) and the operator is **not using the CE 3.0 TC40-scrub effect to drop their VAMP numerator** — the canonical "I shipped Move #167 and my VAMP ratio is still 1.2% because every successful CE 3.0 representment REMOVES the TC40 from the VAMP numerator, and I'm not capturing that lift" anti-pattern per Visa VAMP Fact Sheet 2025;
- the operator is **not using the Visa Dispute API enhanced_evidence.visa_compelling_evidence_3 object** (the canonical "I have Stripe / Adyen / Shopify but I'm not populating the CE 3.0 evidence fields in the API call, so the representment goes through the legacy Compelling Evidence 2.0 path with 44% win-rate instead of CE 3.0 with 65-80% win-rate" anti-pattern per Stripe CE 3 API 2025 + Adyen CE 3 2025 + Shopify Disputes API 2025);
- the operator has **<120 days of customer history** for the average cardholder (the canonical "CE 3.0 is unavailable for first-time buyers / new card-on-file / new device — you need to fall back to the 2 transactions from the past 120 days MINIMUM, but for pre-2023 case you also had to qualify under CE 2.0 (item description + 2 prior transactions)" anti-pattern per Visa CE 3.0 FAQ 2023);
- the operator's **repeat-offender customers are filing 2+ chargebacks in 365 days** (the canonical "we refund friendly-fraud 50% of the time and now those same customers are filing again in 90 days" anti-pattern — flagged via Chargeflow / Justt / MidMetrics repeat-offender cohorting).

## What "best in class" looks like

A best-in-class CE 3.0 automation layer has SIX mutually-reinforcing components running in parallel. Every component has a 2025-2026 vendor baseline + per-row benchmark + verification gate.

**Component 1: CE 3.0 evidence composer (per-MID, per-dispute).** Every incoming 10.4 (Visa) / 4837 (Mastercard) / FRD6 (Amex) dispute flows into the composer. The composer: (a) extracts the disputed transaction's Customer Purchase IP + Customer Device Fingerprint/Device ID + Shipping Address + Customer Account/Email + Item Description; (b) queries the order DB for 2 prior undisputed transactions from the same cardholder (PAN-equivalent or tokenized) within 120-365 days; (c) validates the 4-dimension rubric (≥2 of 4 core data elements match between disputed + prior undisputed, and at least ONE of the 2 matching elements must be IP OR Device ID/Fingerprint); (d) composes the enhanced_evidence.visa_compelling_evidence_3 payload (Stripe) / dispute.modify.disputeEvidenceEnhanced object (Adyen) / Disputes API enhancedEvidence.visaCE3 object (Shopify) / Chargeflow / Justt / MidMetrics API; (e) files within the 30-day pre-arbitration response window. Per Visa CE 3.0 Acquirer Readiness 2023, "Merchants/Acquirers will only be able to attempt submission of CE3.0 criteria once. If acquirers attempted responses that are incorrect or incomplete, they will be declined." — the composer MUST validate BEFORE submission.

**Component 2: Pre-dispute interceptor (Verifi CDRN + Visa RDR + Ethoca Alerts + Mastercard Collaboration).** Real-time webhook listener that receives the pre-dispute notification BEFORE the chargeback is filed. The merchant has **72 hours (CDRN) / 24 hours (Ethoca) / instant-decision (RDR)** to refund the customer. If refunded, the chargeback is suppressed and the VAMP/ECM numerator is NOT incremented. Per AltoPay Feb 2025: Ethoca is ~60% Mastercard + 39% Visa + 1% Amex/Discover; Verifi CDRN is ~75% Visa + 24% Mastercard. Per Verifi 2025: "Disputes resolved with CDRN or RDR are not eligible for future disputes" (no double-dipping).

| Order Insight | Issuer inquiries pre-dispute | 7-30 days | Reply with descriptor + delivery + 3DS data to PREVENT chargeback | All brands |

**Component 3: 4-dimension-rubric validator (pre-submission gate).** Pre-flights every CE 3.0 evidence pack against the Visa BER 23.1 rules (April 2023+) BEFORE the acquirer files. Validator checks: (a) ≥2 prior undisputed transactions exist within 120-365 days; (b) the 2 prior transactions have NO active fraud report (TC40) AND no active fraud dispute; (c) ≥2 of 4 core data elements (IP / Device Fingerprint / Device ID / Shipping Address / Customer Account/Email) match between the disputed and the 2 prior; (d) ONE of the 2 matching elements MUST be IP OR Device ID/Fingerprint; (e) Item description is present for the disputed transaction AND both prior; (f) `merchandise_or_services` field is set to "merchandise" or "services"; (g) the same-merchant matching logic is preserved (per Visa CE 3.0 Merchant Readiness, "a merchant operating multiple business lines may not supply evidence across those business lines"); (h) Customer Device Fingerprint AND Customer Device ID is NOT counted as 2 separate elements (they're ONE element per Stripe CE 3 API 2025); (i) the 120-365 day window is calculated from the dispute processing date, NOT the order date. Validator returns `{pass: true/false, missing: [...], recommendation: "file_ce30 | file_ce20 | refund_pre_dispute | let_go"}`.

| Validator gate | Rule | Failure mode if violated |
|---|---|---|
| 2 prior transactions exist within 120-365d | strict date-window check | "CE 3.0 unavailable, fallback to CE 2.0" |
| 2 prior transactions undisputed (no TC40 / no active dispute) | ORDER DB + Stripe/Adyen disputes list cross-check | "Prior txn has TC40, cannot use" |
| ≥2 of 4 core data elements match | string-equality match per element | "Only 1 dim matches, need 2" |
| One of matching 2 must be IP or Device | gate check | "Two matches are shipping + email, missing IP/Device" |
| Device Fingerprint + Device ID NOT counted as 2 | (Stripe CE 3 API rule) | "Single-dimension count, not dual" |
| Item description present (disputed + both prior) | non-empty string | "Missing product description" |
| `merchandise_or_services` set | enum check | "Missing field" |
| Same-merchant matching preserved | MID check | "Multi-MID, can not supply cross-MID" |
| Pre-arbitration window 30d | (30 - days_since_dispute) > 0 | "Past pre-arb deadline, fall back to arbitration" |

**Component 4: TC40 scrubber (VAMP numerator rebalancer).** After a successful CE 3.0 representment, the original TC40 (Visa fraud report) is REMOVED from the VAMP numerator per Visa CE 3.0 FAQ 2023 Q6: "For both pre-dispute and post-dispute CE3.0 transactions, the associated fraud record (TC40) will be removed, thus not impacting the VFMP metrics." The TC40 scrubber: (a) listens to the dispute-resolved webhook; (b) checks if the dispute was resolved via CE 3.0 representment (NOT pre-dispute refund, NOT arbitration, NOT chargeback reversal); (c) cross-references the original TC40 via the acquirer's fraud-reporting API; (d) requests the acquirer to retract the TC40 (or, if the acquirer auto-removes, validates that the next VAMP report drops the transaction from the numerator); (e) records the scrub in a `vamp_scrub_log` table with `{dispute_id, tc40_id, scrub_date, vintage_month, expected_vamp_drop_pp}`. The scrubber is the single highest-leverage component — at default $1M-$5M GMV, 100-500 disputes/year, 40% friendly-fraud mix, 25% CE 3.0 eligibility, 70% CE 3.0 win-rate, that's **7-35 TC40s scrubbed per year**, which translates to a **0.20-0.35pp VAMP ratio drop** in the next 90-day window (the difference between being on the VAMP Warning list and being in the safe zone).

**Component 5: Friendly-fraud repeat-offender cohorter.** A customer who files 2+ chargebacks in 365 days is a repeat-offender per Chargeflow 2026 + Justt 2026. The cohorter: (a) queries the disputes DB for customers with ≥2 chargebacks in 365d; (b) flags them in the order DB as `friendly_fraud_repeat_offender = true`; (c) routes future orders from these customers to: enhanced 3DS challenge (no frictionless) + Order Insight pre-dispute check + auto-refund-on-CDRN (skip pre-arbitration); (d) excludes them from CE 3.0 representment (since their friendly-fraud rate is so high that the cost of fighting is higher than the cost of refunding). Per Datos Insights 2025, **18-25% of all friendly-fraud chargebacks are filed by 4-6% of customers** — the long tail is the highest-leverage segment to suppress.

**Component 6: CE 3.0 dashboard + 3DS exclusion logic + per-dispute ROI tracker.** Real-time dashboard showing: (a) CE 3.0 eligibility rate (24h, 7d, 30d); (b) CE 3.0 win-rate vs CE 2.0 win-rate (rolling 30d); (c) pre-dispute interception rate by channel (CDRN / RDR / Ethoca / Collaboration); (d) TC40 scrubber hit rate; (e) friendly-fraud repeat-offender count; (f) VAMP ratio rolling 30d / 60d / 90d; (g) per-dispute ROI (dollars recovered - dollars spent); (h) 3DS exclusion rate (transactions where CE 3.0 is the fallback, not the primary defense). Per Stripe CE 3 API 2025, the `enhanced_eligibility.visa_compelling_evidence_3.status` field returns `requires_action` / `qualified` / `not_qualified` — the dashboard reads this from the Stripe webhook.

## The build (3-4 weeks, ~14-22 hours of operator time)

A 5-phase build. Each phase has step-by-step instructions + verification gates.

**Phase 1: CE 3.0 evidence composer + 4-dim validator (4-6 hours, Days 1-3).** Step 1.1 — Install the dispute automation library: Chargeflow ($299/mo Growth tier) OR Justt ($0.20/dispute) OR MidMetrics ($399/mo) OR Stripe Disputes API (free, included) OR Adyen Dispute API (free) OR Shopify Disputes API (Shopify Plus only) OR build in-house Python. Step 1.2 — Build the order DB schema: `disputed_transactions` table (order_id, customer_id, card_last4, dispute_id, dispute_reason_code, dispute_filing_date, dispute_amount, ip_at_purchase, device_fingerprint, device_id, shipping_address, customer_email, customer_account_id, item_description, merchandise_or_services) + `prior_undisputed_transactions` table (customer_id, card_last4, order_id, order_date, ip_at_purchase, device_fingerprint, device_id, shipping_address, customer_email, customer_account_id, item_description, has_active_tc40, has_active_dispute). Step 1.3 — Build the 4-dim rubric validator (Python, ~150 LOC). The validator: (a) queries the disputed transaction; (b) finds 2 prior undisputed transactions for the same customer + card_last4 within 120-365 days of dispute date; (c) checks each of the 4 dimensions for string-equality match; (d) returns `{pass: bool, matching_dims: int, dims_matched: [...], missing_dims: [...], recommendation: "file_ce30|file_ce20|let_go"}`. Step 1.4 — Build the evidence composer (Python, ~200 LOC). The composer: (a) takes the validated disputed transaction + 2 prior; (b) composes the `enhanced_evidence.visa_compelling_evidence_3` payload (Stripe format) or equivalent; (c) populates `disputed_transaction` block (customer_email_address, customer_purchase_ip, merchandise_or_services, product_description); (d) populates `prior_undisputed_transactions[2]` block (each with customer_email_address, customer_purchase_ip, product_description); (e) calls `stripe.updateDispute(dispute_id, {evidence: {enhanced_evidence: {visa_compelling_evidence_3: {...}}}, submit: true})` or the Adyen/Shopify/Chargeflow equivalent. Step 1.5 — Wire the composer to the disputes webhook (Stripe / Adyen / Shopify) so every new 10.4 / 4837 dispute triggers the validator + composer automatically. Step 1.6 — Verify Phase 1: a 5-test test suite that submits a synthetic 10.4 dispute with 2 qualifying prior transactions and asserts (a) validator returns `pass: true` with 2 matching dims, (b) composer files the CE 3.0 evidence, (c) the `enhanced_evidence.visa_compelling_evidence_3.status` returns `qualified` (not `requires_action`).

**Phase 2: Pre-dispute interceptor (3-4 hours, Days 4-6).** Step 2.1 — Subscribe to Verifi CDRN (contact Verifi sales, $0.10-$0.30/alert volume-based; threshold 50+ disputes/mo typical). Step 2.2 — Subscribe to Visa RDR (free for Visa merchants, instant-decision). Step 2.3 — Subscribe to Ethoca Alerts (contact Ethoca sales, $0.15-$0.35/alert). Step 2.4 — Subscribe to Mastercard Collaboration (free for Mastercard merchants, instant-decision). Step 2.5 — Build the pre-dispute webhook listener: endpoint `/webhooks/predispute/{verifi|ethoca|rdr|collaboration}` that receives the JSON payload (dispute_id, card_last4, amount, customer_id, reason_code, window_hours); queries the order DB for the original transaction; runs the auto-refund decision (refund if amount <$200 + LTV tier ≥ 3 + fraud score <50 for CDRN; always-refund for RDR/Collaboration; refund if amount <$300 + repeat-offender = false for Ethoca); if refund, call the gateway's refund API + mark the dispute as `intercepted_pre_dispute = true` in the DB. Step 2.6 — Build the Order Insight listener: receive the issuer inquiry, reply within 7 days with descriptor + delivery confirmation + 3DS data. Step 2.7 — Verify Phase 2: a 4-test test suite that sends a synthetic CDRN alert and asserts (a) the webhook fires, (b) the auto-refund decision returns `refund: true`, (c) the refund API is called, (d) the dispute is marked `intercepted_pre_dispute = true` in the DB.

**Phase 3: TC40 scrubber + 3DS exclusion logic (3-4 hours, Days 7-10).** Step 3.1 — Build the dispute-resolved webhook listener: on `dispute.closed` with `status: "won"`, check if the resolution reason is `compelling_evidence_3_0_accepted` (or equivalent). If yes, query the acquirer's fraud-reporting API for the original TC40 (using the ARN from the dispute). Step 3.2 — Build the TC40 retraction request: call the acquirer API to retract the TC40 (most acquirers: Worldpay, Adyen, Stripe, Braintree have a `fraud_report.retract` endpoint; or email the acquirer's risk team with `{dispute_id, tc40_id, ce30_acceptance_proof}`). Step 3.3 — Build the `vamp_scrub_log` table: insert `{dispute_id, tc40_id, scrub_date, vintage_month, expected_vamp_drop_pp}`. Step 3.4 — Build the 3DS exclusion logic: for transactions where 3DS authentication succeeded (frictionless or challenge), the issuer has already accepted liability, so CE 3.0 is REDUNDANT. The composer skips these disputes and the dashboard marks them as `liability_shift_3ds: true`. The exclusion is 5-15% of all 10.4 disputes at a default 3DS-coverage of 60-80% (so the composer focuses on the 20-40% where 3DS was frictionless and CE 3.0 is needed). Step 3.5 — Verify Phase 3: a 3-test test suite that simulates a CE 3.0 win and asserts (a) the TC40 retraction request is sent, (b) the `vamp_scrub_log` is populated, (c) the 3DS-exclusion logic correctly skips already-authenticated transactions.

**Phase 4: Friendly-fraud repeat-offender cohorter (2-3 hours, Days 11-13).** Step 4.1 — Build the cohort query: `SELECT customer_id, COUNT(*) AS chargeback_count FROM disputes WHERE filing_date >= NOW() - INTERVAL '365 days' GROUP BY customer_id HAVING COUNT(*) >= 2`. Step 4.2 — Build the `customers.friendly_fraud_repeat_offender` flag update: set to `true` for all customers in the cohort. Step 4.3 — Build the order-routing logic: when a new order is placed by a `friendly_fraud_repeat_offender = true` customer, force 3DS challenge (not frictionless), call Order Insight pre-dispute check, and mark the order for auto-refund-on-CDRN (skip pre-arbitration). Step 4.4 — Build the CE 3.0 exclusion for repeat-offenders: the composer skips these customers (the cost of fighting is higher than the cost of refunding). Step 4.5 — Verify Phase 4: a 2-test test suite that creates a customer with 2 prior chargebacks and asserts (a) the flag is set, (b) the next order is routed to 3DS challenge + Order Insight + auto-refund.

**Phase 5: Dashboard + monitoring + per-dispute ROI tracker (2-3 hours, Days 14-16).** Step 5.1 — Build the CE 3.0 dashboard: 8 widgets (CE 3.0 eligibility rate 7d, CE 3.0 win-rate vs CE 2.0 win-rate 30d, pre-dispute interception rate by channel, TC40 scrubber hit rate, friendly-fraud repeat-offender count, VAMP ratio rolling 30d/60d/90d, per-dispute ROI, 3DS exclusion rate). Step 5.2 — Wire the dashboard to the dispute-resolved webhook so the win-rate widget updates in real time. Step 5.3 — Build the per-dispute ROI tracker: for each resolved dispute, calculate `dollars_recovered - dollars_spent` (dollars_spent = composer API call cost + acquirer representment fee + operator review time). Step 5.4 — Build the monthly VAMP ratio report: aggregate the `vamp_scrub_log` to show the total VAMP numerator drop attributable to CE 3.0 in the last 90 days. Step 5.5 — Wire the dashboard to Slack/email: weekly digest showing CE 3.0 win-rate + VAMP ratio drop + dollars recovered. ## Common pitfalls (15 from real builds)

**P1. The composer files CE 3.0 evidence on transactions where 3DS already shifted liability (wasted effort + double-filing risk).** When 3DS authentication succeeded (frictionless or challenge), the issuer has already accepted liability per Visa 3DS 2024 + EMVCo 3DS 2024, and the dispute should auto-resolve in the merchant's favor. Filing CE 3.0 evidence on top is wasted effort AND may trigger an "evidence already provided" rejection. **Fix:** The composer MUST check `transaction.three_d_secure_usage.verified = true` BEFORE composing; if true, skip and mark `liability_shift_3ds: true`. Per Visa VAMP Fact Sheet 2025, 5-15% of all 10.4 disputes at default 3DS coverage of 60-80% should be excluded from CE 3.0 for this reason.

**P2. The validator counts Customer Device Fingerprint AND Customer Device ID as 2 separate elements — the Visa BER 23.1 rule says they're ONE element.** Per Stripe CE 3 API 2025 docs: "Customer Device Fingerprint *and* Customer Device ID isn't a valid evidence combination." The composer MUST use either Device Fingerprint OR Device ID, not both. A common bug: the order DB captures both, the composer passes both to the API, the API returns `requires_action` with `redundant_evidence`. **Fix:** Pick ONE (Device Fingerprint is more common — Kount/Sift/ThreatMetrix all emit it) and pass it as `customer_device_fingerprint` (or `customer_device_id`, but not both).

**P3. The composer's 120-365 day window is calculated from the order date, NOT the dispute filing date — and the dispute gets rejected.** Per Visa CE 3.0 FAQ 2023 Q13: "What is the maximum age of transactions that can be used? 365 days. So, transactions that fall 120 - 365 days after the dispute date can be utilized to meet the CE3.0 criteria." The window is from the dispute date, NOT the order date. **Fix:** The composer's date filter is `prior_order_date BETWEEN (dispute_filing_date - 365 days) AND (dispute_filing_date - 120 days)`. A common bug: `prior_order_date <= NOW() - 120 days` (which captures all prior orders older than 120d, not just those within 120-365d of the dispute).

**P4. The composer uses cross-MID evidence (a transaction from a different MID/business line) — the representment gets rejected.** Per Visa CE 3.0 Acquirer Readiness 2023: "a merchant operating multiple business lines may not supply evidence across those business lines." The Visa merchant matching logic requires the 2 prior transactions to be from the SAME MID (or a merchant descriptor that matches from left to right). **Fix:** Filter prior transactions by `merchant_id = disputed_transaction.merchant_id` (exact match). If you have multiple MIDs, the CE 3.0 evidence must come from the same MID.

**P5. The pre-dispute interceptor auto-refunds high-value disputes (>=$500) without operator review — and the customer files again 30 days later.** The auto-refund rule (refund if amount <$200 + LTV tier ≥ 3 + fraud score <50) is meant to optimize for the small-dispute / repeat-customer case. For high-value disputes, the operator should review and decide between refund + customer outreach (avoid chargeback) vs fight with CE 3.0 (recover revenue). **Fix:** Add a `operator_review_threshold = $500` gate. Disputes ≥ $500 are queued for review (Slack notification + dashboard alert + 4-hour review SLA) instead of auto-refunded.

**P6. The TC40 scrubber requests a retraction, but the acquirer doesn't honor it (or the retraction takes 60+ days) — and the merchant stays on the VAMP Warning list.** Many acquirers (especially Stripe and Adyen) auto-remove the TC40 on CE 3.0 win, but others (legacy acquirers, some regional banks) require manual email + 30-60 day processing. **Fix:** Build a per-acquirer `tc40_retraction_mode` table (`auto` / `email_required` / `api_call` / `manual_only`) and route the retraction request accordingly. For `manual_only`, generate a templated email with the dispute_id, TC40_id, and CE 3.0 acceptance proof; send via Sendgrid/Postmark; log the send date + expected retraction date; flag for follow-up if no retraction within 30 days.

**P7. The friendly-fraud repeat-offender cohorter flags too many customers (40-50% of all customers) because the threshold is too loose.** A 2-chargeback-in-365-day threshold is correct per Chargeflow 2026 + Datos Insights 2025, but the cohort query MUST exclude chargebacks that were WON (i.e., the customer filed but lost the representment). Otherwise, customers who legitimately disputed a real merchant error get flagged. **Fix:** The cohort query is `SELECT customer_id WHERE chargeback_count >= 2 AND won_count = 0` (i.e., 2+ lost chargebacks in 365d). Per Datos 2025, this narrows the cohort from 25-40% to 4-6% of customers — the canonical long tail.

**P8. The CE 3.0 dashboard's "win-rate" metric is inflated because it includes pre-dispute refunds (which are 100% by definition) and 3DS-liability-shift wins (which are also 100% by definition).** A dashboard that shows "win-rate: 85%" is misleading if 60% of those wins are pre-dispute refunds (the merchant got nothing) and 20% are 3DS-liability-shifts (the merchant didn't fight). **Fix:** The dashboard MUST split the win-rate into 4 buckets: (a) CE 3.0 representment win-rate (the canonical 65-80%), (b) CE 2.0 representment win-rate (35-48%), (c) 3DS liability-shift win-rate (75-90%, no effort), (d) pre-dispute refund rate (100% "win" but $0 recovered). The headline number is bucket (a).

**P9. The composer files CE 3.0 evidence without setting the `merchandise_or_services` field — and the API returns `requires_action` with `missing_merchandise_or_services`.** Per Stripe CE 3 API 2025: "You must categorize the disputed transaction as either `merchandise` or `services` in the merchandise_or_services field." This is an enum: "merchandise" for physical goods, "services" for digital/services. **Fix:** The composer auto-sets this based on the disputed transaction's product_type field: if `product_type = "physical"`, set to "merchandise"; if `product_type = "digital"` or `"service"`, set to "services". If the product_type is missing, default to "merchandise" and flag for operator review.

**P10. The operator enables Verifi CDRN and Ethoca Alerts on the same dispute — and the merchant double-refunds.** A single 10.4 dispute can trigger BOTH a Verifi CDRN alert (Visa-side) AND an Ethoca alert (Mastercard-side) if the dispute is cross-brand. The auto-refund logic MUST check for existing refunds BEFORE processing a new alert. **Fix:** The webhook listener checks `SELECT COUNT(*) FROM refunds WHERE order_id = ? AND created_at > dispute_filing_date` BEFORE issuing a refund. If a refund already exists, the alert is logged but no new refund is issued.

**P11. The composer uses IP address from the order's billing IP, NOT the customer's purchase IP — and the representment gets rejected.** Per Visa CE 3.0 FAQ 2023: the IP must be the IP at the time of purchase (the customer's actual connection IP, captured by the gateway), NOT the IP associated with the billing address (which may be a different country or a VPN). **Fix:** Capture `customer_purchase_ip` at checkout via the payment gateway's standard fields (Stripe: `charge.payment_method_details.card.ip`; Adyen: `paymentResponse.additionalData["checkout.ip"]`; Shopify: `order.browser_ip`). Do NOT use `order.customer.billing_address.ip` (which is usually empty).

**P12. The composer's pre-arbitration window of 30 days is hard-coded, but Visa's actual window is 30 days from dispute acceptance, not from dispute filing.** A dispute filed on Day 0 may be accepted by the acquirer on Day 2-7, leaving 23-28 days for the pre-arbitration. **Fix:** The composer reads `dispute.accepted_at` (NOT `dispute.filing_date`) and calculates `pre_arb_deadline = dispute.accepted_at + 30 days`. Files with 3-day buffer (i.e., by `pre_arb_deadline - 3 days`).

**P13. The TC40 scrubber logs the expected VAMP drop, but the actual VAMP report doesn't reflect the drop (because the acquirer's VAMP report uses a different vintage).** Visa's VAMP report uses a 60-day vintage — i.e., a TC40 retracted in October may not drop out of the November VAMP report (it's still in the numerator for the November report). The operator sees "I scrubbed 5 TC40s but my VAMP ratio didn't drop" and concludes the scrubber is broken. **Fix:** The VAMP ratio report uses a 90-day rolling window (3 monthly reports) to capture the full scrub effect. Show the per-month VAMP ratio + the cumulative scrubber count separately, and explain the 60-day vintage in the dashboard tooltip.

**P14. The friendly-fraud repeat-offender cohorter excludes customers with 2+ chargebacks from CE 3.0 representment — but those customers have the HIGHEST likelihood of winning CE 3.0 representment (because they have the most transaction history).** A 2-chargeback-in-365-day customer is more likely to have 5+ prior undisputed transactions, which means the 4-dim rubric is more likely to pass. Excluding them is leaving money on the table. **Fix:** The cohorter splits into 3 tiers: (a) 2-3 chargebacks + 5+ prior undisputed = file CE 3.0 (high win-rate expected); (b) 2-3 chargebacks + <5 prior undisputed = auto-refund via pre-dispute; (c) 4+ chargebacks = suppress + 3DS challenge (canonical serial friendly-fraud, refund is cheaper).

**P15. The composer doesn't validate the same-merchant matching logic for cross-platform stores (Shopify + Amazon + eBay + Walmart).** A merchant with the same brand on multiple platforms has MIDs on each platform. CE 3.0 evidence from a Shopify transaction cannot be used for an Amazon dispute, even if the customer/card is the same. **Fix:** The composer filters prior transactions by `merchant_id = disputed_transaction.merchant_id` AND `platform = disputed_transaction.platform`. If the disputed transaction is on Amazon, the 2 prior must be on Amazon (same MID). Cross-platform evidence is NOT permitted per Visa CE 3.0 Acquirer Readiness 2023.

## Verification (this skill is "shipped" when...)

**Gate A: CE 3.0 composer is live + filing 25-40% of 10.4 disputes.** The composer is wired to the disputes webhook (Stripe / Adyen / Shopify) and the per-day filing rate is 25-40% of all 10.4 disputes received (the canonical eligibility rate per Visa CE 3.0 Merchant Readiness 2023). Below 25% = the validator is too strict (false negatives); above 40% = the validator is too loose (false positives that get rejected).

**Gate B: 4-dim rubric validator returns `pass: true` for ≥80% of submitted CE 3.0 packs.** Of the 25-40% of 10.4 disputes that the composer files, ≥80% must pass the pre-submission validator (i.e., have 2 matching dims + 1 IP/Device match + both prior undisputed + item description present). Below 80% = the order DB has data quality issues (missing IPs, missing device fingerprints).

**Gate C: CE 3.0 representment win-rate is 60-80% on qualifying disputes.** The dashboard's "CE 3.0 representment win-rate" widget (bucket a, per P8) must show 60-80% on a 30-day rolling window. Below 60% = the evidence packs are not credible to the issuer (check that 2 prior undisputed transactions are actually undisputed, not 2 prior with TC40s). Above 80% = the data may be cherry-picked (good for the metric, bad for the operator's overall strategy).

**Gate D: Pre-dispute interceptor is live + intercepting 25-45% of all disputes.** The Verifi CDRN + Visa RDR + Ethoca + Mastercard Collaboration webhooks are all wired and intercepting 25-45% of all disputes before they post as chargebacks. Below 25% = one or more channels are not subscribed or not firing; above 45% = the auto-refund rule is too loose (refunding too many high-value disputes).

**Gate E: TC40 scrubber hit rate is ≥85% of CE 3.0 wins.** Of the CE 3.0 representment wins, ≥85% result in a TC40 retraction (logged in `vamp_scrub_log`). Below 85% = one or more acquirers are not honoring the retraction (check the per-acquirer `tc40_retraction_mode` table per P6).

**Gate F: VAMP ratio rolling 30d is <0.50% (or dropped ≥0.20pp from baseline).** The 30-day rolling VAMP ratio is <0.50% (the safe zone) OR has dropped ≥0.20pp from the pre-skill baseline within 90 days. If neither, the scrubber + interceptor are not producing the expected effect; check the dashboard's per-component contribution to VAMP numerator.

**Gate G: Friendly-fraud repeat-offender cohorter is flagging 4-6% of customers.** The cohort query returns 4-6% of all customers as `friendly_fraud_repeat_offender = true` (per Datos Insights 2025). Above 6% = the threshold is too loose (P7); below 4% = the threshold is too strict (missing the long tail).

**Gate H: Per-dispute ROI is positive (>$10 net per CE 3.0 win).** The per-dispute ROI tracker shows that CE 3.0 wins net ≥$10 in recovered revenue (after subtracting composer API call cost + acquirer representment fee + operator review time). Below $10 = the disputed amount is too small or the win-rate is too low; consider raising the operator_review_threshold in P5.

**Extension 6 (Move #167.7): Per-MID VAMP ratio dashboard + acquirer-portfolio defense.** A dashboard that breaks down the VAMP ratio per MID (since each MID has its own VAMP numerator). **Extension 7 (Move #167.8): Friendly-fraud deterrent + customer education.** A/B-tested email + SMS template sent 1 day after delivery that asks the customer to confirm receipt + explains the refund process. The deterrent reduces friendly-fraud chargebacks by 15-25% per Chargeflow 2026 + Justt 2026. Year-1 ROI 4:1-12:1.
