# Hypothesis accuracy tracker + auto-tuning — close the Move #6 feedback loop, auto-tune Move #6.12 ranker weights + Move #6.13 recipe blast-radius scores + Move #6.14 per-recipe-affected-platform-set (Move #6.15)

> Move #6.12 (cross-platform root-cause correlation engine, shipped 2026-10-01 16:38 UTC as skill/443) fires a **ranked hypothesis** within 90 seconds of a co-fire — but its **ranker weights are static** (set when Move #6.12 was first deployed). Move #6.13 (attribution auto-remediation runbook executor, shipped 2026-10-01 17:42 UTC as skill/444) auto-executes the 5-min fix recipe for the 5 known patterns — but its **blast-radius scores are static** (per-recipe blast-radius set when Move #6.13 was first deployed). Move #6.14 (per-event revenue-impact attribution, shipped 2026-10-01 18:56 UTC as skill/445) computes the dollar-value of every Move #6.13 execution — but its **per-recipe-affected-platform-set is static** (YAML config, versioned but rarely reviewed). **All three layers are blind to the operator's REAL-WORLD feedback loop** — the operator has no way to say "Move #6.12 ranked H1 first but the actual root cause was H4" or "Move #6.13 R1 fired but the breach-cost recovery was only $400 vs the predicted $3,400" or "Move #6.14's R1 platform-set should include LinkedIn, not just Meta+Google+TikTok+Snap+Pinterest". Move #6.15 closes the loop: it (1) **ingests operator feedback** from Slack (`/wrong hypothesis` + `/wrong recipe` + `/wrong breach-cost` slash-commands) + Notion post-mortem reviews + Linear / Jira / PagerDuty issue close-reasons + the CFO-board-pack weekly-reconciliation corrections, (2) **scores accuracy** of Move #6.12's ranker (NDCG@5 + MRR + Brier-score + ECE) + Move #6.13's recipe-success-rate (precision-recall + Cohen's-kappa vs operator-confirmed-good-execution) + Move #6.14's breach-cost accuracy (predicted-vs-actual within ±5% / ±15% / ±30% bands), (3) **persists accuracy to a Move #6.15 ledger** (ClickHouse + 90d retention + S3 cold archive), (4) **auto-tunes the three layers** — Move #6.12's ranker weights via contextual-bandit Thompson-sampling, Move #6.13's blast-radius scores via gradient-boosted regression on past-90-day feedback, Move #6.14's per-recipe-affected-platform-set via drift-detection + operator-marked-affected-platform feedback, AND (5) **publishes the Move #6.15 accuracy-dashboard** at `/attribution-accuracy-tracker` with NDCG@5 trend, recipe-success-rate trend, breach-cost accuracy bands, weekly auto-tuning diff, and the operator-feedback volume heatmap. For the default $500k–$5M GMV brand, Move #6.15's auto-tuning compounds: a 5% NDCG@5 lift on Move #6.12 + a 10% recipe-success-rate lift on Move #6.13 + a 15% breach-cost-accuracy lift on Move #6.14 across 100+ breaches/year = **~$30,000–$200,000 of additional recovered-revenue that Move #6.10/6.11/6.12/6.13/6.14 ALONE would have left on the table**. Year-1 ROI band **11:1–32:1**. Ship AFTER Move #6.10 + #6.11 + #6.12 + #6.13 + #6.14 all live and producing audit JSON + breach-cost ledger (Move #6.15 consumes ALL three layers' audit logs + operator-feedback + reconciliation-corrected dollar-values as its training data).

## Common pitfalls (15 from real builds)

1. **Auto-tuning Move #6.12 ranker weights WITHOUT enough operator-feedback volume.** A naive Move #6.15 ships the contextual-bandit rank-tuner on Day 1 with only 5–10 operator-marked-correct/incorrect events, and tunes on noise (every feedback event causes a weight-swing). The minimum-feedback threshold for the bandit is **≥30 operator-marked events** before the bandit is allowed to tune; below 30, Move #6.15 emits a "feedback-volume-too-low — manual tuning required" Slack alert and falls back to the static Move #6.12 weights.

2. **Computing NDCG@5 over ALL ranked hypotheses instead of only the operator-confirmed subset.** A naive scorer reads Move #6.12's `ranked_hypotheses` for every co-fire and computes NDCG@5 against the operator-marked-correct hypothesis — but Move #6.12 logs 5 ranked hypotheses per co-fire (the canonical 5-pattern library) AND operator feedback may be on a hypothesis that Move #6.12 didn't rank (e.g. a new pattern not yet in the library). Always filter to the operator-marked-target-id subset before computing NDCG@5.

3. **Drift-detecting Move #6.14 platform-set on a weekly cadence instead of a daily cadence.** A weekly cadence misses short-lived drift events (a 3-day BFCM-weekend platform-mix shift that auto-corrects by the next Monday). Always run PSI + KS + JSD on a **daily cadence at 00:00 local** AND on a **per-event cadence** for any Move #6.14 computation whose predicted-vs-actual deviation > ±30%.

4. **Using raw operator-feedback counts as the auto-tuning reward signal (instead of normalized accuracy-scores).** A naive implementation rewards the bandit with `correct=1 / incorrect=0` per event, but the bandit then over-tunes toward the most-frequent-co-fire pattern (e.g. CDP-write-loss) at the expense of rare-but-important patterns (e.g. ad-pixel-re-deploy). Always use **class-balanced rewards** (inverse-frequency weighting) so rare patterns get equal tuning pressure.

5. **Auto-tuning Move #6.13 blast-radius scores WITHOUT the Move #6.14 breach-cost accuracy feedback loop.** A naive regressor trains on Move #6.13's per-recipe execution success/failure only — but the breach-cost accuracy (predicted-vs-actual-reconciliation) is the STRONGEST signal of whether blast-radius was correctly sized (over-recovery = blast-radius-too-small → too many platforms attributed; under-recovery = blast-radius-too-large → too few platforms attributed). Always include Move #6.14's breach-cost accuracy as a feature in the regressor.

6. **Skipping the statistical-significance-gate and tuning-on-noise.** A naive Move #6.15 emits a new YAML config every Monday regardless of whether the past 7 days of feedback shows a statistically-significant change. The mSPRT-valid α=0.05 gate is REQUIRED — without it, Move #6.15 will tune on random weekly fluctuations and over-fit the ranker weights to the most recent week's noise.

7. **Not version-controlling the auto-tuning YAML configs.** A naive Move #6.15 overwrites the Move #6.12 / #6.13 / #6.14 YAML configs in-place without git-versioning. The rollback-safety-net CANNOT revert without version-control. Always commit each auto-tuning diff as a new YAML version + tag `move_6_15_tuning_<date>`.

8. **Computing Move #6.12 NDCG@5 over the FULL co-fire history (including Move #6.12 false-positives that Move #6.13 auto-rejected).** A co-fire that Move #6.12 ranked but Move #6.13's circuit-breaker blocked (false-positive) should NOT count against Move #6.12's accuracy — Move #6.12 correctly ranked H1 (CDP-write-loss) but the actual cause was a transient network blip that resolved before Move #6.13 fired. Always filter to **Move #6.13-confirmed-true-positive** co-fires before computing Move #6.12's accuracy-score.

9. **Tuning Move #6.14 affected-platform-set on per-recipe median breach-cost instead of per-recipe predicted-vs-actual accuracy.** A naive drift-detected-platform-set-updater trains on median breach-cost-per-platform (assumes the recipe-affected-set should match the platforms with highest breach-cost), but the correct signal is the **per-platform residual** (predicted breach-cost for the platform minus operator-confirmed actual breach-cost for the platform). A platform with HIGH median breach-cost but LOW residual is correctly tuned; a platform with LOW median breach-cost but HIGH residual needs to be ADDED to the affected-set.

10. **No idempotency-key on the operator-feedback-ingest pipeline.** A Slack `/wrong hypothesis` slash-command that fires 3x (Slack retry-on-network-glitch) triggers 3 normalized feedback events for the same operator-action. The accuracy-scorer double-counts the feedback and over-weights the operator's preference. Always include `{layer}-{target_id}-{operator_id}-{timestamp_minute}` as the idempotency-key + store in Redis with 60-min TTL.

11. **Auto-tuning Move #6.12 weights on a single feature (co-fire-id) instead of the full evidence-vector.** A naive bandit tunes each weight on the co-fire-id alone, but the 9 Move #6.12 evidence signals (S1 CDP-dedup-counter + S2 email-bounce-rate + S3-S5 downstream-status + S6 Cloudflare-Radar + S7 BGP-AS-path + S8 ad-platform-401 + S9 ad-pixel-deploy) are the CONTEXTUAL features that should condition the Thompson-sampling. Without the full evidence-vector, the bandit can't generalize to unseen co-fire patterns.

12. **Not testing the rollback-safety-net with a simulated bad-tuning.** A naive Move #6.15 ships the rollback-safety-net but never validates that the auto-revert actually works. Always include a load-test scenario where the auto-tuning produces a worse accuracy-score in the next 7 days → verify the auto-revert fires within 5 min + the Linear issue is opened + the prior YAML version is restored.

13. **Computing Move #6.14 breach-cost accuracy against operator-marked-wrong (instead of operator-marked-reconciliation-corrected).** A naive scorer reads "operator marked breach-cost wrong" → assumes the operator's correct value is the breach-cost ledger's actual. But the operator's `/wrong breach-cost` slash-command often lacks a specific number (just "this looks wrong") — the TRUE actual breach-cost comes from the CFO-board-pack weekly-reconciliation (Move #6.14's dollar-value minus the operator's manual reconciliation difference). Always use reconciliation-corrected breach-cost as the accuracy signal.

14. **Skipping the post-mortem template when Move #6.15 detects sustained accuracy drop.** When Move #6.15 detects NDCG@5 < 0.65 for 7 consecutive days OR sustained PSI > 0.5 for 3 consecutive weeks, the post-mortem template MUST auto-generate + the Linear / Jira issue MUST auto-open. Without the post-mortem, the operator can't trace which Move #6.12 hypothesis weight / Move #6.13 blast-radius score / Move #6.14 platform-set caused the drop.

15. **Tuning the 3 layers' auto-tuning schedules independently (instead of joint-tuning).** A naive Move #6.15 tunes Move #6.12 weights on Monday, Move #6.13 blast-radius on Tuesday, Move #6.14 platform-set on Wednesday — but the 3 layers are COUPLED (a Move #6.12 rank-error triggers a wrong Move #6.13 recipe which produces a wrong Move #6.14 breach-cost). Always run the 3 auto-tuning events JOINTLY on a single Monday cadence so the regression-detection can attribute accuracy-drops to the correct layer.
