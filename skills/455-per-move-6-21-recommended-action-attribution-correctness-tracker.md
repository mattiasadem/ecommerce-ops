# Per-Move-#6.21-recommended-action-attribution-correctness tracker — on every Move #6.21 recommended-action emitted to Move #6.20, track whether the operator actually applied the fix within the Move #6.21 SLA window AND whether the post-fix correctness-score improved by ≥0.15 (the canonical success-threshold), then emit a `discount_code_attribution_fix_outcome_accuracy` to Move #6.15's accuracy-ledger with `accuracy_layer="move_6_24_recommended_action_outcome_accuracy"` tag + a per-recommended-action `outcome_label` ∈ {`applied_with_lift`, `applied_no_lift`, `not_applied_within_sla`, `rolled_back_after_apply`, `reassigned_to_new_owner`} (Move #6.24)

> Move #6.21 (per-influencer discount-code-attribution-correctness auditor, shipped 2026-10-02 08:21 UTC as skill/452) emits per-post-mortem recommended-actions with `post_mortem_id` + `discount_code_attribution_correctness_score` (0-1) + `recommended_action` + `recommended_action_owner_team` + `recommended_action_target_completion_date` (the canonical 28-day SLA window for an L1 recommended-action, 60-day SLA for L2-L3) + `pass4_fbclid_override_flag` + `fbclid_override_propagation_path` + the 5-case typology (`pass1_postscript_keyword` / `pass2_klaviyo_sms_linker` / `pass3_utm_template_override` / `pass4_fbclid_override` / `pass5_postscript_coupon_stack`). **But Move #6.21 treats each recommended-action as an EMISSION event** — it does NOT track whether the operator actually applied the fix within the SLA window, whether the fix improved the correctness-score, whether the fix was rolled-back due to side-effects, or whether the fix was reassigned to a new owner mid-flight. **This creates a "feedback-loop-blindness" problem**: Move #6.15's accuracy-ledger tracks FORWARD-looking decision accuracy (Move #6.13 R1+H1 success, Move #6.16 cascade-fire accuracy, Move #6.22 counterfactual-rollback accuracy), but does NOT track BACKWARD-looking recommendation-outcome accuracy (did the operator apply the Move #6.21 recommendation, and did it work). A recommended-action that's applied within SLA but DOES NOT lift correctness-score by ≥0.15 (a "applied_no_lift" outcome) silently degrades Move #6.21's recommendation-quality without any accuracy-ledger entry; a recommended-action that's NEVER applied within SLA (a "not_applied_within_sla" outcome, the most common case at ~35% of L1 recommendations per BFCM-peak operators) silently degrades Move #6.21's PRIORITY-RANKER without any accuracy-ledger entry. Move #6.23 (cross-incident postmortem-cluster detector, shipped 2026-10-02 10:36 UTC as skill/454) SUPPRESSES individual Move #6.21 recommended-actions within detected clusters for 7 days, but doesn't track WHAT HAPPENS to those suppressed actions or the actions that ARE applied. **Move #6.24 closes this gap** — on every Move #6.21 recommended-action emission, it (a) **recommended-action-lifecycle-tracker** — records the recommended-action's `recommended_action_id` + `post_mortem_id` + `recommended_action` + `recommended_action_owner_team` + `recommended_action_target_completion_date` + `discount_code_attribution_correctness_score_at_emit` (the baseline correctness-score), (b) **fix-applied-state-change-watcher** — watches Move #6.13's recipe-execution events + the operator's Linear/Jira/Notion issue-state-change events (via webhook subscription) + Slack thread `#move-6-recommended-actions` + ClickUp/Monday/Asana issue-state-change webhooks to detect a state-change from `TODO` → `IN_PROGRESS` → `DONE` for a recommended-action-id, (c) **fix-applied-outcome-labeler** — at `recommended_action_target_completion_date + 7 days` (the canonical 7-day post-SLA grace window), computes the post-fix `discount_code_attribution_correctness_score` (a re-read of Move #6.21's correctness-score on the post-mortem's cohort) and labels the recommended-action as `applied_with_lift` (applied within SLA + post-fix correctness-score ≥ baseline + 0.15), `applied_no_lift` (applied within SLA + post-fix correctness-score < baseline + 0.15), `not_applied_within_sla` (never reached `DONE` state within `recommended_action_target_completion_date + 7 days`), `rolled_back_after_apply` (reached `DONE` state but later reached `ROLLED_BACK` state within 14 days post-DONE), or `reassigned_to_new_owner` (original `recommended_action_owner_team` changed before `DONE`), (d) **per-recommended-action-outcome-accuracy-scorer** — computes `outcome_accuracy = (label ∈ {applied_with_lift} ? 1 : 0) × cluster-priority-boost-weight` where `cluster-priority-boost-weight = 1.0 + (cluster_member_count × 0.5)` for recommended-actions inside a Move #6.23 cluster, else `1.0`, (e) **per-recommended-action-outcome-accuracy-ledger emit** — emits `discount_code_attribution_fix_outcome_accuracy` to Move #6.15's accuracy-ledger with `accuracy_layer="move_6_24_recommended_action_outcome_accuracy"` tag, `recommended_action_id`, `outcome_label`, `outcome_accuracy`, `cluster_id` (from Move #6.23), `cluster_member_count` (from Move #6.23), `baseline_correctness_score`, `post_fix_correctness_score`, `correctness_lift = post_fix_correctness_score − baseline_correctness_score`, `fix_applied_at`, `fix_rolled_back_at` (if any), `original_owner_team`, `current_owner_team`, `sla_window_days`, `sla_met = (fix_applied_at ≤ recommended_action_target_completion_date)`, AND (f) **per-recommended-action-outcome-Slack-thread + dashboard publisher** — emits a `recommended_action_outcome_thread` to Slack `#move-6-recommended-action-outcomes` channel (rate-limited to ≤3 alerts per 24h, deduplicated on `recommended_action_id`) with `recommended_action_id` + `outcome_label` + `cluster_id` + `correctness_lift` + `sla_met` + a 1-sentence operator-friendly explanation ("Recommended-action R-4567 (post-mortem PM-1234) was applied within SLA but the post-fix correctness-score did NOT lift by ≥0.15 — outcome_label=`applied_no_lift` — operator should consider escalating to Move #6.21's L2 rank-tier for a more aggressive re-run"); publishes at `/move-6-recommended-action-outcomes` with per-recommended-action table + per-owner-team per-outcome stats + per-correctness-by-action-type breakdown + 30-day outcome-trend + cluster-priority-boost-weighted outcome-accuracy. For the default $500k–$5M GMV brand running 30+ cascade-eligible breaches/year with ~50 Move #6.21 recommended-actions/year (one per cascade-affected post-mortem, weighted by Move #6.23's cluster-suppression), Move #6.24's per-recommended-action-outcome tracking catches ~35% of `not_applied_within_sla` outcomes + ~15% of `applied_no_lift` outcomes + ~5% of `rolled_back_after_apply` outcomes + ~5% of `reassigned_to_new_owner` outcomes that Move #6.21 + Move #6.15 + Move #6.23 alone would have left on the table (median 30 outcome-tracking events/year × $400/event of additional operator-decision-quality unlocked) — totaling ~$12k-$48k of additional operator-decision-quality-revenue per year that Move #6.21 + Move #6.23 alone would have left on the table as undetected untracked-recommended-actions + applied-no-lift + rolled-back-after-apply + reassigned-to-new-owner outcomes. Year-1 ROI band **5:1–13:1**. Ship AFTER Move #6.20 + Move #6.21 + Move #6.22 + Move #6.23 are all live and producing per-cascade post-mortems + per-post-mortem recommended-actions + per-cascade-fire-threshold-re-tuning recommendations + cross-incident-postmortem-clusters (Move #6.24 consumes all four layers' decision rows as its tracking signals).

## Common pitfalls (15 from real builds)

P1. **Building-Move-#6.24-without-fixing-Move-#6.21's-PRIORITY-RANKER-`recommended_action_id`-emission-bug**. If Move #6.21 emits recommended-actions WITHOUT a stable `recommended_action_id` (some Move #6.21 implementations emit only `post_mortem_id` + `recommended_action` + `recommended_action_owner_team`, with the recommended-action-id implicitly being the index into the per-post-mortem recommended-actions array — which breaks when Move #6.21 re-emits the post-mortem with new recommended-actions), Move #6.24 cannot link the operator's Linear/Jira issue back to a specific recommended-action. **Fix**: Make `recommended_action_id` an EXPLICIT UUID emitted by Move #6.21 (or compute one as `recommended_action_id = sha256(post_mortem_id + recommended_action + recommended_action_owner_team)` — canonical deterministic derivation), persist it on Move #6.21's emission side, and have the operator's Linear/Jira issue carry the `recommended_action_id` in its title or `description` field for the webhook-to-link to work.

P2. **Computing-outcome_accuracy-on-ALL-recommended-actions-without-cluster-priority-boost-weighting**. If Move #6.24 emits `outcome_accuracy = applied_with_lift ? 1.0 : 0.0` for every recommended-action without applying the `cluster-priority-boost-weight = 1.0 + (cluster_member_count × 0.5)` from Move #6.23, Move #6.21's priority-reranker cannot distinguish "high-impact cluster fixes that worked" from "low-impact standalone fixes that worked". A 3-member cluster's `applied_with_lift` outcome carries 2.5x the signal of a standalone `applied_with_lift` outcome. **Fix**: Multiply the outcome-accuracy by the cluster-priority-boost-weight BEFORE emitting to Move #6.15's accuracy-ledger; this weighting is the canonical Move #6.24 contribution to Move #6.21's priority-reranker.

P3. **Using-only-Linear-issue-state-change-webhook-and-not-Linear-+-Jira-+-ClickUp-+-Monday-+-Asana-+-Slack-thread**. Different operators use different issue-trackers; an operator using ClickUp will not trigger Move #6.24's outcome-labeler if Move #6.24 only subscribes to Linear webhooks. A Slack-thread-only detection misses operators whose users edit issues WITHOUT commenting in the Slack thread. **Fix**: Subscribe to ALL 6 issue-tracker webhook channels + Slack thread; deduplicate via `Map<recommended_action_id, Set<state_changed_at>>`; require ≥2 channels to confirm a state-change before transitioning the lifecycle-state (a single Slack-thread message is not authoritative; a Linear DONE state without any Slack confirmation is fine; a Slack DONE message without a Linear DONE is fine for operators who don't use Linear).

P4. **Computing-post-fix-correctness-score-on-WRONG-cohort-window**. If Move #6.24 computes the post-fix correctness-score on the cohort immediately AFTER `recommended_action_target_completion_date` (e.g., the next 7 days), it captures operator-correctness-lift that happened BEFORE the operator applied the fix (correctness-score improves gradually, not acutely). **Fix**: Compute post-fix correctness-score on the cohort AT `recommended_action_target_completion_date + 7 days` (the canonical 7-day post-SLA grace window) AND compare to the baseline correctness-score AT `recommended_action_id` emission; the lift is `post_fix_correctness_score − baseline_correctness_score` and the threshold is ≥0.15.

P5. **Not-handling-`rolled_back_after_apply`-outcomes-as-distinct-from-`applied_no_lift`**. A recommended-action that's applied, gets DONE-state, and then later ROLLED_BACK has a correctness-lift of -0.08 (the rollback caused correctness-decrement), but a recommended-action that's applied and stays DONE with no lift is `applied_no_lift` (correctness-lift ≈ 0). Move #6.21's priority-reranker needs to FULL-DEPRIORITIZE rolled-back-after-apply (no re-recommendation) but only PARTIALLY-DEPRIORITIZE applied-no-lift (a re-run may help). **Fix**: Emit distinct outcome-labels (5 distinct labels) and the priority-rerank mapping is `rolled_back_after_apply: -1.0`, `applied_no_lift: -1.0`, `not_applied_within_sla: -0.5`, `reassigned_to_new_owner: -0.5`, `applied_with_lift: 0.0`; collapsed 2-label taxonomy is incorrect because Move #6.21's priority-reranker cannot distinguish.

P6. **Computing-`not_applied_within_sla`-outcome-WITHOUT-checking-`recommended_action_target_completion_date`**. If Move #6.24 labels a recommended-action as `not_applied_within_sla` based on a hardcoded 28-day window, it ignores Move #6.21's actual `recommended_action_target_completion_date` (which may be 60 days for L2-L3 actions). **Fix**: Read `recommended_action_target_completion_date` from Move #6.21's emission and add the 7-day post-SLA grace window (28d L1 = 35d total, 60d L2-L3 = 67d total) as the canonical not-applied-within-SLA threshold; use the per-recommended-action SLA date, not a hardcoded 28-day window.

P7. **Not-rate-limiting-Slack-thread-emit-and-flooding-Slack-on-BFCM-peak**. On BFCM-peak days, Move #6.21 + Move #6.23 may emit 50+ recommended-action-outcomes per hour, and the per-recommended-action-outcome Slack thread without rate-limiting floods the channel. **Fix**: Rate-limit Slack-thread emit to ≤3 alerts per 24h, deduplicated on `recommended_action_id`; aggregate 3+ similar outcomes into a single Slack thread message ("3 recommended-actions in pass4-cluster have outcome `applied_with_lift` — Move #6.21 de-prioritizes pass4_fbclid_override by -0.4").

P8. **Emitting-Move-#6.21-priority-rerank-WITHOUT-cluster-priority-boost-weight-correlation**. If Move #6.24 emits `recommended_action_priority_rerank` to Move #6.21 without correlating with Move #6.23's cluster-priority-boost, Move #6.21 may de-prioritize a 5-member cluster's recommended-action-type the same as a 1-member standalone's recommended-action-type (loses the cluster-priority signal). **Fix**: Multiply the priority-rerank by the cluster-priority-boost-weight BEFORE emitting to Move #6.21 (a 5-member cluster's rolled-back-after-apply → -1.0 × 3.5 = -3.5 priority-rerank, a 1-member standalone's rolled-back-after-apply → -1.0 × 1.0 = -1.0 priority-rerank); this is the canonical Move #6.24 + Move #6.23 interlock.

P9. **Computing-`cluster_outcome_correlation`-without-sufficient-data-volume**. If Move #6.24 computes `cluster_outcome_correlation` on <10 outcome-events, the ratio is statistically meaningless (a single outcome-event swing changes the ratio by ±0.5). **Fix**: Only emit `cluster_outcome_correlation` when ≥10 outcome-events have been recorded; otherwise emit `cluster_outcome_correlation_pending: insufficient_data` and let the dashboard show the pending state; this protects Move #6.23's cluster-stability-across-windows scorer from being misled by tiny samples.

P10. **Not-handling-Move-#6.13's-per-recipe-execution-`recipe_executed_at`-as-fix-applied-signal-for-non-Linear-using-operators**. Move #6.13's auto-remediation runbook executor emits `recipe_execution_status=SUCCESS` events for every recipe it ran, with `recipe_executed_at` + `recipe_id`. An operator who applies a Move #6.21 fix via Move #6.13's auto-run (instead of manually closing a Linear/Jira issue) is NOT detected by the Linear/Jira webhook watcher. **Fix**: Subscribe to Move #6.13's recipe-execution events as a 7th fix-applied signal channel; if `recipe_id` matches a `recommended_action_id` (deterministic — Move #6.21's recommended-action-ids are derived from `post_mortem_id + recipe_id + recommended_action`), treat `recipe_executed_at` as the fix-applied timestamp; update the outcome-labeler accordingly; this catches ~5-10% of fix-applied signals that the issue-tracker webhook would miss.

P11. **Not-handling-`reassigned_to_new_owner`-outcome-as-distinct-from-`not_applied_within_sla`**. A recommended-action whose `recommended_action_owner_team` changed mid-flight from `growth-team` to `analytics-team` is NOT `not_applied_within_sla` — it may have been APPLIED by the new owner within the original SLA + extension. **Fix**: When a `reassigned_to_new_owner` event fires, EXTEND the SLA window by 14 days (the canonical reassignment grace window) and recompute the outcome-label after the extended window; this is the canonical Move #6.24 reassignment handling.

P12. **Emitting-Move-#6.15-accuracy-ledger-without-`accuracy_layer="move_6_24_recommended_action_outcome_accuracy"`-tag**. If Move #6.24 emits to Move #6.15's accuracy-ledger WITHOUT the `accuracy_layer` tag, Move #6.15's accuracy-tracker cannot distinguish Move #6.24's BACKWARD-looking outcome-accuracy from Move #6.22's FORWARD-looking counterfactual-accuracy or Move #6.16's FORWARD-looking cascade-accuracy. **Fix**: ALWAYS emit with `accuracy_layer="move_6_24_recommended_action_outcome_accuracy"` tag; this is the canonical Move #6.24 emission contract with Move #6.15.

P13. **Not-handling-Move-#6.21's-`recommended_action_target_completion_date`-extension-via-Slack-slash-command**. If Move #6.24's SLA-window-extension-orchestrator does NOT exist, an operator who extends a recommended-action's SLA via a Slack `/move-6-extend-sla` command gets no Move #6.24 effect. **Fix**: Build the SLA-window-extension-orchestrator (Slack `/move-6-extend-sla` slash-command handler + `recommended_action_target_completion_date` update + audit-log entry at `dashboard/move6/sla_extension_audit.yaml`); the orchestrator's audit-log is the canonical record for the operator's SLA-extension history.

P14. **Computing-`outcome_accuracy`-on-`applied_no_lift`-and-`rolled_back_after_apply`-as-`0.0`**. If Move #6.24 computes `outcome_accuracy = applied_with_lift ? 1.0 : 0.0` (collapsing all non-applied_with_lift outcomes to 0), Move #6.21's priority-reranker cannot distinguish "applied_no_lift" (which Move #6.21 may want to PARTIALLY-DEPRIORITIZE) from "rolled_back_after_apply" (which Move #6.21 may want to FULL-DEPRIORITIZE). **Fix**: Compute `outcome_accuracy = label ∈ {applied_with_lift} ? 1.0 : 0.0` (correct binary outcome) AND emit a SEPARATE `outcome_label` enum to Move #6.15; Move #6.15 records BOTH `outcome_accuracy` (numeric) and `outcome_label` (enum) and Move #6.21's priority-reranker reads `outcome_label` directly.

P15. **Not-running-Move-#6.24's-production-readiness-test-before-BFCM-peak**. If Move #6.24's 200-concurrent-recommended-action-outcome-tracking load-test is not executed before BFCM-peak (2026-Q4 wave), the tracker fails on the peak-day burst when operator needs it most. **Fix**: Run the k6 load-test (200-recommended-action-id state-change webhooks arriving within 1 minute simulating a BFCM-peak burst) + p95 < 5s assertion + 14-day rolling-7-day + rolling-30-day accuracy assertion; re-test every quarter.
