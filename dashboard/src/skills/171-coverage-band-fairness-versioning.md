## Common pitfalls (18 from real builds)

1. **Running Move #171 before Move #170 is shipped.** Move #171 requires Move #170 per-coverage-band-fairness-engine as the canonical upstream per-coverage-band-fairness decomposition — Move #170 must be live in production with all 10 verification gates passing per Move #170 playbook before Move #171 deployment begins. **Fix:** confirm `Move #170 verification log shows 10/10 gates PASS` before starting Move #171.

2. **Loosening the anti-monopoly-floor to make version-lineage-floor pass.** The anti-monopoly-floor (no single per-coverage-band-fairness × per-version-lineage-id >30% of events) is pinned at 30% by the SRE-coverage-band-fairness-versioning-2026 benchmark — loosening it to make a version-lineage-floor violation pass is the canonical Move #170-style regression trap. **Fix:** NEVER loosen the canonical 30% anti-monopoly-floor without a documented reason AND a TICK: <date> marker; the threshold is pinned by Move-#171-canonical-thresholds-published test.

3. **Treating version-1-initial as the only version-lineage.** The canonical 5-version-lineage-overlay decomposition is version-1-initial + version-2-rollback + version-3-fallback + version-4-recovery + version-5-deprecation — operators who only ship version-1-initial miss the per-coverage-band-fairness × per-version-lineage decomposition for the 4 downstream version-lineage categories. **Fix:** deploy all 5 version-lineage categories in Pillar B Step 1 + verify each version-lineage has ≥10% of total events in the verification log.

4. **Confusing per-version-lineage-bucket with per-version-lineage-classifier.** Per-version-lineage-bucket is the per-event runtime classifier that tags each event with one of the 5 canonical version-lineage categories; per-version-lineage-classifier is the static mapping table that maps per-coverage-band-fairness to canonical version-lineage (the table in section 3).
