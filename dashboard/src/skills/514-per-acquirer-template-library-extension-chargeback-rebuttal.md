## Common pitfalls (15 from real builds)

1. **Per-acquirer-chargeback-reason-code scope creep.** The most common pitfall. The per-acquirer-chargeback-reason-code algorithm covers 6 networks × ~20 reason-codes each = ~120 reason-codes total (Visa's 22 + MasterCard's 27 + AmEx's 19 + Discover's 13 + JCB's 11 + UnionPay's 11 + the 5 region-bucks-per-network sets for the 9 Brazil VISA-ADMIN / 9 Mexico VISA-ADMIN / 9 Argentina VISA-ADMIN / 9 Chile VISA-ADMIN / 9 Colombia VISA-ADMIN / 9 Peru VISA-ADMIN / 9 LATAM Mastercard-LAC / 9 LATAM AmEx / 9 LATAM Discover sets). If you start adding the 50+ less-common reason-codes (10.5 / 11.3 / 12.6 / 13.6 / F24 / F25 / F26 / F27 / A02 / C32 / C44 / C58 / C59 / C60 / C61 / C62 / C64 / C65 / C68 / C69 / FR4 / FR6 / 100 / 200 / 300 / 400 / 500 / 600 / 700 / 800 / 900 / U01 / U02 / 0100 / 0200 / 0300 / 0400 / 0500 / 0600 / 0700 / 0800 / 0900 / 1000 / 1100), the per-acquirer-chargeback-reason-code algorithm balloons to 200+ reason-codes and the per-acquirer-finance team can't keep them all current. The fix is to ship the 6 networks × 20 = 120 reason-codes first, observe which 30-40 reason-codes the per-acquirer-finance team uses 80% of the time, and only add the next 20 reason-codes when 80%+ of the existing reason-codes are being used monthly. Don't ship a per-acquirer-chargeback-reason-code algorithm with 200+ reason-codes — ship 120 and add 20 per quarter.
2. **Per-acquirer-chargeback-evidence-bundle completeness depends on the per-acquirer-network-program-context.** The pitfall. The per-acquirer-chargeback-evidence-bundle-template MUST auto-detect per-acquirer-network-program-context (Visa VAMP-2025/2026 → 3DS-frictionless-CE-3.0 + signed-delivery-confirmation + AVS-attestation + 3DS-server-response + device-fingerprint + IP-geolocation + order-history-record + ETickets-issued-anywhere + 10.5 reason-codes included; MasterCard ECM-HECM-2025/2026 → 3DS-frictionless-CE-3.0 + signed-delivery-confirmation + AVS-attestation + 3DS-server-response + device-fingerprint + IP-geolocation + order-history-record + F24 / F25 / F26 / F27 reason-codes included; AmEx MER-2025/2026 → 3DS-frictionless-CE-3.0 + signed-delivery-confirmation + AVS-attestation + 3DS-server-response + device-fingerprint + IP-geolocation + order-history-record + A02 / C32 / C44 reason-codes included; Discover DMP-2025/2026 → 3DS-frictionless-CE-3.0 + signed-delivery-confirmation + AVS-attestation + 3DS-server-response + device-fingerprint + IP-geolocation + order-history-record + AA / AR / AT reason-codes included; JCB Ref-2025/2026 → 3DS-frictionless-CE-3.0 + signed-delivery-confirmation + AVS-attestation + 3DS-server-response + device-fingerprint + IP-geolocation + order-history-record + 100 / 200 / 300 reason-codes included; UnionPay REFPD-2025/2026 → 3DS-frictionless-CE-3.0 + signed-delivery-confirmation + AVS-attestation + 3DS-server-response + device-fingerprint + IP-geolocation + order-history-record + 0100 / 0200 / 0300 reason-codes included) and auto-include the per-acquirer-network-program-context-specific evidence-bundle-required-evidence. Without the per-acquirer-network-program-context auto-detection, the per-acquirer-chargeback-evidence-bundle-template is incomplete for 50-70% of chargebacks per per-acquirer-network-payments-ops-enter-2025 benchmarks, dropping per-acquirer-chargeback-recovery-rate from 70-90% → 50-70% per per-acquirer-network-payments-ops-enter-2025.
3. **Per-acquirer-chargeback-timebarred-window is per-acquirer-network-program-specific.** The pitfall. The per-acquirer-chargeback-timebarred-window varies by network: Visa 120d (per VROL §5.5.4.1) + MasterCard 120d (per Mastercom §3.7.1) + AmEx 120d (per AmEx-CB §2.5) + Discover 120d (per DMP §2.4) + JCB 90d (per JDRP §2.2) + UnionPay 60d (per UPGD §2.1). The per-acquirer-chargeback-timebarred-challenge-template MUST auto-detect per-acquirer-network-program-timebarred-window AND per-acquirer-network-program-timebarred-window-exceeded. If the per-acquirer-chargeback-timebarred-challenge-template hard-codes 120d for all 6 networks, the per-acquirer-JCB-chargebacks are always past-timebarred-window at 91d-120d (30 days past-timebarred-window), and the per-acquirer-UnionPay-chargebacks are always past-timebarred-window at 61d-120d (60 days past-timebarred-window) — the per-acquirer-chargeback-timebarred-challenge-template produces per-acquirer-chargeback-timebarred-challenge for non-timebarred chargebacks (which the per-acquirer-network-program rejects) and misses per-acquirer-chargeback-timebarred-window-exceeded chargebacks (which the per-acquirer-finance team manually catches). Per per-acquirer-network-payments-ops-timebarred-2025 benchmarks, 5-15% of chargebacks are timebarred in the per-acquirer-network-program-timebarred-window — the per-acquirer-chargeback-timebarred-challenge-template recovers 5-15% × $50-$500/chargeback × 25-60 chargebacks/mo × 12 mo = $10K-$50K/yr of per-acquirer-chargeback-timebarred-recovery.
4. **Per-acquirer-chargeback-rebuttal-render function trusts the chat agent to fill the per-acquirer-chargeback-data correctly.** The pitfall. The per-acquirer-chargeback-rebuttal-render-pipeline must NEVER trust the chat agent to fill the per-acquirer-chargeback-rebuttal-template base skeleton with correct per-acquirer-chargeback-data — the chat agent will hallucinate per-acquirer-chargeback-currency formats, per-acquirer-chargeback-region-regulatory-references, per-acquirer-chargeback-network-program-context, per-acquirer-chargeback-evidence-bundle-completeness-checks, per-acquirer-chargeback-timebarred-window-detection. The fix is to call the per-acquirer-cadencer-MCP-server (Move #167.5.12.1) to fetch the canonical per-acquirer-chargeback-data, then fill the per-acquirer-chargeback-rebuttal-template base skeleton with the canonical per-acquirer-chargeback-data, then run the per-acquirer-chargeback-rebuttal validation pass to catch hallucinations. If the per-acquirer-chargeback-rebuttal validation pass fails, the per-acquirer-chargeback-rebuttal-template-library MUST reject the per-acquirer-chargeback-rebuttal-render and re-call the per-acquirer-cadencer-MCP-server.
5. **Per-acquirer-chargeback-routing-channel isn't auto-detected.** The pitfall. The per-acquirer-chargeback-routing-channel varies by per-acquirer-network-program: Visa → VROL + CE-3.0 + Verifi + Ethoca + RDIF + RDRF (per VROL §3.2.1); MasterCard → Mastercom + CDRN + Verifi + Ethoca + RDIF + RDRF (per Mastercom §2.4.1); AmEx → AmEx-CB-Portal + AmEx-CB-SDK + Verifi + Ethoca + RDIF + RDRF (per AmEx-CB §2.3); Discover → Discover-Network-Portal + Discover-Dispute-SDK + Verifi + Ethoca + RDIF + RDRF (per DMP §2.2); JCB → JCB-Dispute-Portal + JCB-Dispute-SDK + Verifi + Ethoca + RDIF + RDRF (per JDRP §2.1); UnionPay → UnionPay-Dispute-Portal + UnionPay-Dispute-SDK + Verifi + Ethoca + RDIF + RDRF (per UPGD §2.1). The per-acquirer-chargeback-submission-template MUST auto-detect per-acquirer-network-program-routing-channel AND emit per-acquirer-chargeback-submission via the canonical per-acquirer-network-program-routing-channel. If the per-acquirer-chargeback-submission-template hard-codes per-acquirer-network-program-routing-channel, the per-acquirer-chargeback-submission is routed to the wrong per-acquirer-network-program and the per-acquirer-finance team has to manually re-route per per-acquirer-network-program-routing-channel.

If the per-acquirer-chargeback-rebuttal-render-pipeline takes 10-30 seconds, the per-acquirer-finance team will revert to manual per-acquirer-chargeback-rebuttal drafting because the manual drafting is faster. The fix is to (a) pre-cache the per-acquirer-chargeback-rebuttal-template skeletons, (b) pre-fetch the per-acquirer-cadencer-MCP-server data, (c) pre-validate the per-acquirer-chargeback-rebuttal-template against the per-acquirer-chargeback-validation rules, (d) stream the per-acquirer-chargeback-rebuttal-template render to the per-acquirer-finance team's browser so the per-acquirer-finance team sees the per-acquirer-chargeback-rebuttal-template render in <1s.

The per-acquirer-chargeback-evidence-bundle validation pass MUST call the per-acquirer-cadencer-MCP-server (Move #167.5.12.1) to verify the per-acquirer-chargeback-evidence-bundle's per-acquirer-currency, per-acquirer-region, per-acquirer-network-program, per-acquirer-tax-form, per-acquirer-data-protection references against the canonical per-acquirer-chargeback-data. A regex-only lint will pass a per-acquirer-chargeback-evidence-bundle with `per-acquirer-chargeback-amount-of-$1,234,567` when the actual per-acquirer-chargeback-amount is `$123,456` — the regex doesn't catch numeric-drift. The fix is to fetch the canonical per-acquirer-chargeback-data from the per-acquirer-cadencer-MCP-server and compare the per-acquirer-chargeback-evidence-bundle's per-acquirer-currency values + per-acquirer-network-program-context + per-acquirer-tax-form + per-acquirer-data-protection references against the canonical per-acquirer-chargeback-data.

The per-acquirer-chargeback-friendly-fraud-fast-resolve-mode MUST auto-detect per-acquirer-network-program-friendly-fraud-fast-resolve-channel AND emit per-acquirer-chargeback-friendly-fraud-fast-resolve via the canonical per-acquirer-network-program-friendly-fraud-fast-resolve-channel. If the per-acquirer-chargeback-friendly-fraud-fast-resolve-mode hard-codes per-acquirer-network-program-friendly-fraud-fast-resolve-channel, the per-acquirer-chargeback-friendly-fraud-fast-resolve is rejected by the per-acquirer-network-program and the per-acquirer-finance team has to manually re-route per per-acquirer-network-program-friendly-fraud-fast-resolve-channel.
