## When to use this skill

**Use this skill when the operator is doing ≥$1M GMV AND has ≥$300k ARR AND ≥$50 AOV AND ≥2 multi-warehouse-3PL contracts AND ≥1,000 new-orders-per-month AND is uncertain which 3PL warehouse cohort is driving the highest 12-month-LTV AND/OR is routing new orders only by ship-cost (the canonical naive approach — picks the lowest-cost warehouse, NOT the highest-LTV-cohort-cluster warehouse) AND/OR is uncertain whether the per-warehouse cohort-LTV-Δ vs baseline is recoverable through per-warehouse-cohort-LTV-driven-routing-engine + per-warehouse-routing-by-cohort-LTV-optimizer.** Per-warehouse-cohort-LTV-attribution is structurally distinct from Move #21's 3PL-migration (which is the multi-3PL-launch playbook), from Move #249's per-warehouse-return-rate-attribution-engine (which has the per-warehouse RETURN-RATE dimension WITHOUT the per-warehouse cohort-LTV dimension — Move #249 answers "which 3PL has the lowest damaged-in-shipping rate", Move #251 answers "which 3PL warehouse cohort drives the highest 12-month-LTV"), from Move #119's per-cohort-attribution-decision-engine (which has the per-CO cohort-LTV dimension WITHOUT the per-warehouse dimension — Move #119 answers "which cohort has the highest LTV", Move #251 answers "which 3PL warehouse cohort drives the highest LTV"), from Move #248's per-SKU-return-rate-forecasting-and-return-cost-attribution (which has the per-channel per-cohort per-vertical per-SKU layer WITHOUT the per-warehouse dimension), from Move #110's sku-inventory-allocation-engine (which handles the per-warehouse-inventory-allocation layer WITHOUT cohort-LTV), and from Move #45's warehouse-management-fulfillment-orchestration (which is the broader-WMS-layer that has a per-warehouse cohort-LTV bullet among 200+ metrics but no dedicated per-warehouse-cohort-LTV-overlay + per-warehouse-routing-engine). Move #251 is the **per-warehouse cohort-LTV attribution + per-warehouse 12-month-LTV-overlay + per-warehouse cohort routing optimizer + per-warehouse cohort-30/60/90/180/365-day-LTV curve + per-warehouse repeat-purchase-rate + per-warehouse subscription-conversion-rate + per-warehouse reorder-cadence + per-warehouse AOV-by-cohort + per-warehouse cohort-LTV-driven multi-warehouse routing engine** layer — the operator should only initiate it when ALL of the following are true:

**You have:**

1. **Move #21 (3PL-migration) shipped ≥60 days** — Move #251 gates on having ≥60 days of post-3PL-launch baseline so the per-warehouse cohort-LTV-overlay can correlate against the pre-mix-period to measure the lift from per-warehouse-cohort-LTV-driven-routing-engine.
2. **Move #88 (returns-reverse-logistics-prevention) shipped ≥60 days** — Move #251 reads Move #88's per-warehouse grading-cost + recommerce-handoff + liquidation-handoff + reverse-pick-pack-cost to compute the per-warehouse cohort-LTV-net-of-return-cost overlay (the canonical cohort-LTV-net-of-return-cost per Smile.io Cohort LTV 2024 + Triple Whale Cohort LTV 2024 + Recharge Cohort LTV 2024 + Skio Cohort LTV 2024 benchmarks).
3. **Move #249 (per-warehouse-return-rate-attribution-engine) shipped ≥30 days** — Move #251 builds on Move #249's per-warehouse return-rate-baseline + per-warehouse-damaged-in-shipping-baseline + per-warehouse-grading-A-rate + per-warehouse-recovery-loss-by-grade to compute the per-warehouse cohort-LTV-overlay that nets out return-cost (the canonical 3PL × cohort-LTV intersection per Ecommerce Per Warehouse Cohort LTV 2024 + Ecommerce Per Warehouse Reorder Cadence 2024 + Ecommerce Per Warehouse Repeat Purchase Rate 2024 + Ecommerce Per Warehouse Subscription Conversion Rate 2024 + Ecommerce Per Warehouse AOV By Cohort 2024 benchmarks).
4. **A documented per-warehouse cohort-LTV-baseline AND a documented per-warehouse ship-cost-baseline** — Move #251 reads Move #21's per-warehouse mix-shift baseline (ShipBob + ShipMonk + ShipHero mix shares) and overlays the canonical per-warehouse 12-month-cohort-LTV + per-warehouse 90-day-repeat-purchase-rate + per-warehouse subscription-conversion-rate baseline to compute the per-warehouse cohort-LTV-driven routing engine.

**You want to:**

- Answer the canonical operator question: *"which 3PL warehouse cohort drives the highest 12-month-LTV, and where should I route new orders to maximize LTV (NOT just minimize ship-cost)?"*
- Surface the per-warehouse cohort-LTV-overlay gap: the operator is currently routing by ship-cost-only and is missing $84–$340 per-customer 12-month-LTV because the highest-LTV cohort-cluster ships from warehouses that aren't the lowest-ship-cost warehouse.
- Quantify the per-warehouse cohort-30/60/90/180/365-day-LTV curve so the operator can see which warehouse cohort pays back CAC fastest, which has the longest reorder-tail, and which has the lowest churn.
- Run a per-warehouse cohort-LTV-driven multi-warehouse routing engine that biases new-order routing toward the highest-LTV-cohort-cluster warehouse (NOT just lowest-ship-cost).
- Track the per-warehouse subscription-conversion-rate because subscription-cohort is the highest-LTV-cohort cluster and the warehouse that converts the most first-time-buyers into subscribers is the canonical "highest-LTV warehouse" for the operator.

**You do NOT have:**

- A per-warehouse cohort-LTV dashboard (the operator currently can see per-warehouse SHIP-COST but not per-warehouse cohort-LTV)
- A per-warehouse routing engine that biases toward highest-LTV-cohort-cluster warehouse (the operator currently routes only by ship-cost)
- A per-warehouse cohort-30/60/90/180/365-day-LTV curve (the operator currently sees only aggregate 12-month-LTV, not per-warehouse × per-cohort decomposition)
- A per-warehouse subscription-conversion-rate signal (the operator currently does not know which 3PL converts the most first-time-buyers into subscribers)
- A per-warehouse reorder-cadence signal (the operator currently does not know which 3PL has the shortest reorder-cadence — the canonical "habit-formation warehouse" indicator)

## Common pitfalls (16 from real builds)

1. **Routing by ship-cost-only (canonical naive approach).** Operator routes new orders to the lowest-ship-cost warehouse without consulting cohort-LTV. The highest-LTV cohort-cluster ships from a warehouse that costs $0.40–$1.20 more per order to ship — but the LTV upside is $84–$340 per customer over 12 months. Fix: route via per-warehouse cohort-LTV-driven routing engine (Phase 2.3) that biases toward highest-LTV-cohort-cluster warehouse (per the per-warehouse cohort-LTV-overlay from Phase 2.1).

2. **Per-warehouse cohort-LTV measured only at 12-month (not the 5-point 30/60/90/180/365-day curve).** Operator sees only aggregate 12-month-LTV-by-warehouse and misses the per-warehouse cohort-30-day-LTV (the canonical early-purchase-signal warehouse indicator) and per-warehouse cohort-180-day-LTV (the canonical reorder-tail warehouse indicator). Fix: compute the canonical 5-point cohort-LTV curve per warehouse in Phase 1.2 (Triple Whale + Polar + Northbeam + Smile + Recharge + Skio APIs).

3. **Per-warehouse subscription-conversion-rate not tracked.** Operator tracks per-warehouse repeat-purchase-rate but not per-warehouse subscription-conversion-rate — and misses that the highest-LTV-cohort is the subscription-cohort, and the warehouse that converts the most first-time-buyers into subscribers is the canonical "highest-LTV warehouse". Fix: add per-warehouse subscription-conversion-rate signal in Phase 1.3 (Recharge + Skio + Smile APIs).

4. **Per-warehouse cohort-LTV-overlay doesn't net out return-cost.** Operator measures per-warehouse 12-month-cohort-LTV GROSS but not NET-OF-RETURN-COST — and a warehouse with high gross-LTV but also high return-rate (per Move #249 per-warehouse-return-rate-attribution-engine) has lower net-LTV than expected. Fix: build the canonical per-warehouse-net-cohort-LTV in Phase 2.1 that nets out per-warehouse return-cost (per Move #249 substrate).

5. **Per-warehouse reorder-cadence not tracked.** Operator tracks per-warehouse repeat-purchase-rate but not per-warehouse reorder-cadence — and misses the canonical "habit-formation warehouse" indicator (the warehouse cohort with the shortest reorder-cadence is the highest-LTV-cohort-cluster). Fix: add per-warehouse reorder-cadence signal in Phase 1.3 (Triple Whale + Polar + Northbeam APIs).

6. **Per-warehouse ship-time-vs-LTV-tradeoff not analyzed.** Operator assumes shorter ship-time = higher LTV, but data shows that for some cohorts, the warehouse with 2-day ship-time has LOWER cohort-LTV than the warehouse with 4-day ship-time (because the slower warehouse serves a different cohort-segment that has higher AOV and higher reorder-rate). Fix: build the canonical per-warehouse ship-time-vs-LTV-tradeoff-decision-engine in Phase 2.2 that surfaces the per-warehouse × per-cohort ship-time-vs-LTV tradeoff curve.

7. **Per-warehouse cohort-LTV-dashboard doesn't include the per-warehouse × per-cohort heatmap.** Operator sees per-warehouse 12-month-LTV in aggregate but not the per-warehouse × per-cohort decomposition (which cohort drives the highest LTV at which warehouse). Fix: include the per-warehouse × per-cohort heatmap in Phase 3.1 dashboard as the canonical "where do my best customers ship from" view.

8. **Per-warehouse subscription-conversion-rate not segmented by offer.** Operator tracks per-warehouse subscription-conversion-rate in aggregate but not by subscription-offer (e.g., "Subscribe & Save 15%" vs "Subscribe & Save 20%") — and misses that the warehouse that converts on the 15% offer is different from the warehouse that converts on the 20% offer. Fix: extend Phase 1.3 to compute per-warehouse subscription-conversion-rate × per-subscription-offer.

9. **Per-warehouse cohort-LTV-overlay doesn't include ship-cost delta.** Operator measures per-warehouse cohort-LTV lift but doesn't compare against the ship-cost delta (the canonical "is the LTV lift worth the ship-cost delta" tradeoff). Fix: include the per-warehouse ship-cost-vs-LTV-decision-engine in Phase 2.2 that surfaces the per-warehouse ROI-curve.

10. **Per-warehouse routing-decision-explainer not captured.** Operator runs per-warehouse cohort-LTV-driven routing but doesn't log the per-order routing-decision-explainer ("this order routed to warehouse X because cohort Y has LTV $Z") — and can't audit or replay the routing decisions when cohort-LTV-deltas drift. Fix: capture the per-warehouse routing-decision-audit-trail in Phase 2.4 with per-order × per-decision × per-explainer rows.

11. **Per-warehouse quarterly-renegotiation-decision-engine missing.** Operator tracks per-warehouse cohort-LTV but doesn't tie it to the 3PL contract renegotiation decision (the canonical "this 3PL is costing us $84/customer in cohort-LTV upside, renegotiate or off-board" signal). Fix: wire the per-warehouse quarterly-renegotiation-decision-engine in Phase 4.3 with the canonical Path A-baseline threshold.

12. **Per-warehouse cohort-LTV-board-pack not automated.** Operator manually computes per-warehouse cohort-LTV-board-pack quarterly, missing monthly trend signals. Fix: wire the per-warehouse monthly cohort-LTV-board-pack automation in Phase 4.2 (auto-email + Slack post + Notion page on the 1st of every month).

13. **Per-warehouse AOV-by-cohort not tracked.** Operator tracks per-warehouse AOV in aggregate but not per-warehouse AOV-by-cohort — and misses that some warehouses serve higher-AOV cohorts (the canonical "premium-customer warehouse" indicator). Fix: add per-warehouse AOV-by-cohort signal in Phase 1.3 (Triple Whale + Polar + Northbeam APIs).

14. **Per-warehouse cohort-LTV-driven routing-engine biases toward highest-LTV only, ignoring ship-cost.** Operator runs LTV-overlay routing but ignores ship-cost-delta (the canonical "is the LTV lift worth the ship-cost delta" tradeoff) — and routes orders to a warehouse with $4 higher ship-cost for $2 LTV lift (a net loss). Fix: include the per-warehouse ship-cost-vs-LTV-decision-engine in Phase 2.2 with the canonical ROI-curve threshold (LTV lift must exceed ship-cost delta × 12-month-cohort-volume).

15. **Per-warehouse cohort-LTV-dashboard doesn't include per-customer-segment routing view.** Operator sees per-warehouse cohort-LTV at the cohort level but not per-customer (the canonical "LTV-buyer to LTV-warehouse, value-buyer to value-warehouse" stretch routing). Fix: add per-customer-segment routing view in Phase 3.1 dashboard (Path C stretch scope).

16. **Per-warehouse cohort-LTV baseline not refreshed.** Operator builds per-warehouse cohort-LTV baseline once and never refreshes — and misses cohort-LTV drifts caused by 3PL service-quality changes, ship-time drift, or cohort-mix shift. Fix: refresh per-warehouse cohort-LTV baseline weekly in Phase 4.2 with per-warehouse-cohort-LTV-alert-routing-engine configured for >5pp LTV-delta alerts.
