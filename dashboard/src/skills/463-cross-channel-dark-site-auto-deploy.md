## The build (12-20 hours for a competent operator with $5k-15k setup cost)

### Step 1 — Bootstrap the dark-site-template library from Move #1's post-incident learning ledger (4 hours)

Pull from Move #1's post-incident learning ledger (Notion / Linear / Confluence / Airtable / Google Sheets / custom-DB):

1. **Dark-site HTML templates (8 templates, one per Move #1 8-scenario vulnerability matrix)**:
   - Template 1: **Product recall** (Daily Harvest, Drunk Elephant, Krave Beauty pattern) — full-refund + replacement + return-flow + recall-notice + FDA/CPSC-link
   - Template 2: **Viral TikTok / Instagram** (Kardashian Sunscreen, Glossier Cornrows pattern) — founder-statement + FAQ + press-kit + return-flow
   - Template 3: **Founder controversy** (Bud Light, Logan Paul / Lunchly pattern) — founder-statement + executive-bio + investor-letter + employee-letter
   - Template 4: **Supply-chain failure** (Patagonia, Allbirds pattern) — supply-chain-statement + timeline + recovery-plan + customer-impact
   - Template 5: **Creator fallout** (Move #1 creator-fallout lane) — creator-statement + creator-coordination + creator-disclosure + FTC-compliance
   - Template 6: **Contamination** (Daily Harvest listeria, Drunk Elephant recall pattern) — contamination-statement + return-flow + health-authority-link + FAQ
   - Template 7: **Brand reputation** (Bud Light Dylan Mulvaney, Glossier Cornrows pattern) — brand-statement + values-restatement + customer-letter
   - Template 8: **Operational** (Move #1 operational lane: warehouse-fire / 3PL-failure / payment-outage) — operational-status-page + recovery-timeline + customer-impact
2. **FAQ templates (8 templates)**: one per Move #1 8-scenario, auto-populated with the 12-15 most-common customer questions per scenario (e.g. recall-FAQ: "Is the product safe to use?" / "How do I return it?" / "Will I get a refund?" / "How long will the refund take?" / "Is my data safe?" / "Can I exchange for a different product?" / "What if I bought it as a gift?" / "What if I bought it on Amazon?" / "What if I already used some?" / "Will there be a replacement?" / "How do I contact support?" / "Will my subscription be paused?")
3. **Return-flow templates (5 templates)**: full-refund / replacement / store-credit / repair / recall-with-replacement — each linked to Move #28 returns-portal-orchestration
4. **Press-kit templates (4 templates)**: statement / FAQ / b-roll / exec-bio — each pre-staged and auto-translated via LLM
5. **Status-page-component templates (8 templates)**: one per Move #1 8-scenario, with auto-create-incident + auto-update-status + auto-resolve-on-deploy
6. **Multi-language templates (3 baseline languages)**: English / Spanish / French — auto-translated via LLM at deploy-time
7. **Severity-score-driven content-blocks (10 blocks)**: severity-score 80-100 (page-1 hero statement), severity-score 60-80 (page-2 FAQ), severity-score 40-60 (page-3 return-flow), severity-score <40 (page-4 press-kit) — Move #1.2 auto-routes the customer to the right content-block based on severity-score + per-cohort (e.g. recall-only-for-affected-customers)

Save to a single Notion workspace (with the 8 templates + 8 FAQ + 5 return-flow + 4 press-kit + 8 status-page + 3 language + 10 content-block = 46 templates total) and connect via Notion-API.

### Step 2 — Build the Cloudflare-Pages + Cloudflare-R2 + Cloudflare-Workers dark-site-deploy infrastructure (4 hours)

Set up the dark-site hosting + deploy infrastructure:

1. **Cloudflare-Pages project**: create a new Pages project (`<brand>-crisis-dark-site`) connected to a GitHub-repo (`<brand>/crisis-dark-site`).
2. **Cloudflare-R2 bucket**: create an R2 bucket for static assets (images, video, PDFs, FAQ-icons, press-kit-b-roll) — public-read via custom-domain `cdn.<brand>-crisis.com`.
3. **Cloudflare-Workers function**: a Cloudflare-Worker that reads Notion-API-page-content + Linear-API-issue-content + Statuspage-API-incident-content, and renders the dark-site HTML at edge (low-latency, global).
4. **GitHub-Actions deploy-hook**: a GitHub-Action that triggers Cloudflare-Pages deploy on Notion-API-page-content-change (Notion-webhook → GitHub-Action → Cloudflare-Pages-deploy-hook).
5. **DNS pre-pointing**: pre-register `crisis.<brand>.com` (or `<brand>-status.com`) and pre-point DNS to Cloudflare-Pages (CNAME) so the deploy is instant (no DNS-propagation delay).
6. **Statuspage-API integration**: connect Statuspage-API-component-create-incident to the Cloudflare-Worker (auto-create-incident-on-deploy + auto-update-status + auto-resolve-on-deploy).
7. **Move #28 returns-portal-orchestration integration**: connect Move #28's 5-flow return-flow to the dark-site (auto-link-to-returns-portal + auto-route-product-SKU-to-right-return-flow).
8. **Move #6.15 attribution-accuracy-tracker integration**: connect Move #6.15 to the dark-site-analytics (dwell-time + page-views + per-cohort + per-language + per-platform + per-incident-recovery-dashboard).

Deploy the Cloudflare-Worker + Cloudflare-Pages + Cloudflare-R2 + GitHub-Action + DNS pre-pointing → dark-site is live at `crisis.<brand>.com` with all 46 templates ready to be auto-populated.

### Step 3 — Build the Move #1.1 severity-score-trigger + auto-deploy-pipeline (4 hours)

Connect Move #1.1's severity-score≥80 trigger to the auto-deploy-pipeline:

1. **Move #1.1 webhook**: when Move #1.1's severity-score reaches ≥80, it fires a webhook to Move #1.2's trigger-handler (Cloudflare-Worker).
2. **Trigger-handler logic**:
   - Receive Move #1.1 severity-score + 4-lane-routed-alert + incident-type
   - Look up the right dark-site-template (e.g. recall → Template 1, viral-TikTok → Template 2, founder-controversy → Template 3, etc.)
   - Look up the right FAQ-template + return-flow-template + press-kit-template + status-page-template
   - Look up the right language (default English, then auto-translate to Spanish + French via LLM)
   - Render the dark-site HTML at edge (Cloudflare-Worker)
   - Deploy to Cloudflare-Pages (deploy-hook)
   - Create Statuspage-incident (Statuspage-API)
   - Create Linear-issue (Linear-API)
   - Send Slack-block-kit-alert to `#crisis-<lane>` channel with the dark-site-link
3. **LLM-auto-population**: a Claude / GPT-4 / Gemini / Cohere fine-tuned prompt that takes the incident-type + product-SKU + return-flow + legal-terms and auto-populates the 8-template FAQ + 5-flow return-flow + 4-template press-kit (≤60 sec end-to-end including LLM-latency).
4. **DDOS-mitigation + rate-limiting**: Cloudflare-DDOS + Cloudflare-rate-limiting + bot-detection + WAF-rules (auto-engage on severity-score≥80 to prevent malicious traffic from overwhelming the dark-site).
5. **Multi-region-failover**: Cloudflare-Pages + Cloudflare-Workers + Cloudflare-R2 deploy to 200+ edge-locations globally (default), with multi-region-failover to Fastly + AWS-Cloudfront (stretch).
6. **Auto-rollback-on-deploy-failure**: if the dark-site-deploy fails (e.g. Notion-API 500 error), auto-rollback to the last-known-good-template + send PagerDuty-15min-SLA-page + Slack-#crisis-ops alert.

Test the trigger-handler end-to-end with a synthetic Move #1.1 severity-score≥80 alert → dark-site-deploys in <60 sec + Statuspage-incident-creates + Linear-issue-creates + Slack-alert-sends.

### Step 4 — Build the post-incident-dwell-time-tracker + post-incident-recovery-dashboard (4 hours)

Track the post-incident-dwell-time + post-incident-recovery-delta:

1. **Per-page-dwell-time-tracker**: Cloudflare-Web-Analytics + Plausible + Fathom + GA4 + custom-JS (dwell-time = time-on-page - time-on-F-A-Q-CTA - time-on-return-flow-CTA) → emit to Move #6.15 attribution-accuracy-tracker.
2. **Per-cohort-dwell-time**: track dwell-time per-cohort (affected-customers vs non-affected-customers vs press vs investors vs employees) → emit to Move #1's post-incident learning ledger.
3. **Per-language-dwell-time**: track dwell-time per-language (English / Spanish / French) → emit to Move #6.15 + Move #1's post-incident learning ledger.
4. **Per-platform-dwell-time**: track dwell-time per-platform (TikTok / Instagram / Twitter / Reddit / Google / direct) → emit to Move #6.15 + Move #1.1 AI-crisis-classifier (feedback-loop).
5. **Per-incident-recovery-dashboard**: a `/crisis-recovery-dashboard` page that shows per-incident: deploy-latency + uptime + per-page-dwell-time + per-cohort-dwell-time + per-language-dwell-time + per-platform-dwell-time + recovery-time (incident→resolved) + brand-impact-delta (pre-crisis vs post-crisis brand-sentiment-score) → emit to Move #1's 5-funnel-stage response cascade.
6. **Move #1.1 feedback-loop**: feed the dwell-time + recovery-time + brand-impact-delta back to Move #1.1's AI-crisis-classifier so it can recalibrate the severity-score (e.g. if severity-score≥80 + <60 sec deploy + <30 min recovery = +5 severity-score-bump; if severity-score≥80 + >2 hour deploy = −5 severity-score-bump).

## Common pitfalls

1. **Building the dark-site-template library without Move #1's post-incident learning ledger bootstrap** — the 8 templates need to be bootstrapped from past crises (Daily Harvest recall, Drunk Elephant recall, Bud Light Dylan Mulvaney, etc.), not invented from scratch. **Without the post-incident learning ledger, the 8 templates will be generic ("we apologize for any inconvenience") instead of crisis-specific ("here's how to return your Daily Harvest lentil-cracker batch")** — the dark-site will look like a marketing page, not a crisis response.
2. **Using a hardcoded-HTML-in-GitHub-repo approach instead of Notion-as-CMS** — the operator (not the engineer) needs to be able to update the press-statement + FAQ + return-flow within minutes of a crisis. **Without Notion-as-CMS, every crisis requires an engineer to push a Git-commit + wait for CI/CD-deploy + wait for Cloudflare-Pages-cache-invalidation** — adds 30-90 minutes to the deploy-latency.
3. **Single-region-deploy instead of multi-region-failover** — if the dark-site is deployed to a single region (e.g. `us-east-1` only), a regional outage (DDoS, AWS-outage, network-partition) takes the dark-site offline during the crisis. **Without multi-region-failover, the dark-site is unavailable exactly when customers need it most** — the crisis-response is broken.
4. **No-DDOS-mitigation** — high-profile crises attract opportunistic attackers (DDoS, bot-traffic, malicious-form-submissions) who target `crisis.<brand>.com` to amplify the crisis. **Without Cloudflare-DDOS + Cloudflare-rate-limiting + bot-detection + WAF-rules, the dark-site goes offline within minutes of going live** — the crisis-response is broken.
5. **No-auto-rollback-on-deploy-failure** — if the dark-site-deploy fails (e.g. Notion-API 500 error, Cloudflare-Pages-deploy-error, LLM-API-rate-limit), the team needs to know immediately and rollback to the last-known-good-template. **Without auto-rollback + PagerDuty-page, the dark-site is broken for 30-90 minutes while the team debugs** — the crisis-response is delayed.
6. **Static-template-FAQ (operator-edits-each-crisis) instead of LLM-auto-populated-FAQ** — if the operator has to manually edit the FAQ for each crisis, the deploy-latency is 30-90 minutes (not <60 sec). **Without LLM-auto-population, the FAQ is generic ("here are some FAQs") instead of crisis-specific ("here's how to return your lentil-cracker batch")** — the dark-site looks unprepared.
7. **No-multi-language-support (English-only)** — if the brand has Spanish-speaking or French-speaking customers (50%+ of US-DTC brands), the dark-site needs to be auto-translated. **Without 3-language baseline (English / Spanish / French), 50%+ of customers see a dark-site in a language they don't understand** — the crisis-response is incomplete.
8. **No-Statuspage-integration (manual-Statuspage-update)** — if the operator has to manually update the Statuspage after deploying the dark-site, the Statuspage is 30-90 minutes behind. **Without auto-create-incident + auto-update-status + auto-resolve-on-deploy, customers checking the Statuspage see "all systems operational" while the dark-site is live with a recall-notice** — confusing.
9. **No-Linear-issue-creation (no-incident-tracking)** — if the operator has to manually create a Linear-issue to track the crisis, the incident-response is uncoordinated. **Without auto-create-Linear-issue + auto-link-dark-site + auto-assign-incident-owner, the crisis-response is fragmented across Slack + Notion + Linear + Statuspage** — the team is uncoordinated.
10. **No-Move-#6.15-attribution-accuracy-tracker-integration** — if the operator doesn't track per-deploy dark-site dwell-time + post-incident-recovery-delta, they can't measure the impact of Move #1.2 on brand-recovery. **Without Move #6.15 integration, the operator can't see "Move #1.2 cut dwell-time from 3 hours to 45 seconds in Q4-2025, which correlated with a 35% lift in post-incident brand-recovery-score"** — Move #1.2's value is invisible.
11. **No-Move-#1.1-feedback-loop (no-severity-score-recalibration)** — if the dark-site-deploy-latency + recovery-time + brand-impact-delta don't feed back to Move #1.1's AI-crisis-classifier, the severity-score is permanently mis-calibrated. **Without the feedback-loop, severity-score≥80 may actually be severity-score≥60 (over-paging) or severity-score≥80 may actually be severity-score≥95 (under-paging)** — the team is either alert-fatigued or under-prepared.
12. **No-severity-score-driven content-blocks (single-template-for-all-severities)** — if the dark-site uses the same template for severity-score 40-60 vs 60-80 vs 80-100, the customer sees the same content regardless of severity. **Without severity-score-driven content-blocks, a severity-score 45 (operational issue, not a crisis) gets the same hero-statement as a severity-score 95 (recall, life-safety)** — over- or under-responding.
13. **No-per-cohort-access-control (recall-only-for-affected-customers)** — if a recall affects only customers who bought SKU-X in the last 90 days, the dark-site should ONLY show the return-flow to those customers (not to all customers). **Without per-cohort-access-control, every customer sees a recall-notice (even if their product is not affected) → 80%+ of customers panic-unnecessarily** — the crisis is amplified.
14. **No-per-product-SKU dynamic-return-flow** — if the return-flow is a single "click here to return" link (not a per-SKU flow), the customer doesn't know WHICH product they're returning. **Without per-product-SKU dynamic-return-flow, the customer submits a generic return-request → Move #28 returns-portal-orchestration has to manually-route the request → 24-48 hour delay** — the customer is frustrated.
15. **Not-running-Move-#1.2's-production-readiness-test-before-BFCM-peak** — 200-concurrent-dark-site-deploy load-test p95 < 60 sec is REQUIRED. **Without load-test, Move #1.2 silently fails on BFCM-peak days when the operator needs it most** — the crisis-response is broken.
16. **Using-Cloudflare-Pages-free-tier-only-without-upgrade-to-Cloudflare-Pages-Pro** — free-tier has 500-builds/month limit + 1-custom-domain limit + no-DDOS-mitigation. **Without Pro-tier, the dark-site-deploys-fail-during-peak-crisis-traffic** — the crisis-response is broken.
