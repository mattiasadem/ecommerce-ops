## Common pitfalls (15 from real builds)

1. **Per-acquirer single-cutover approach (no per-acquirer dual-MID parallel-run).** The canonical anti-pattern: the operator decides to migrate from Adyen to Braintree and schedules a single-cutover approach (deactivate Adyen / activate Braintree on Day 1); 2-15% of transactions fail in week 1 due to per-acquirer integration bugs + per-MID decline-rate differences + per-MID 3DS-routing issues + per-MID stored-payment-method migration issues; the operator loses $50K-$200K of revenue in week 1 alone + 4-8 weeks of engineering recovery effort. Per Acquirer Parallel-Run 2025 + Acquirer Parallel-Run 2026 + Acquirer Dual-MID 2025 + Acquirer Dual-MID 2026 + Acquirer Cutover 2025 + Acquirer Cutover 2026 + Stripe Migration 2025 + Adyen Migration 2025 + Braintree Migration 2025 + Worldpay Migration 2025, the per-acquirer dual-MID parallel-run approach (90/10 → 50/50 → 10/90 → 0/100 traffic split over 30-180 days) absorbs the per-acquirer transition failure rate in 1-5% increments and prevents the 2-15% revenue shock. Fix: ALWAYS run the per-acquirer dual-MID parallel-run orchestrator (Component 5) BEFORE the per-acquirer cutover, with the per-acquirer-specific traffic-split ramp and parallel-run duration.

2. **Per-acquirer 90-day deactivation notice (no per-acquirer 60-day rollback feasibility).** The canonical anti-pattern: the operator sends a 90-day deactivation notice to the OLD acquirer per the contract, then tries to roll back to the OLD acquirer 30-60 days post-cutover because the NEW acquirer's approval-rate dropped 10%+; the OLD acquirer's per-MID is already deactivated and the re-activation takes 14-21 days; the operator loses $100K-$300K of revenue during the 14-21 day re-activation window. Per Acquirer Rollback 2025 + Acquirer Rollback 2026 + Acquirer Cutover 2025 + Acquirer Cutover 2026 + Acquirer Dual-MID 2025 + Adyen Migration 2025 + Braintree Migration 2025, the per-acquirer 60-day deactivation notice (instead of 90-day) is the canonical rollback-feasibility lever. Fix: ALWAYS send a 60-day deactivation notice to the OLD acquirer (NOT 90-day) per Component 2 Step 2.1 + Component 6 Step 8, AND pre-position the OLD acquirer's per-MID re-activation request 7-14 days before the per-acquirer cutover.

3. **No per-acquirer post-migration validation (per-MID drift detected 60+ days post-cutover).** The canonical anti-pattern: the operator migrates the per-MID from Adyen to Braintree and considers the migration "done" at the 0/100 cutover; 60+ days post-cutover, the per-MID chargeback-ratio has drifted from 0.6% to 1.2% (Braintree's per-MID CE 3.0 deployment was 60% vs Adyen's 95%, so friendly-fraud chargebacks were not pre-disputed and the per-MID ratio spiked); the per-MID is now in Visa VAMP Excessive + Mastercard ECM CMM + Amex RED Excessive territory. Per Acquirer Post-Migration Validation 2025 + Acquirer Post-Migration Validation 2026 + Acquirer Cutover 2025 + Acquirer Cutover 2026 + Stripe Migration 2025 + Braintree Migration 2025, the per-acquirer post-migration validation must run for 30/60/90/180 days post-cutover, with per-MID per-day monitoring of 10 metrics. Fix: build the per-acquirer post-migration validation (Component 7) BEFORE the per-acquirer cutover, with the 10-metric × 30/60/90/180 day monitoring playbook + the per-acquirer per-MID remediation-plan trigger.

4. **Per-acquirer integration effort underestimated (no per-acquirer integration effort estimator).** The canonical anti-pattern: the operator receives a 4-6 week integration effort estimate from Auth.net, a 6-12 week estimate from Braintree, and a 1-3 week estimate from Stripe; the operator picks Braintree based on Move #167.5.9's per-acquirer RFP verdict and budgets 8-12 weeks × 1 engineer × $80K; the actual integration takes 14-22 weeks × 2 engineers × $200K because the per-acquirer custom-fields + per-acquirer 3DS / CE 3.0 / fraud-rules + per-acquirer webhooks / reconciliation / settlement + per-acquirer recurring-subscription + per-acquirer custom-routing-rules were each underestimated by 50-100%. Per Acquirer Integration Effort 2025 + Acquirer Integration Effort 2026 + Acquirer PSP Replacement 2025 + Acquirer PSP Replacement 2026 + Stripe Migration 2025 + Adyen Migration 2025 + Braintree Migration 2025 + Worldpay Migration 2025, the per-acquirer integration effort estimator (Component 2) must be built BEFORE the per-acquirer RFP verdict is finalized. Fix: ALWAYS build the per-acquirer integration effort estimator (Component 2) with the 7-acquirer × 5-dimension matrix BEFORE finalizing the per-acquirer Move #167.5.9 RFP verdict, AND budget 2× the per-acquirer integration effort estimate to absorb the 50-100% underestimation.

5. **Per-acquirer revenue-at-risk unmodeled (5-25% revenue shock absorbed as surprise).** The canonical anti-pattern: the operator migrates the per-MID from Adyen to Braintree without modeling the per-MID revenue-at-risk during the transition; in week 1, the per-MID approval-rate drops 12% (vs Adyen's per-MID baseline) due to per-acquirer integration bugs + per-MID decline-rate differences; the operator loses $50K-$200K of revenue in week 1 alone, which is 10-40% of the per-MID monthly revenue. Per Acquirer Revenue-at-Risk 2025 + Acquirer Revenue-at-Risk 2026 + Acquirer Switch 2025 + Acquirer Switch 2026 + Acquirer Dual-MID 2025 + Acquirer Dual-MID 2026, the per-acquirer revenue-at-risk is 5-25% of per-MID monthly revenue × 30-90 day transition window. Fix: ALWAYS build the per-acquirer revenue-at-risk calculator (Component 3) with the 7-acquirer × 5-dimension matrix BEFORE the per-acquirer cutover, AND size the per-acquirer dual-MID parallel-run to absorb the per-MID revenue-at-risk.

6. **No per-acquirer dual-MID parallel-run traffic-routing logic on the gateway.** The canonical anti-pattern: the operator runs a per-acquirer dual-MID parallel-run but the gateway traffic-routing logic is hard-coded to route 100% to the OLD acquirer (the per-acquirer traffic-split ramp is set in the acquirer's portal, not in the gateway); the gateway never routes traffic to the NEW acquirer, the parallel-run shows 0% NEW-acquirer traffic, and the operator cannot validate the per-MID per-acquirer integration. Per Acquirer Parallel-Run 2025 + Acquirer Parallel-Run 2026 + Acquirer Dual-MID 2025 + Acquirer Dual-MID 2026, the per-acquirer traffic-routing logic must be in the gateway, not in the acquirer's portal.
