## Common pitfalls (18 from real builds)

**P1 — Don't infer the pillar field from `category` without explicit override.** The canonical Move #N.26 PILLAR CLASSIFIER auto-infers the pillar from `MOVE_RECOMMENDATIONS[i].category` (per the pillar-inference-table above), but a future contributor who adds a new move with `category: ai-customer-service-automation` and forgets to set `pillar: 'retention'` will silently land in the wrong pillar bucket. Fix: emit a `pillarInferred` flag on every move so the operator can spot moves with auto-inferred pillar + add a sentinel regression guard `assertEq(buildCalculatorRoiPortfolio(defaults, []).pillars.length, 4)` + per-pillar-bucket check.

**P2 — Don't hardcode the canonical-mix at 35/30/25/10 — derive it from operator-stage.** The canonical-mix is operator-stage-specific: pre-revenue is 50/20/20/10 / early-stage is 45/30/20/5 / mid-market Path B is 35/30/25/10 / large-DTC Path C is 30/30/25/15 / enterprise Path D is 25/30/30/15 per Kruze DTC Benchmarks 2024. A future operator at $25M GMV should NOT be benchmarked against the $5M GMV canonical-mix. Fix: `getCanonicalPillarMix(operatorStage)` derives the canonical from operator-stage-input.

**P3 — Don't roll up realized-lift + on-the-table-lift into a single `totalLift` without the shipped-mix factor.** The Move #N.7 realized-ROI-ledger ships realized-lift + on-the-table-lift as separate numbers, but Move #N.26's per-pillar rollup rolls them into `totalLift` per pillar. A future contributor who conflates realized + on-the-table into a single `totalLift` without the shipped-mix factor will silently double-count: realized-lift is ALREADY on the books, on-the-table is FUTURE. Fix: emit `shippedLift` + `onTheTableLift` + `totalLift` as 3 separate numbers per pillar.

**P4 — Don't apply the cohort-LTV-multiplier at the MOVE level instead of the PILLAR level.** Move #N.23.1 cohort-aware-projection applies cohort-multiplier per-move based on the move's landing-cohort-mix, but Move #N.26 rolls up at the PILLAR level. The canonical Acquisition-pillar cohort-mix is different from Move #1's landing-cohort-mix (Acquisition-pillar 75% new_visitor + Conversion-pillar 30% new_visitor + Retention-pillar 0% new_visitor). A future contributor who applies per-move multiplier-then-rolls-up will silently under- or over-count per-pillar cohort-LTV. Fix: derive the canonical pillar-cohort-mix from the 7 cohort-bands × 4 pillars = 28 pillar-cohort-mix cells, NOT from per-move.

**P5 — Don't fire portfolio-drift-detection at <3 shipped moves.** Below 3 shipped moves, the chi² portfolio-drift-score has insufficient degrees of freedom (4 pillars × n=2 effective samples = 7 degrees of freedom, but expected counts <5 in ≥2 cells). Fix: defensive gate `if (shipped.length < 3) return { driftIndicator: null, reason: 'insufficient-samples' }`.

**P6 — Don't emit `expectedCascadeDollarImpact` without the per-pillar cascade-strategy.** The cross-pillar-cascade simulator needs to know WHICH pillar-to-pillar cascade fires (Acquisition → Attribution 0.50 strength vs Acquisition → Conversion 0.30 strength vs Acquisition → Retention 0.10 strength) before computing the cascade-dollar-impact. A future contributor who fires all 4×4=16 cascades uniformly will emit $50k/yr cascade for moves that only cascade $5k/yr. Fix: derive the per-cascade-strength from the canonical cross-pillar-dependency-matrix + apply `cascadeDollarImpact = pillarAnnualLiftHigh × cascadeStrength × cohortLTVMultiplier`.

**P7 — Don't use the operator's `monthlyOrders` for retention-pillar projection without cohort-aging-factor.** Retention-pillar moves (Move #8 loyalty, Move #5 subscription-replenishment) compound over multiple years — a $100k/yr Retention projection at $5M GMV is actually $100k × 1.30 × 1.30 = $169k in Year-3 per the cohort-compounding factor. A future contributor who uses raw `$/yr × 12` without cohort-compounding will understate the Retention-pillar 3-year-lifetime-value by 30%. Fix: `cohortCompoundingRate` per pillar (Acquisition 1.10/Conversion 1.08/Retention 1.30/Attribution 1.25) × Number-of-Years (3) for the lifetime projection.

**P8 — Don't emit `recommendedShipNextPillar` without operator-stage context.** The portfolio-drift detector's recommendation should depend on operator-stage + BFCM-cohort-mix-flip: a $5M-GMV operator in Q4 with Retention-drift should ship Acquisition-next (per the 20/30/40/10 row), but a $5M-GMV operator in Q1 with the same Retention-drift should ship Attribution-next (per the 40/35/20/5 row). Fix: `getRecommendedNextPillar(operatorStage, currentPortfolioMix, isBFCMCohortFlip)` with 4 canonical branches.

**P9 — Don't include the `pillar: 'attribution'` moves in the Acquisition-pillar rollup silently.** Move #6 (Triple Whale) is Attribution-pillar but ALSO drives Acquisition-attribution-accuracy — a future contributor who classifies Move #6 as pure-Attribution will under-count the Acquisition-pillar indirect-lift. Fix: emit `cascadedFromAttributionToAcquisition` as a separate row in the per-pillar output so the operator sees BOTH the direct Attribution-pillar $/yr AND the cascaded-into-Acquisition $/yr.

**P10 — Don't wire the per-pillar cohort-LTV-multiplier-table without Triple Whale cohort-band-coverage.** The cohort-LTV-multipliers (high_ltv_active 1.25× / mid_ltv_active 1.0× / low_ltv_active 0.7× / winback_target 0.5× / churned_premium 0.3× / dormant_resurrectable 0.6× / new_visitor 0.85×) require Triple Whale (or Polar / Northbeam) cohort-band-substrate. A future operator without Triple Whale will get a defensive-fallback of `cohortLTVMultiplier = 1.0` (no adjustment). Fix: emit `cohortLTMSubstrateAvailable: bool` flag + defensive-fallback-row with `pillarInferred: true` + warning-message.

**P11 — Don't cross-compare per-pillar `$/yr` from different operator-stages.** A $1M-GMV operator's `$/yr` portfolio (Acquisition $20k / Conversion $15k / Retention $10k / Attribution $3k = $48k total) is NOT comparable to a $25M-GMV operator's `$/yr` portfolio (Acquisition $620k / Conversion $480k / Retention $380k / Attribution $190k = $1.67M total). Fix: emit `perPillarPctOfRevenue` (Acquisition $/yr ÷ Total GMV) so the operator can compare cross-stage.

**P12 — Don't fire `portfolio-drift-auto-rebalance-trigger` on a brand-new operator with 0 shipped moves.** At 0 shipped moves, the portfolio-drift-score is N/A (the canonical portfolio is empty). A future contributor who fires the trigger unconditionally will emit `recommendedShipNextPillar: 'Acquisition'` always — even when the operator explicitly wants to start with Retention (e.g., a subscription-DTC brand). Fix: defensive-gate `if (shipped.length === 0) return { driftIndicator: null, recommendedShipNextPillar: null, reason: 'no-ships-yet' }` + `defaultRecommendedShip: 'first-pillar-from-priority-queue'`.

**P13 — Don't emit `lifetimeValueByPillar.Conversion` without PDP-cohort-validation.** Conversion-pillar moves (Move #9 mobile-PDP / Move #9.5 PDP-A/B / Move #12 PDP-personalization) drive Conversion ONLY when the cohort-mix on the PDP is `mid_ltv_active + high_ltv_active`. A future operator running Move #9 on a 90% new-visitor PDP will see Conversion-lift at $40k/yr but Conversion-cohort-LTV-adjusted at $32k/yr (0.79× new-visitor-mix × $40k = $32k). Fix: emit `pillarCohortRealityCheck: { pillar, expectedCohortMix, actualCohortMix, deltaVsCanonical, recommendation }` per pillar with a warning if `actualCohortMix` is > 30pp off canonical.

**P14 — Don't classify Move #2 (post-purchase-upsell) as Acquisition-pillar — it's Conversion-pillar.** Move #2 fires on the post-purchase page which is `mid_ltv_active + high_ltv_active` cohort (NOT new-visitor) — so it's Conversion-pillar (not Acquisition). A future contributor who classifies Move #2 as Acquisition will inflate Acquisition-pillar $/yr by $80k/yr Path B (Move #2 default = $80k Path B at $5M GMV per Move #2 calculator) — silently biasing the portfolio-drift-detector toward "Acquisition is over-invested". Fix: hardcode the pillar-classifier-table for the 30 wired-and-recommended moves + emit `pillarClassifierOverride` for each.

**P15 — Don't emit `cascadeExpected` as a single number — emit per-pillar cascade breakdown.** A `$80k/yr cascade` from Conversion into Retention is NOT the same as a `$80k/yr cascade` from Conversion into Attribution. Fix: emit `cascadeByPillar: { Acquisition: $X, Conversion: $Y, Retention: $Z, Attribution: $W, total: $X+Y+Z+W }`.

**P16 — Don't apply the Move #N.23.1 cohort-aware-projection at the move-level AND the pillar-level simultaneously.** The move-level cohort-multiplier (Move #N.23.1) and the pillar-level cohort-multiplier (Move #N.26) are TWO different multipliers — applying both compounds them (1.04× pillar × 0.85× new-visitor-mix = 0.88× total = under-projection). Fix: Move #N.26 ROLLS UP the move-level cohort-aware projection from `buildCalculatorRoiRank` (which already applies move-level cohort-multiplier per Move #N.23.1) — the pillar-level cohort-multiplier is applied as a `pillarCoarsenAdjustment` on top of the move-level rollup, NOT as a separate multiplier.

**P17 — Don't fire the portfolio-drift-detector without a 30-day-lookback window.** A freshly-shipped move (e.g., Move #8 loyalty on Day-1) hasn't accumulated enough realized-lift to compute drift.
