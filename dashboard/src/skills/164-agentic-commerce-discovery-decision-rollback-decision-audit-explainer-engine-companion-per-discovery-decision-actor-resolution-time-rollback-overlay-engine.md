## Common pitfalls (18 from real builds)

**Cluster A — per-discovery-decision-actor-resolution-time-rollback-overlay-router + bucket-assignment + decoder-family-router**

1. **Treating rollback-decision-status as a static property of the rollback-engine rather than a streaming signal that drifts per-rollback-execution.** The Pillar B Step 1 rollback-overlay-window-bucket-assignment reads Move #155's `rollback-decision-status` field as if it were a per-rollback cache key. **Fix:** treat `rollback-decision-status` as a per-rollback × per-rollback-execution × per-stream-processing-pipeline streaming signal — emit a `rollback-stage-change` event every time Move #155's rollback-decision-status classifier flips a rollback from `rollback-pending` to `rollback-decided` to `rollback-executed` to `rollback-recovered` to `rollback-archived`; the Pillar B Step 1 bucket-assignment MUST subscribe to this event stream and re-bucket historical events whose rollback-stage shifted within the canonical 24-hour lookback window.

2. **Confusing the canonical `agentic-commerce-rollback-overlay-completeness-score` (0.0–1.0) with the canonical `rollback-decision-status` (5-state discrete).** A rollback-decision with completeness-score=0.74 is NOT necessarily rollback-executed — rollback-stage boundaries are non-linear and per-rollback-execution per Move #155 benchmarks. **Fix:** use Move #155's rollback-stage classifier directly as the Pillar B Step 1 bucket-assignment source; the completeness-score is a SECONDARY signal for the Pillar D industry-benchmark-engine only.

3. **Hardcoding the 5-resolution-time-rollback-overlay-window boundaries to Move #163's 5-resolution-time-versioning-overlay-window SLAs.** The versioning-overlay SLAs (sub-2s / sub-30s / sub-5min / sub-1h / sub-24h) are NOT identical to the rollback-overlay SLAs because rollback-pending rollbacks expect sub-100ms stream-processing latency on synchronous-stream windows. **Fix:** define Move #164's 5-resolution-time-rollback-overlay-window SLAs separately per rollback-pending = sub-2s / rollback-decided = sub-30s / rollback-executed = sub-5min / rollback-recovered = sub-1h / rollback-archived = sub-24h; document the difference in the operator-UX dashboard's `rollback-overlay-vs-versioning-overlay-comparison` widget.

**Cluster B — per-discovery-decision-actor-resolution-time-rollback-overlay-freshness + staleness + backpressure + event-stream-emission**

4. **Window-1 (rollback-pending) freshness-floor regression from sub-2s to sub-5s after a Move #163 router refactor.** **Fix:** add a Move-#164-window-1-freshness-floor-canary that pages the on-call SRE the moment Move-#164's rollback-pending-window freshness-floor exceeds 2s p99 over a 15-minute window; gate any Move #163 router deploy that pushes rollback-pending freshness above 2s p99.

5. **Window-5 (rollback-archived) staleness-violation false-negative because rollback-archived rollbacks emit at most 1 event per 24h.** **Fix:** the staleness-ceiling for window-5 is 24h, but the freshness-emission floor for window-5 MUST be at least 1 event per rollback-decision per 24h; if no event arrives within 24h, emit a synthetic `rollback-archived-staleness-heartbeat` event so the dashboard reflects the rollback-decision's true state.

6. **Backpressure-floor collision between synchronous-stream + change-data-capture-stream pipelines on rollback-pending rollbacks during peak event-storm.** **Fix:** Pillar B Step 2 backpressure computation reads each stream-processing-pipeline's queue-depth-or-rate-limiter-headroom independently and tags each event with `backpressure-source-stream-pipeline`; the canonical backpressure-floor is per-pipeline (queue-depth <100/<1k/<10k/<100k/<1M + rate-limiter-headroom >50%/>40%/>30%/>20%/>10% per window × per pipeline).

7. **Event-stream emission drop on Move-#164 → Move-#163 back-feed when the Move-#163 router is degraded.** **Fix:** the Move-#164 → Move-#163 back-feed event stream is a SEPARATE Kafka topic (`rollback-overlay-resolution-time-pressure-v1`); if Move-#163's main event-stream topic degrades, Move-#164 still emits to the back-feed topic and Move-#163 still receives per-resolution-time-rollback-overlay-pressure updates.

**Cluster C — per-discovery-decision-actor-resolution-time-rollback-overlay-fairness + coverage + versioning + decomposition**

8. **Anti-monopoly-floor violation when one rollback-decision-status dominates a rollback-pending window (e.g. a single `rollback-pending` rollback-decision = 60% of rollback-pending events).** **Fix:** the anti-monopoly-floor per-resolution-time-rollback-overlay-window × per-discovery-decision-actor-id is per-discovery-decoder-family, NOT per-rollback-decision-status; if a single rollback-decision-status >40% of a per-window × per-decoder-family bucket, split the rollback-decision's events across multiple `discovery-decision-actor-id` partitions and surface a `rollback-decision-status-monopoly-warning` chip on the operator-UX dashboard.

9. **Coverage-benchmark false-positive when Move-#155 `rollback-decision-status` field is absent on legacy rollback-decisions (pre-2026 rollback-engines).** **Fix:** Pillar C decomposition decoder-set falls back to the canonical UCP/ACP-rollback-overlay-window-2026 stage classifier when Move-#155 field is absent; the operator-UX dashboard surfaces a `coverage-source-mix` widget showing the % of events from Move-#155 vs UCP/ACP-rollback-overlay-window-2026 per window.

10. **Move-#164 → Move-#163 → ... → Move-#123 version-lineage drift when a Move-#155 schema-field is renamed (e.g. `rollback-decision-status` → `active-rollback-stage`).** **Fix:** Move-#164 rollback-overlay-watcher subscribes to Move-#155's schema-event-stream and re-emits historical events under BOTH the old AND new field names for the canonical 7-day migration window; the operator-UX dashboard surfaces a `rollback-overlay-drift-warning` chip whenever Move-#164 ingests a Move-#155 schema-rename event.

11. **Rollback-overlay-window × per-versioning-overlay decomposition mis-classification when a rollback-decision's `rollback-decision-status` and `version-status` are computed by different upstream signals (Move-#155 vs Move-#163).** **Fix:** Pillar C decomposition decoder-set reads the canonical `agentic-commerce-rollback-overlay-completeness-score` and the canonical `versioning-overlay-completeness-score` as cross-validation; surface a `cross-validation-mismatch-warning` chip when the two signals disagree by >0.20 completeness-score.

**Cluster D — per-discovery-decision-actor-resolution-time-rollback-overlay-cohort + merchant-impact + rollback-decision-audit + decomposition-deep**

12. **Cohort-impact false-positive when a rollback-pending rollback-decision's events dominate the per-cohort aggregation.** **Fix:** Pillar B Step 3 aggregation-rollup is per-cohort × per-channel × per-rollback-decision-status; if a single rollback-pending rollback-decision >30% of per-cohort events, surface a `cohort-impact-rollback-decision-monopoly` chip on the operator-UX dashboard.

13. **Merchant-impact regression when a rollback-stage shift (rollback-pending → rollback-decided) is treated as merchant-impact-positive rather than merchant-impact-negative.** **Fix:** the merchant-impact direction depends on the rollback-stage direction: rollback-pending → rollback-decided is merchant-impact-negative (decision made to revert, suggests earlier regression); rollback-decided → rollback-executed is merchant-impact-negative (rewind in flight); rollback-executed → rollback-recovered is merchant-impact-positive (rewind succeeded); the operator-UX dashboard's merchant-impact widget MUST classify shifts by direction and surface both directions.

14. **Rollback-decision-audit false-positive when the per-resolution-time-rollback-overlay-window freshness-floor regression is mis-classified as a rollback-trigger.** **Fix:** the canonical rollback-decision-audit-engine ONLY fires a rollback-decision when (a) freshness-floor regression >2× SLA for >15min AND (b) the merchant-impact direction is negative AND (c) the per-rollback-window decision is `rollback-now`; emit a `rollback-decision-audit-no-op` chip otherwise.

15. **Rollback-overlay-decomposition-deep (Pillar C sub-decomposition (e)) over-emission when per-failure-mode granularity explodes (12 canonical discovery-failure-modes × 5 rollback-decision-status × 5 windows × 12 rollback-windows × 5-stream-processing-pipelines = 18,000 cells).** **Fix:** Pillar C decomposition decoder-set emits at most 1 cell per (per-resolution-time-rollback-overlay-window × per-failure-mode × per-stream-processing-pipeline); cells where the event-count <10 within the canonical 7-day window are aggregated to `failure-mode-stream-pipeline-cluster` for the operator-UX dashboard.

**Cluster E — per-discovery-decision-actor-resolution-time-rollback-overlay-recovery-decoder-decision + rollback-window-decision + cohort-impact-decomposition + event-stream-auto-feeding-back**

16. **Recovery-decoder-decision mis-fires when the canonical 5-window rollback-window-decision is `rollback-now` but the per-cohort-impact is positive.** **Fix:** the canonical recovery-decoder-decision is `rollback-now + cohort-impact-positive = rollback-defer`; only `rollback-now + cohort-impact-negative` actually fires a rollback-decision; surface a `recovery-decoder-decision-deferred` chip on the operator-UX dashboard.

17. **Rollback-window-decision collision when a rollback-stage shift (rollback-decided → rollback-executed) within the canonical 1-hour window collides with a Move-#163 rollback-window-decision.** **Fix:** Move-#164's rollback-window-decision takes precedence over Move-#163's when the rollback-stage shift is the proximate cause; otherwise Move-#163 takes precedence; the operator-UX dashboard surfaces a `rollback-window-decision-source` chip showing which engine fired the decision.

18. **Event-stream-auto-feeding-back-loop-broken when Move-#155's `rollback-decision-status` field is dropped (Move-#155 schema evolution).** **Fix:** Pillar F back-feed emits BOTH a `rollback-decision-status-change` event AND a `rollback-overlay-resolution-time-pressure-change` event on every rollback-stage shift; if Move-#155 drops the rollback-stage field, the back-feed still surfaces the rollback-overlay-pressure event with `rollback-decision-status-source: legacy-v1` so Move-#155 can fall back to the canonical UCP/ACP-rollback-overlay-window-2026 stage classifier.
