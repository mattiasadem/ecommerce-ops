# Cross-platform MID-orchestrator — per-MID dispute ratio + per-platform 3DS coverage + per-platform CE 3.0 evidence composer + cross-platform 10.4 dispute correlation (Move #167.5)

> A best-in-class **Cross-platform MID-orchestrator** closes the canonical "we sell on Shopify + Amazon + eBay + Walmart + TikTok Shop, our 3DS coverage is 80% blended but only 65% on TikTok Shop + our 10.4 dispute rate is 0.4% blended but 0.7% on Walmart + our VAMP ratio is computed at the merchant-level but Visa VAMP is at the per-ACQUIRER-portfolio level — and we have 5 separate acquirer relationships" gap. Per Visa VAMP 2025 + Visa CE 3.0 2025 + Mastercard ECM 2025 + Adyen Multi-MID 2025 + Amazon Pay Dispute 2025 + eBay Managed Payments 2025 + Walmart Marketplace Payments 2025 + TikTok Shop Seller 2025, every sales channel has its own MID, its own 3DS coverage, its own dispute-processing rules, its own CE 3.0 evidence-pack composer constraints, and its own acquirer-relationship — a merchant-level "blended" view of chargeback management hides per-platform liability-shift failures and per-platform MATCH-list risk. The Move #167.1 CE 3.0 evidence composer + Move #167.2 Account Updater audit + Move #167.3 per-network fee-modeling + Move #167.4 3DS-frictionless fallback all treat the merchant as a single entity; this layer decomposes the merchant into per-MID + per-platform + per-acquirer operations, computes the per-platform 10.4 dispute rate + per-platform 3DS coverage + per-platform CE 3.0 evidence-eligibility independently, correlates 10.4 disputes across platforms to catch repeat-offender cardholders, models the per-MID VAMP-ratio contribution, and projects the cross-platform liability-shift ledger (3DS shifted liability on Shopify but not on TikTok Shop; CE 3.0 applies on Shopify + Amazon but not on Walmart — the per-platform matrix is non-uniform). At default $1M-$5M GMV split across 4-5 platforms with 0.3-0.6% blended dispute ratio but 0.6-1.2% on the worst platform, the orchestrator projects **15-30% reduction in 10.4 dispute volume on the worst platform** + **0.05-0.15pp VAMP-ratio drop on the worst MID** + **$10k-$50k/year of additional dispute recovery** + **$5k-$25k/year of VAMP fine avoidance** + **per-MID MATCH-list risk detection 4-6 months earlier than the merchant-level view**. **Year-1 ROI 4:1-12:1** at the default $1M-$5M GMV; payback in 6-10 weeks once a per-MID-vs-merchant discrepancy is detected. Closes the gap between "we're on 5 platforms" (a sales achievement) and "we're on 5 platforms with per-platform dispute compliance" (a program).

## When to use this skill

Use this skill the first time any of these is true:

- the operator is **selling on 2+ platforms** (Shopify + Amazon + eBay + Walmart + TikTok Shop + Etsy + Target Plus + etc.) AND is **NOT running per-MID dispute ratio tracking** (the canonical "we sell on Shopify + Amazon + eBay but our chargeback dashboard shows a 'blended' 0.4% rate — Amazon's actual rate is 0.7% (worse than merchant-level), Shopify's is 0.3% (better), eBay's is 0.9% (way worse, hiding behind the blend) — VAMP is per-acquirer-portfolio, not per-merchant" anti-pattern per Visa VAMP 2025 + Mastercard ECM 2025 + Adyen Multi-MID 2025 + Amazon Pay Dispute 2025 + eBay Managed Payments 2025);
- the operator has **shipped Move #167 (chargeback management) + Move #167.1 (CE 3.0 evidence-pack automation) + Move #167.2 (Account Updater audit) + Move #167.3 (per-network fee-modeling) + Move #167.4 (3DS-frictionless fallback)** at Tier-1 AND is **NOT decomposing the chargeback-management flow into per-MID operations** (the canonical "our CE 3.0 composer is shipping blended evidence packs to all 5 platforms, but Amazon's CE 3.0 program uses different field names + Walmart's 3DS-frictionless fallback requires the 3DS data as 4-dim support + eBay's dispute window is 60 days not 120 — the blended composer silently fails on 30-40% of disputes per platform" anti-pattern per Amazon Pay Dispute 2025 + Walmart Marketplace Payments 2025 + eBay Managed Payments 2025 + TikTok Shop Seller 2025);

## What "best in class" looks like

A best-in-class Cross-platform MID-orchestrator has **EIGHT mutually-reinforcing components** running in parallel. Every component has a 2024-2026 network-published + per-row benchmark + verification gate.

**Component 1: Per-platform MID registry + acquirer-relationship ledger.** The registry maps every sales platform to its (a) acquirer, (b) MID (or platform-issued payment-ID), (c) chargeback-processing email/portal, (d) CE 3.0 program-version supported, (e) 3DS coverage baseline, (f) dispute window, (g) MATCH-list threshold applicable, (h) acquirer pass-through multiplier. The ledger is the SINGLE source of truth for "what MID does this chargeback belong to" — without it, every downstream component fails silently. Per Visa VAMP 2025 + Mastercard ECM 2025 + Adyen Multi-MID 2025 + Amazon Pay 2025 + eBay Managed Payments 2025 + Walmart Marketplace Payments 2025 + TikTok Shop Seller 2025, the per-platform MID structure is NOT a single merchant-ID; each platform issues its own payment-ID (or routes to its acquirer-issued MID) and the dispute data warehouse must key on the per-platform MID, not the per-merchant brand.

**Component 2: Per-platform dispute data warehouse + per-MID ratio dashboard.** The warehouse ingests per-platform dispute feeds (Shopify Disputes API + Amazon Pay Chargeback API + eBay SNR API + Walmart Disputes API + TikTok Shop Seller Center + Etsy Payments + Stripe Chargebacks API + Adyen Disputes API + Braintree Disputes API) and computes per-MID dispute ratio = (10.4 + 13.1 + 11.3 + 12.6 + others) ÷ (per-MID Placed Order count). The dashboard shows the per-MID ratio AND the per-MID ratio's contribution to the merchant-level blended ratio. The per-MID ratio is the RIGHT unit of analysis for VAMP / ECM / RED / DMP — Visa's 1.5% threshold is per-ACQUIRER-portfolio, not per-merchant.

**Component 3: Per-platform 3DS coverage + frictionless-rate dashboard.** The dashboard tracks 3DS coverage = (3DS-authenticated ÷ total 3DS-eligible) PER platform AND per-platform 3DS-frictionless-rate = (frictionless_performed ÷ 3DS-authenticated) per platform. Per Visa 3DS 2024 + EMVCo 3DS 2024 + Shopify 3DS 2025 + Amazon Pay 3DS 2025 + TikTok Shop 3DS 2025, 3DS coverage varies 30-50pp across platforms (Shopify 75-85% / Amazon Pay 65-80% / TikTok Shop 45-65% / Walmart 55-70% / eBay 55-75%) — a merchant-level "we're at 75% 3DS" hides the 45-65% on TikTok Shop that is causing the high dispute rate. The dashboard is the input to Component 4 (3DS tuning) + Component 5 (CE 3.0 eligibility).

**Component 4: Per-platform 3DS challenge-vs-frictionless tuning.** For each platform, the tuning system adjusts the 3DS challenge threshold (when to escalate frictionless → challenge) based on (a) the platform's baseline 3DS coverage, (b) the platform's per-issuer frictionless-acceptance rate (per Move #167.4 Component 4), (c) the platform's per-MID VAMP-ratio contribution. The tuning uses each platform's NATIVE 3DS tool (Stripe Radar 3DS for Shopify / Amazon Pay 3DS for Amazon Pay / Adyen Dynamic 3D Secure for TikTok Shop / eBay 3DS for eBay / Walmart 3DS for Walmart) — a single "tune 3DS once" is the canonical P2 anti-pattern. Per Stripe Radar 3DS Rules 2025 + Adyen Dynamic 3D Secure 2025 + Amazon Pay 3DS 2025 + TikTok Shop 3DS 2025 + eBay 3DS 2025, per-platform 3DS tuning can shift 3DS coverage by 10-25pp and 10.4 dispute rate by 0.1-0.3pp.

**Component 5: Per-platform CE 3.0 evidence composer with platform-specific eligibility.** For each platform, the composer first checks (a) is the platform's acquirer in the CE 3.0 program (Visa CE 3.0 covers Visa chargebacks from Visa-network acquirers; Amazon Pay has its own internal CE 3.0 mirror; Walmart has its own; eBay has its own), (b) does the merchant meet the per-platform CE 3.0 prerequisites (75+ prior transactions + 65%+ 3DS coverage + 3DS 2.2+ support), (c) does the 3DS data field set match the per-platform's expected fields (e.g., Amazon Pay uses different field names; Walmart uses different dispute-reason codes), (d) does the dispute-reason-code map to the per-platform's CE 3.0 reason (CE 3.0 covers 10.4 + 13.1 + 12.6, but each platform has its own sub-codes). A blended composer fails silently on 30-50% of disputes per platform.

**Component 6: Cross-platform 10.4 dispute correlation + repeat-offender cardholder detection.** The orchestrator correlates 10.4 disputes ACROSS platforms by (a) cardholder email (when available), (b) cardholder billing-address hash, (c) card BIN (first 6 digits of the card number), (d) device fingerprint (when the platform exposes it), (e) IP address (when the platform exposes it). The correlation surfaces repeat-offender cardholders who file 10.4 on multiple platforms within a 12-month window — these are the canonical "serial friendly-fraud" cohort that justifies per-cardholder suppression + per-platform block-listing. Per Visa 2025 Global Ecommerce Payments Fraud Report + Chargebacks911 Multi-MID 2025 + Redress Multi-MID 2025 + Datos Insights 2026, 8-15% of friendly-fraud 10.4 disputes come from repeat-offender cardholders who file on 2+ platforms; without cross-platform correlation, these repeat-offenders are invisible to each platform's individual anti-fraud system.

**Component 7: Per-MID MATCH-list risk calculator + cross-platform VAMP-ratio model.** For each platform-acquirer combination, the calculator computes (a) the per-MID dispute ratio, (b) the per-MID chargeback volume, (c) the per-MID MATCH-list threshold applicable (Mastercard HECM at 3.0%+ + 300+ cb/mo; Visa at 1.5%+; Amex RED at 1.0%+; Discover DMP at 1.0%+), (d) the per-MID 90-day forward projection (if current ratio trend continues), (e) the per-acquirer-portfolio's prior history (some acquirers are stricter than others). The output is a per-MID MATCH-risk score 0-100 + a per-MID VAMP/ECM/RED/DMP warning-status flag. The per-MID model is the RIGHT unit of analysis; merchant-level blended hides the worst MID.

**Component 8: Per-platform dispute-cost ledger + cross-platform liability-shift ledger.** The ledger tracks (a) per-platform gross dispute volume + per-platform win-rate + per-platform recovery-amount, (b) per-platform acquirer pass-through (the 1.0x-2.5x multiplier on the network fine), (c) per-platform reserve-requirement impact (some acquirers increase reserve on a MATCH-warning MID), (d) cross-platform liability-shift ledger (3DS shifted liability on platform A but not on platform B; CE 3.0 applies on platform A but not on platform B). The ledger surfaces the per-platform economics of chargeback management and is the input to Move #167.3's per-network fee-modeling layer (which then ranks the ROI of each mitigation per platform).

## The build (time estimate: 5-7 days for the full 8-component orchestrator)

### Phase 1: Per-platform MID registry + acquirer-relationship ledger (4-6 hours)

- **Step 1.1** — Build a per-platform MID registry spreadsheet (or DB) with columns: platform, acquirer, MID format, chargeback-processing email/portal, CE 3.0 program-version, 3DS coverage baseline, dispute window, MATCH-list threshold, acquirer pass-through multiplier. Pull from each platform's seller-center documentation. **Time: 2-3h.**
- **Step 1.2** — Set up per-platform dispute data ingestion: Shopify Disputes API + Amazon Pay Chargeback API + eBay SNR API + Walmart Disputes API + TikTok Shop Seller Center + Etsy Payments + Stripe Chargebacks API + Adyen Disputes API + Braintree Disputes API. Each platform has a different API; build a normalized dispute-record schema (platform, MID, dispute_id, reason_code, amount, cardholder_hash, transaction_timestamp, dispute_status, evidence_due_date). **Time: 2-3h.**

### Phase 2: Per-platform dispute data warehouse + per-MID ratio dashboard (6-8 hours)

- **Step 2.1** — Build a per-MID dispute data warehouse (BigQuery / Snowflake / Postgres) keyed on (platform, MID, date). Each row = (platform, MID, date, Placed_Order_count, Placed_Order_GMV, dispute_count_by_reason, dispute_amount_by_reason). **Time: 3-4h.**
- **Step 2.2** — Build a per-MID ratio dashboard (Looker / Mode / Metabase / custom React) showing: per-MID dispute ratio (10.4 + 13.1 + 11.3 + 12.6) / Placed_Order_count, per-MID ratio contribution to blended, per-MID ratio vs Visa VAMP threshold (1.5%) + Mastercard ECM threshold (1.5%) + Amex RED threshold (1.0%) + Discover DMP threshold (1.0%), per-MID 90-day forward projection. **Time: 3-4h.**

- **Step 4.1** — For each platform, configure the NATIVE 3DS tool (Stripe Radar 3DS / Adyen Dynamic 3D Secure / Amazon Pay 3DS / TikTok Shop 3DS / Walmart 3DS / eBay 3DS) with platform-specific challenge thresholds. Higher challenge-rate on high-dispute platforms (Walmart, TikTok Shop) + lower challenge-rate on low-dispute platforms (Shopify). **Time: 2-3h.**

## Common pitfalls (15 from real cross-platform MID-orchestrator builds)

1. **Treating the merchant as a single entity** — the canonical P1 anti-pattern. The merchant's blended dispute ratio HIDES the worst MID's ratio. If the blended is 1.1% (below 1.5% VAMP threshold) but the worst MID is 1.7% (above threshold), the worst MID gets the fine, not the merchant. The orchestrator's FIRST job is to surface per-MID ratios. (Source: Visa VAMP Fact Sheet 2025 + Mastercard ECM Merchant 2025 + Adyen Multi-MID 2025 + Chargebacks911 Multi-MID 2025 + Redress Multi-MID 2025.)
2. **Single CE 3.0 composer for all platforms** — the canonical P2 anti-pattern. Each platform has its own CE 3.0 program (or no CE 3.0 program — Walmart has its own internal evidence program; Amazon Pay has its own internal mirror). A single composer that ships blended evidence packs will fail silently on 30-50% of disputes per platform because the field names, reason codes, and dispute windows differ. (Source: Visa CE 3.0 Merchant Readiness 2025 + Amazon Pay Dispute 2025 + Walmart Marketplace Payments 2025 + eBay Managed Payments 2025 + Chargeflow CE3 2025 + Justt CE3 2025.)
3. **Single 3DS tuning for all platforms** — the canonical P3 anti-pattern. Stripe Radar 3DS, Adyen Dynamic 3D Secure, Amazon Pay 3DS, TikTok Shop 3DS, Walmart 3DS, and eBay 3DS each have different challenge-vs-frictionless tuning mechanisms. A "tune 3DS once" assumes the same 3DS data source on all platforms; in reality, each platform has its own 3DS data store and its own challenge-threshold configuration. (Source: Stripe Radar 3DS Rules 2025 + Adyen Dynamic 3D Secure 2025 + Amazon Pay 3DS 2025 + TikTok Shop 3DS 2025 + Walmart 3DS 2025 + eBay 3DS 2025.)
4. **Not correlating 10.4 disputes across platforms** — the canonical P4 anti-pattern. The same cardholder who files 10.4 on Shopify (Apr) + Amazon (Jun) + Walmart (Aug) is a serial friendly-fraud offender, but the merchant-level dashboard shows three different "customers." Without cross-platform correlation, the repeat-offender cohort (8-15% of friendly-fraud disputes) is invisible and the per-platform anti-fraud systems don't share data. (Source: Visa 2025 Global Ecommerce Payments Fraud Report + Chargebacks911 Multi-MID 2025 + Redress Multi-MID 2025 + Datos Insights 2026 + Juniper Research Friendly Fraud 2026.)
5. **Blended MATCH-list risk** — the canonical P5 anti-pattern. MATCH-list is per-ACQUIRER-portfolio, not per-merchant. If the merchant has 5 acquirer relationships (5 MIDs) and ONE of them is at HECM threshold (3.0%+ + 300+ cb/mo), that ONE MID gets MATCH-listed and the merchant loses the ability to process on that platform. The blended "we're at 1.5% across 5 platforms" hides the 3.0%+ on the worst platform. (Source: Mastercard MATCH Pro 2025 + Visa MATCH 2024 + Redress Compliance 2025 + Redress MATCH Removal 2025 + Acquirer Portfolio 2025.)
6. **Ignoring per-platform dispute windows** — the canonical P6 anti-pattern. CE 3.0's 120-day vintage window assumes Visa's standard 120-day dispute window, but Amazon Pay's dispute window is 60 days, eBay's is 60 days, Walmart's is 90 days, TikTok Shop's is 30-90 days. A composer that uses the 120-day window for Amazon Pay disputes will miss the 60-day evidence-due date and lose by default. The composer MUST respect the SHORTER per-platform window. (Source: Amazon Pay Dispute 2025 + eBay SNR 2025 + Walmart Dispute 2025 + TikTok Shop Dispute 2025 + Visa CE 3.0 2025.)
7. **Treating Amazon Pay / eBay / Walmart MATCH absorption as total** — the canonical P7 anti-pattern. Amazon Pay, eBay, and Walmart DO absorb MATCH-list risk for their issued MIDs, but they ALSO enforce their own internal dispute ratio thresholds (e.g., Amazon's Account Health requires <1.0% ODR; eBay's seller performance requires <0.5% defect rate; Walmart's seller scorecard requires <1.5% dispute rate). A merchant on these platforms can lose the selling PRIVILEGE even without a MATCH-listing. (Source: Amazon Pay 2025 + Amazon Seller Central Dispute 2025 + eBay Managed Payments 2025 + eBay SNR 2025 + Walmart Marketplace Payments 2025 + Walmart Dispute 2025 + Etsy Payments 2025.)
8. **Treating per-MID VAMP-ratio contribution as additive** — the canonical P8 anti-pattern. Visa VAMP is per-ACQUIRER-portfolio, not the sum of per-MID ratios. If 3 MIDs are on the same acquirer (e.g., 3 Shopify stores all on Stripe), the acquirer-portfolio ratio is the sum-weighted average, not the per-MID. The orchestrator must compute the per-ACQUIRER-portfolio ratio, not just per-MID, and recognize that MIDs on the same acquirer can SAVE each other (one good MID can offset one bad MID on the same acquirer). (Source: Visa VAMP Fact Sheet 2025 + Mastercard ECM 2025 + Adyen Multi-MID 2025 + Braintree 2025 + Acquirer Portfolio 2025.)
9. **No per-platform Account Updater audit** — the canonical P9 anti-pattern. Move #167.2 (Account Updater audit) covers the merchant-level Account Updater wiring (Shopify DTC + Stripe), but each marketplace (Amazon Pay + eBay + Walmart + TikTok Shop + Etsy) has its own Account Updater mechanism for subscription/membership renewals. A merchant with subscriptions on Shopify + Amazon Subscribe & Save + Walmart Auto-Ship + TikTok Shop must audit Account Updater on EACH platform independently. (Source: Visa Account Updater 2025 + Mastercard Automatic Billing Updater 2025 + Amazon Subscribe & Save 2025 + Walmart Auto-Ship 2025 + Etsy Payments 2025 + Stripe Account Updater 2025.)
10. **Assuming per-platform 3DS data is in the same field set** — the canonical P10 anti-pattern. EMVCo 3DS 2.3.0 defines a canonical field set (ds_trans_id + three_ds_server_trans_id + authentication_value + authentication_timestamp + message_category + transaction_status), but Amazon Pay + Walmart + TikTok Shop + eBay each store these fields in platform-specific locations. A Move #167.4 3DS-frictionless-fallback composer that reads `payment_intent.payment_method_options.card.three_d_secure_usage` (Stripe-native) will fail silently on Amazon Pay + Walmart + TikTok Shop + eBay. (Source: EMVCo 3DS Data Fields 2024 + EMVCo 3DS Merchant Data 2024 + Visa 3DS Authentication Data 2024 + Amazon Pay 3DS 2025 + Walmart 3DS 2025 + TikTok Shop 3DS 2025 + eBay 3DS 2025.)
11. **Single acquirer pass-through multiplier** — the canonical P11 anti-pattern. Each acquirer has a different pass-through multiplier (Stripe $8/VAMP-Count / Adyen $11/VAMP-Count / Braintree $8-$10/VAMP-Count / Auth.net $9/VAMP-Count). The Move #167.3 per-network fee-modeling uses a 1.0x-2.5x range, but the per-MID pass-through is per-ACQUIRER, not per-network. The orchestrator must model per-acquirer pass-through, not per-network. (Source: Braintree 2025 + Adyen Multi-MID 2025 + Acquirer Pass-Through 2025 + Redress Acquirer 2025 + Chargeflow Acquirer 2025.)
12. **Not modeling per-platform reserve-requirement impact** — the canonical P12 anti-pattern. A MATCH-warning MID triggers an acquirer reserve increase (typically 5-15% of monthly volume × 6-12 months). The reserve impact is per-ACQUIRER, not per-merchant, and a merchant with a Shopify-Stripe MATCH-warning can see a $50k-$200k reserve held by Stripe even if Shopify-Stripe is only 30% of the merchant's volume. (Source: Acquirer Reserve 2025 + Visa VAMP 2025 + Mastercard MATCH Pro 2025 + Acquirer Portfolio 2025 + Redress Compliance 2025.)
13. **Cross-platform 10.4 correlation without cardholder consent / privacy** — the canonical P13 anti-pattern. Cross-platform cardholder correlation requires hashing cardholder PII (email + billing-address + device-fingerprint) and storing the hash across platforms. Some platforms' ToS prohibit cross-platform PII storage (especially EU under GDPR). The orchestrator must use one-way hash + per-platform opt-in flag for cross-platform correlation. (Source: GDPR 2025 + Visa 2025 Global Ecommerce Payments Fraud Report + Mastercard Identity Check 2024 + Datos Insights 2026 + EU PSD2 2025.)
14. **Per-platform CE 3.0 without per-platform 3DS-data extractor** — the canonical P14 anti-pattern. Move #167.1's CE 3.0 composer expects the canonical EMVCo 3DS 2.3.0 field set, but per-platform 3DS data is in platform-specific locations. The composer must call a per-platform 3DS-data extractor FIRST (Component 5 prerequisite) before composing CE 3.0 evidence. Without the per-platform extractor, the composer fails silently on 30-50% of disputes per platform. (Source: Visa CE 3.0 Data Fields 2025 + EMVCo 3DS Data Fields 2024 + EMVCo 3DS Merchant Data 2024 + Amazon Pay 3DS 2025 + Walmart 3DS 2025 + TikTok Shop 3DS 2025 + Chargeflow CE3 2025 + Justt CE3 2025.)
15. **Per-MID optimization without cross-platform liability-shift ledger** — the canonical P15 anti-pattern. Optimizing each MID in isolation can SHIFT disputes across platforms (e.g., tighter 3DS on Shopify pushes customers to Amazon Pay, where the 3DS is less strict and the dispute rate is higher). The orchestrator must maintain a cross-platform liability-shift ledger to detect and prevent platform-shifting regressions. (Source: Visa 3DS 2024 + EMVCo 3DS 2024 + Chargeflow 3DS Frictionless 2025 + Justt 3DS Fallback 2025 + Datos Insights 2026 + Cross-Border 3DS 2025 + Multi-Platform Merchant 2025 + Omnichannel Chargeback 2025.)
