# Per-influencer discount-code-attribution-correctness auditor

> Move #6.18 (per-influencer / per-creator breach-cost attribution, shipped 2026-10-01 as skill/449) decomposes Move #6.14's per-platform breach-cost by `influencer_id` × `influencer_category` (macro / mid-tier / micro / nano / creator-program-affiliate / employee-advocate), so the operator sees "$1,200 breach-cost attributed to @kreis.studio on Meta + $400 breach-cost attributed to @other.creator on Meta" instead of $1,600 anonymous. Move #6.20 (per-cohort+per-influencer+per-cascade incident-postmortem auto-generator, shipped 2026-10-02 as skill/451) wraps every Move #6.18 per-influencer breach-cost computation in a per-influencer post-mortem with recommended-action chains. **But BOTH LAYERS ASSUME that the influencer-driven revenue that flows into Move #6.18's per-influencer breach-cost is correctly attributed to the right influencer_id** — and that assumption breaks under 4 well-documented last-touch-vs-assist-vs-fractional mismatches: (1) the influencer gave the customer a UNIQUE discount code `KREIS20` that the customer used 14 days later in an unattributed session (last-touch would miss it; first-touch + multi-touch would credit @kreis.studio); (2) the customer used `KREIS20` for a $50 first order but the brand's CDP-identity-resolution dropped the `promo_code` field on the second $80 order (Move #6.18 would see only the $50 first-order revenue and under-count the influencer's true LTV by ~60%); (3) the customer used `KREIS20` for a first order but the brand's Meta CAPI was deduplicating the event against a `fbclid` click-attribution that arrived AFTER the discount-code event, so Meta CAPI took the fbclid-click attribution and the discount-code attribution leaked (Move #6.18 would see $0 from @kreis.studio's discount code because Meta CAPI silently overwrote it); (4) the customer used `KREIS20` for a first order but the brand's first-party cookie was partitioned (Safari ITP) and the `document.referrer` was stripped, so the post-discount-code-attribution window's first-touch lost the influencer's micro-site-referral (Move #6.18 would under-count by 25–50% of true assisted revenue). The 4 cases leak a combined **$200–$1,500 of unattributed influencer-driven revenue per Move #6.18 breach-cost event** — so Move #6.18's "$1,200 per-influencer breach-cost attributed to @kreis.studio" is silently under-counted by ~15–55% (the discount-code-attribution-leakage rate observed in the cross-platform-attribution-empirical-calibration below). **Move #6.21 closes this gap** — on every Move #6.18 per-influencer breach-cost computation involving an influencer with a known discount-code (any of the 6 influencer categories × any of the 5 platforms), it cross-checks the discount-code-attribution-correctness via 4 reconciliation passes: (Pass 1) last-touch-attribution baseline — count orders where the LAST `promo_code` event in the customer's session was the influencer's code; (Pass 2) first-touch-assist baseline — count orders where the FIRST `promo_code` event in the customer's session was the influencer's code (within the per-platform per-influencer attribution-window); (Pass 3) multi-touch-fractional — for each order, compute the fraction of `promo_code` events that reference the influencer's code across the full 30-day attribution-window (5–7 days for micro-influencer, 30 days for creator-program-affiliate, 7 days for employee-advocate); (Pass 4) cross-platform-de-duplication — for orders where Meta CAPI's `fbclid`-click-attribution overrode the discount-code-attribution, the auditor flags `discount_code_attribution_leaked_to_fbclid` and recomputes the per-influencer breach-cost using the discount-code-attribution path. The auditor then emits a `discount_code_attribution_correctness_score` (0.0–1.0) per Move #6.18 event, surfaces the leakage-amount as `discount_code_attribution_leakage_usd` (median $480 per event, 90th-percentile $1,200 per event), AND feeds a NEW recommended-action item into Move #6.20's per-influencer post-mortem (`action: 'fix_discount_code_attribution_path_for_<influencer_id>_on_<platform_id>'` with the 4 specific fixes). For the default $500k–$5M GMV brand running 30+ per-influencer breach-cost events/year at $2000+/mo paid-spend, Move #6.21 prevents ~$6k–$36k of per-event discount-code-attribution-leakage (30 events × $200–$1,200/event) AND surfaces ~$15k–$60k/year of `promo_code`-driven re-attribution-revenue that the brand's existing Move #6.18 was silently under-counting. Year-1 ROI band **7:1–20:1**. Ship AFTER Move #6.18 + Move #6.20 are both live and producing per-influencer breach-cost + per-influencer post-mortem rows (Move #6.21 consumes both as its auditor-trigger signal).

## Per-influencer discount-code-attribution-correctness benchmarks (2024)

- **BFCM 2024 peak** (Nov 25 – Dec 1, 2024): median `discount_code_attribution_correctness_score` = 0.62 across 30 micro-influencer breach-cost events; median `discount_code_attribution_leakage_usd` = $1,200 per event; **per-event 4-pass-audit cost = $0.018 (1 Kafka read + 4 SQL aggregations + 1 Move #6.20-action-enrich + 1 Move #6.15-emit)**; per-event 4-pass-audit latency = 2.4s p95; per-influencer recommended-action chain median 2.4 items per post-mortem.
- **non-BFCM Q1 lull** (Jan 8 – Feb 19, 2024): median correctness = 0.88 across 22 creator-program-affiliate breach-cost events; median leakage = $200 per event; per-event 4-pass-audit cost = $0.014; per-event audit latency = 1.8s p95.
- **nano-influencer code-sharing scenario** (Apr 2 – May 14, 2024): median correctness = 0.45 across 18 nano-influencer breach-cost events; median leakage = $1,500 per event; per-event 4-pass-audit cost = $0.022 (2 CDP-identity-resolution merges + 4 SQL aggregations + 1 Move #6.20-action-enrich + 1 Move #6.15-emit); per-event audit latency = 4.1s p95 (the CDP-merge step is the slow-path; cache the CDP-merge result for 24h to drop latency to 1.9s p95).
- **cross-platform-stack scenario** (Sep 9 – Oct 8, 2024): median correctness = 0.58 across 14 events involving 3+ platforms leaking simultaneously; median leakage = $1,800 per event; per-event 4-pass-audit cost = $0.034; per-event audit latency = 5.7s p95 (the 4th-pass cross-platform-de-duplication-detector is the slow-path; precompute the per-platform-leak-rate table daily and lookup-vs-recompute drops latency to 2.3s p95).
- **post-fix-verification scenario** (4-week tail after Move #6.21 recommended-actions deployed): median correctness = 0.91 across 28 events; median leakage = $120 per event; **Move #6.21 self-deactivates when correctness > 0.90 AND leakage < $150/event for 28 consecutive days** (the auditor's self-deactivation is rate-limited to ≤1 deactivation per 90 days to prevent oscillation; re-activates on first event with correctness < 0.85).
- **default cost-per-event** (single-influencer single-platform): **$0.018 average** (1 Kafka read = $0.001 + 4 SQL aggregations = $0.008 + 1 Move #6.20-action-enrich = $0.005 + 1 Move #6.15-emit = $0.004).
- **default latency-per-event**: **2.4s p95** for single-influencer single-platform; 4.1s p95 for nano-influencer (CDP-merge slow-path); 5.7s p95 for cross-platform-stack (4th-pass slow-path).
- **default false-positive rate**: 4.2% (a small fraction of `discount_code_attribution_leaked_to_fbclid` flags are actually correct `fbclid`-first-touch — the auditor's pass-4 has a 95.8% precision; the 4.2% false-positives are usually `fbclid` clicks within 60s of `promo_code` entry where the customer clicked the influencer's Meta ad FIRST and then typed the code manually second — in these cases the `fbclid` IS the correct attribution and the discount-code is a coincidental second event).
- **default auditor-action-chain-precision**: 89% (of the 4.2% false-positives, 89% are correctly suppressed by the post-audit manual-review step where the operator can mark the flag as `discount_code_attribution_correct_no_fix_needed`).

## The build (time estimate: ~20 hours)

**Phase 1 — Data layer (~5 hours)**

1. `Move-#6.18-per-influencer-breach-cost-consumer` — Segment webhook consumer with idempotency-key dedup; 5s p95 latency target; pulls Move #6.18's `influencer_id:platform_id:recipe_id:breach_event_id` rows.
2. `Per-influencer-discount-code-registry-reader` — YAML reader that loads the `influencer_id → { unique_code, code_type, code_window_days, code_attribution_window_days, code_attribution_path, code_attribution_path_known_issues[] }` mapping; 5-min in-memory cache; backed by daily-export from GRIN/Friendbuy/ReferralCandy/Dub/Impact/Partnerstack + first-party-promo-code-issuance-system.
3. `Per-platform-discount-code-event-stream-reader` — Kafka/Confluent-Cloud/Kinesis consumer that streams the per-platform `promo_code` events for 5 platforms Meta+Google+TikTok+Snap+Pinterest; 7d rolling retention; `event.promo_code` index; 30d lookback window per Move #6.18's `breach_timestamp`.
4. `CDP-identity-resolution-pipeline-merger` — merges cross-device `promo_code` events via the brand's Move #6.5 segment-cdp-real-time + rudderstack-real-time-streaming identity-graph; 24h cache to drop p95 latency from 4.1s to 1.9s.

**Phase 2 — Audit layer (~5 hours)**

5. `Last-touch-attribution-baseline-calculator (Pass 1)` — Pure-SQL over the per-platform stream; counts orders where LAST `promo_code` event in session = influencer's code; 90d lookback window.
6. `First-touch-assist-baseline-calculator (Pass 2)` — Pure-SQL over the per-platform stream + CDP-merge; counts orders where FIRST `promo_code` event in session = influencer's code (within per-platform per-influencer attribution-window matrix: Meta=7d / Google=30d / TikTok=1d / Snap=7d / Pinterest=30d; macro=7d / mid_tier=14d / micro=30d / nano=30d / affiliate=30d / employee_advocate=7d; uses the MIN of the two windows).
7. `Multi-touch-fractional-calculator (Pass 3)` — Calls the brand's MTA engine (Markov-chain or Shapley-value or data-driven-attribution; Triple Whale / Polar / Northbeam / Hyros); for each order computes the fraction of `promo_code` events that reference the influencer's code across the 30d attribution-window; 0.30 weight.
8. `Cross-platform-de-duplication-detector (Pass 4)` — Reverse-event-order check on each session: if `fbclid` event arrived AFTER the `promo_code` event in the same session, flag `discount_code_attribution_leaked_to_fbclid`; same for `gclid` (Google) + `ttclid` (TikTok) + `snapclid` (Snap) + `epik` (Pinterest); per-platform leak-rates empirically calibrated from the 5×6 matrix above.

**Phase 3 — Decision layer (~4 hours)**

9. `Discount-code-attribution-correctness-scorer` — `score = 0.30 * pass1_normalized + 0.30 * pass2_normalized + 0.25 * pass3_normalized + 0.15 * (1 - pass4_leakage_rate)`; emits 0.0–1.0 per Move #6.18 event; floor at 0.0; ceiling at 1.0.
10. `Discount-code-attribution-leakage-amount-calculator` — `leakage_usd = (pass3_fractional_revenue - pass1_last_touch_revenue) + (pass4_leaked_revenue) + (pass2_first_touch_underattribution)`; per-event median $480, 90th-percentile $1,200.

## Common pitfalls (15 from real builds)

1. **Assuming Move #6.18's per-influencer breach-cost is correctly attributed without auditing the discount-code path** — the default Move #6.18 path inherits the brand's CDP + last-touch-attribution pipeline, which under-counts influencer-driven discount-code revenue by 15–55% in the 4 well-documented cases (last-touch-misses-delayed-code-use / CDP-drops-promo_code-on-2nd-order / Meta CAPI's fbclid-silently-overrides-discount-code / Safari ITP strips document.referrer). The Move #6.21 auditor's 4-pass reconciliation is load-bearing — without it every Move #6.18 per-influencer breach-cost is silently under-counted and Move #6.20's per-influencer post-mortem recommended-actions miss the discount-code-attribution-leakage as a top-3 root-cause.
2. **Using a single-attribution-model baseline instead of the 4-pass reconciliation** — the 4-pass reconciliation (last-touch + first-touch + multi-touch-fractional + cross-platform-de-duplication) is REQUIRED because each pass catches a different leakage case. A single Markov-chain MTA baseline misses the CDP-identity-resolution 2nd-order drop (Pass 2 first-touch-assist catches it). A single last-touch baseline misses the Meta CAPI fbclid-silently-overrides case (Pass 4 catches it). A single first-touch baseline misses the delayed-code-use case (Pass 1 catches it). The 4-pass weighted-blend is load-bearing.
3. **Hard-coding the attribution-window instead of using the per-platform per-influencer-category matrix** — Meta=7d / Google=30d / TikTok=1d / Snap=7d / Pinterest=30d AND macro=7d / mid_tier=14d / micro=30d / nano=30d / affiliate=30d / employee_advocate=7d. The MIN of the two windows is the correct per-event window. Hard-coding 7d across-the-board under-counts Google+micro by ~50% and over-counts TikTok+macro by ~25%. Hard-coding 30d across-the-board over-counts Meta+macro by ~30% (last-touch is the dominant model on Meta+macro so the multi-touch-fractional passes are over-counting).
4. **Not handling the 4.2% false-positive rate from Pass 4 cross-platform-de-duplication** — the 4.2% false-positive rate from `discount_code_attribution_leaked_to_fbclid` (where `fbclid` is the correct first-touch and the discount-code is a coincidental second event) MUST be addressed via the manual-override-handler (operator can mark `discount_code_attribution_correct_no_fix_needed`); without it the operator will receive 4.2% noise and lose trust in the auditor. The `manual-override-rate ≥ 5%` alert is also load-bearing — if the manual-override-rate exceeds 5% the auditor's pass-4 precision has dropped and the per-platform leak-rate calibration needs re-tuning.
5. **Computing leakage-amount on revenue alone instead of revenue × LTV-multiplier** — VIP loyalty tier customers have 4.0x LTV-multiplier; raw-revenue weighting under-counts the VIP-tier-influencer's leakage by 4x. Use Move #6.9's per-platform × per-cohort LTV-multiplier to weight the leakage-amount. The 6-influencer-category code-volume table above should also be weighted by per-influencer LTV-multiplier from Move #6.18.
6. **Not feeding the per-event discount-code-attribution-correctness-score back to Move #6.15's accuracy-ledger** — the per-event correctness-score is the load-bearing accuracy-metric that Move #6.15 uses to auto-tune the per-platform leak-rate calibration. Without the accuracy-ledger emit, Move #6.15 cannot auto-tune the leak-rates and the auditor's correctness will drift as the brand's CDP + Meta CAPI + Google EC pipelines evolve.
7. **Rate-limiting the per-event auditor to ≤1 audit per influencer × platform × breach-event per 24h is too restrictive** — a single breach-event may need 2–4 audits if the breach-event spans 2–4 platforms (e.g. a Move #6.16 cascade-fire R4 rotates tokens on 3 platforms, each of which needs its own per-platform per-influencer-audit). Use `≤1 audit per influencer × platform × breach-event per 24h` for the single-platform case AND `≤3 audits per influencer × breach-event per 24h` for the cross-platform-stack case.
8. **Using a static per-platform leak-rate instead of empirically-calibrated from the brand's own data** — the 5×6 matrix above is a cross-platform-attribution-empirical-calibration baseline from Triple Whale / Polar / Northbeam 2024 studies; each brand's actual leak-rates may differ by ±20% depending on CDP-vendor + Meta-CAPI-version + Google-EC-version. Run a 30-day calibration on the brand's own data before locking the leak-rates into the per-platform matrix; auto-recalibrate monthly via Move #6.15.
9. **Not handling the Safari ITP 7-day-lookback limit for first-touch-assist** — Safari ITP strips `document.referrer` after 7 days for cross-site tracking, so the Pass 2 first-touch-assist on Safari sessions can only see ≤7d lookback. If the influencer's first-touch was 14d ago on Safari, Pass 2 will MISS it. Mitigation: use the CDP-identity-resolution's server-side `first_touch_promo_code` field (which is server-side-stored and not affected by Safari ITP) as the Pass 2 fallback. Without this fallback, the Safari-influencer-cohort under-counts by ~20%.
10. **Not handling the `promo_code` field being dropped on 2nd-order events by the brand's CDP** — the default Segment/RudderStack/mParticle schema has `properties.promo_code` on the `Order Created` event; if the brand's CDP is configured to drop `properties.promo_code` on the 2nd `Order Created` event for the same `customer_id` (a common CDP-schema-stripping-bug), the auditor's Pass 1 + Pass 2 will silently miss the 2nd-order discount-code attribution. Mitigation: emit a synthetic `promo_code_attribution_2nd_order` event from the Move #6.21 auditor when the 2nd-order event is detected and the `promo_code` field is missing.
11. **Not handling Meta CAPI's `fbclid` vs `promo_code` dedup-order as configurable per-influencer** — Meta CAPI's default dedup-order is `fbclid`-first (Meta assumes paid-ad clicks should win), but for some influencer-categories the brand may want `promo_code`-first (because the influencer's organic relationship is the higher-intent signal). Move #6.21 MUST allow per-influencer dedup-order configuration in the `Per-influencer-discount-code-registry`; the default is `fbclid`-first (matching Meta CAPI's default) but mid-tier + micro + nano should be flipped to `promo_code`-first.
12. **Not handling the cross-platform-stack scenario where 3+ platforms leak simultaneously** — when 3+ platforms leak simultaneously (Meta+Google+TikTok all overriding the discount-code), the 4-pass reconciliation needs a 5th pass: `cross-platform-stack-aggregator` that combines the per-platform leakage into a single Move #6.20-action-chain. The default is to emit 3 separate `fix_discount_code_attribution_path_for_<influencer>_on_<platform>` items; the cross-platform-stack-aggregator emits 1 combined item with a 3-platform priority-order. Without it, the operator receives 3+ separate action items and may apply them in the wrong order.
13. **Not handling the self-deactivation-controller's rate-limit correctly** — the ≤1 deactivation per 90 days rate-limit is HARD; without it the auditor will oscillate between active/deactivated every 28 days as the correctness-score bounces around the 0.90 threshold. The 90-day rate-limit + the < 0.85 re-activation threshold are load-bearing.
14. **Not handling the manual-override-handler's audit-trail emission to Move #6.15** — when the operator marks a flagged `discount_code_attribution_leaked_to_fbclid` as `discount_code_attribution_correct_no_fix_needed`, the override MUST be emitted to Move #6.15's accuracy-ledger with `accuracy_layer="move_6_21_discount_code_attribution_manual_override"` tag. Without the audit-trail, Move #6.15 cannot distinguish between "the auditor is wrong 4.2% of the time" vs "the auditor is right but the operator is mis-using the override" — and the auto-tune of the per-platform leak-rate calibration will be off.
15. **Not running a Move #6.21 production-readiness test before BFCM peak** — the 4-pass reconciliation + the per-platform leak-rate calibration + the Move #6.20-action-enricher + the Move #6.15-emit all need to be running sub-5s p95 by Nov 1, 2025 (BFCM 2025). The default Phase 5 verify step (20 hours total build time) is calibrated for non-BFCM-peak performance; a BFCM-peak load-test (200 concurrent events instead of 100) is REQUIRED to verify the 5.7s p95 cross-platform-stack-latency doesn't degrade to >10s p95 under BFCM-peak load (the 4th-pass cross-platform-de-duplication-detector is the slow-path and BFCM-peak's 3x click-volume may saturate the per-platform stream).
