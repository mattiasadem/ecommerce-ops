## Common pitfalls (18 from real builds)

1. **Running Move #170 before Move #169 is shipped.** Move #170 requires Move #169 per-coverage-band-engine as the canonical upstream per-coverage-band decomposition — Move #169 must be live in production with all 10 verification gates passing per Move #169 playbook before Move #170 deployment begins. **Fix:** confirm `Move #169 verification log shows 10/10 gates PASS` before starting Move #170.

2. **Loosening the anti-monopoly-floor to make fairness-floor pass.** The anti-monopoly-floor (no single per-coverage-band × per-coverage-band-fairness-id >30% of events) is pinned at 30% by the SRE-coverage-band-fairness-2026 benchmark — loosening it to make a fairness-floor violation pass is the canonical Move #169-style regression trap. **Fix:** NEVER loosen the canonical 30% anti-monopoly-floor without a documented reason AND a TICK: <date> marker; the threshold is pinned by Move-#170-canonical-thresholds-published test.

3. **Treating coverage-band-1-fairness-floor as the only coverage-band-fairness.** The canonical 5-coverage-band-fairness decomposition is coverage-band-1-fairness-floor + coverage-band-2-fairness-acceptable + coverage-band-3-fairness-warning + coverage-band-4-fairness-violation + coverage-band-5-fairness-critical — operators who only ship coverage-band-1-fairness-floor miss the per-coverage-band-fairness × per-coverage-band decomposition for the 4 downstream coverage-band-fairness categories. **Fix:** deploy all 5 coverage-band-fairness categories in Pillar B Step 1 + verify each coverage-band-fairness has ≥10% of total events in the verification log.

4. **Confusing per-coverage-band-fairness-bucket with per-coverage-band-fairness-classifier.** Per-coverage-band-fairness-bucket is the per-event runtime classifier that tags each event with one of the 5 canonical coverage-band-fairness categories; per-coverage-band-fairness-classifier is the static mapping table that maps per-coverage-band to canonical coverage-band-fairness (the table in section 3). Mixing them produces a runtime classifier that drifts from the static mapping. **Fix:** keep the static mapping table in Move-#170-coverage-band-fairness-classifier.ts as the source of truth and the runtime classifier reads it on every event.

5. **Forgetting to update Gate J's "previous" values.** Gate J (Pillar F Move #155 back-feed) compares current per-coverage-band-fairness-p99 + freshness + staleness + coverage + conformance to the previous-cycle values — without updating the "previous" values weekly, Gate J is meaningless. **Fix:** update the "previous" values weekly per the canonical cadence; the gate is meaningless without them.

6. **Treating the coverage-band-fairness decomposition as a one-time task.** The per-coverage-band-fairness × per-coverage-band × per-resolution-time-cohort-window × per-discovery-decoder-family-overlay-window decomposition is a continuous signal — new AI shopping channels (ChatGPT Agentic Storefronts + Microsoft Copilot Checkout + Perplexity Buy with Pro + Google AI Mode UCP + Walmart Sparky + Amazon Buy for Me) shift the coverage-band-fairness distribution monthly. **Fix:** schedule the weekly cadence and don't skip weeks; Gate G compounds over time.
