# PDP review-highlight cross-channel multi-arm bandit picker

> Move #47.5.1.1.1.1 — a Thompson sampling / UCB1 / LinUCB contextual bandit per cohort × per channel (PDP review-highlight engine × email + SMS + push + DPA + affiliate + display) that picks the winning per-cohort cross-channel snippet picker automatically with always-valid p-values, reduces A/B test cycle time from 14 days to 7 days, and lifts per-cohort per-channel snippet CTR another 10–25% on top of Move #47.5.1.1.1 / skill/529 static A/B picker.

## When to use this skill

Use this skill when ANY of the following is true:

- the operator has shipped Move #47.5.1.1 / skill/528 (per-cohort PDP review-highlight) AND Move #47.5.1.1.1 / skill/529 (per-cohort cross-channel export), and the per-cohort per-channel snippet picker is statically assigned (top-3 reviews by `cohort_LTV_weight × cohort_fit × verified_buyer × recency`) but the cohort's preferred snippet varies by traffic source × device × time-of-day × cohort-region × cohort-product-affinity, AND the static picker is leaving 10–25% per-cohort per-channel snippet CTR on the table;
- the operator is running a 14-day A/B test per cohort per channel and the static-picker winner looks stale by day 7 (the cohort's snippet preference drifted toward a new product / season / cohort-tier shift), AND the operator needs always-valid p-values + per-cohort per-channel bandit;
- the operator has 14 cohorts × 7 channels = 98 snippet picker configurations and the test matrix is too large for frequentist A/B testing (a full grid test takes 4–6 months and consumes 90% of available impressions per cohort per channel);
- the operator needs to optimize MULTIPLE KPIs simultaneously (snippet CTR + ATC CVR + AOV + 90-day LTV + returns rate + spam-filter precision + cross-channel snippet consistency) without seeing the canonical "metric seesaw" anti-pattern (snippet CTR up but AOV down, or ATC CVR up but 90-day LTV down);
- the operator wants to ship per-cohort per-channel LLM-generated snippets (Move #47.5.1.1.1.2) but cannot pick the winning LLM-generated snippet deterministically (LLM outputs vary in tone / length / cohort-resonance) — the bandit picks the winner automatically;
- the operator needs a cold-start guard for new cohorts (the per-cohort bandit falls back to a cohort-proxy based on geo + device + referrer + landing-page category while collecting cohort-specific samples, with a 95%+ precision recall guard);
- the operator needs cross-channel snippet consistency with a per-cohort cross-channel bandit rollup (one bandit per cohort × per-channel + one hierarchical bandit rollup across channels for consistency);
- the operator needs bandit-friendly vendor / experimentation integration with Eppo / Kameleoon / Optimizely / Monetate / VWO / Statsig / AB Tasty / Adobe Target / LaunchDarkly / GrowthBook / Split.io feature flags and warehouse-native bandit computation.

Do NOT use this skill when:

- the operator has not yet shipped Move #47.5.1.1 (per-cohort PDP review-highlight) — the bandit needs the static picker as its `arm space` baseline;
- the operator has not yet shipped Move #47.5.1.1.1 (per-cohort cross-channel export) — the bandit needs the per-channel snippet picker to optimize over;
- the operator has < 2,000 visitors per cohort per month per channel — the bandit needs sufficient traffic to converge in a 7-day window;
- the operator is optimizing a single-channel snippet (no cross-channel dimension) — use Move #47.5.1.1 / skill/528 alone or Move #47.5.1.1.1 / skill/529 with a smaller cohort × channel matrix.

## What "best in class" looks like

A best-in-class Move #47.5.1.1.1.1 deployment has ALL of the following:

1. **Algorithm choice per cohort × per channel.** Thompson sampling (TS) is the default for binary-reward snippet-CTR optimization with batched bTS update at 8–24h windows for delayed ecommerce rewards; UCB1 for non-stationary reward distributions (cohort preference shifts mid-test); LinUCB (Li et al. 2010) for context-vector personalization (cohort × device × time-of-day × traffic-source × locale × product-affinity vectors). Hierarchical bandit (strategy-as-arm vs item-as-arm per ACM UMAP 2025) for reducing action space when the snippet pool exceeds 50 per cohort per channel. BanditLP (LinkedIn 2026) for multi-stakeholder constrained bandit optimization (snippet CTR + ATC CVR + 90-day LTV + returns rate + cross-channel consistency + spam-filter precision + deliverability) — the operator can encode 7+ KPIs simultaneously without metric seesaw.
2. **Per-cohort × per-channel arm space.** The bandit operates on a 14-cohort × 7-channel matrix = 98 cells; each cell has 2–5 snippet variants (top-3 static picker + 1–2 LLM-generated or cohort-A/B-tested challenger variants). Arm count: 196–490 total arms; arm sparsity handled via hierarchical rollup (per-cohort bandit → per-channel bandit → cross-channel rollup).
3. **Context vector (per cohort × per channel).** Cohort identity (anonymous cohort-proxy + Klaviyo identified + Triple Whale cohort-LTV tier), device (mobile/tablet/desktop), time-of-day (8 buckets), traffic-source (8 buckets), locale (16 locales), product-affinity (top-3 product categories from Move #47.5.1), product-velocity (8 buckets), returns-state (Decay/Closed/Open/Refund/Exchange from Move #88), spam-filter precision per cohort (0.95–0.999), cross-channel consistency score (0.0–1.0), channel-specific consent (email consent + SMS consent + push consent + DPA consent + affiliate consent), per-channel frequency-cap (1× per cohort per day), per-channel deliverability (Litmus / Return Path / Twilio / OneSignal / Meta CAPI). Total: 14 cohorts × 14 context dimensions = 196-feature contextual bandit.
4. **Reward function (multi-objective).** Primary: per-cohort per-channel snippet CTR × ATC CVR × AOV × 90-day LTV (encoded as a weighted linear combination per BanditLP). Secondary: per-cohort per-channel returns rate, spam-filter precision, cross-channel snippet consistency, deliverability, frequency-cap compliance, consent-gate compliance. The bandit moves forward 7 days; the picker controls on `winning_arm × cohort_context × reward_window`.
5. **Batched Thompson sampling (bTS) at 8–24h windows.** Per Home Depot 2021 batch-updated MAB paper, ε-greedy with 8h batch size showed best performance for delayed ecommerce rewards; per LotteON 2026 bTS at 24h windows for click/non-click reward aggregation. Default: 24h bTS window for snippet CTR + 7-day window for 90-day LTV readback. Always-valid p-values via sequential testing (mSPRT / Always Valid Inference / anytime-valid confidence sequences per Howard et al. 2021).
6. **Warm-up + exploration floor.** First 7-day window: uniform exploration (5–10% per arm) to build the per-arm posterior; subsequent 7-day windows: ε-greedy with ε=0.1 OR Thompson sampling with α=1.0 prior (Li et al. 2010 LinUCB alpha default). Warm-up guard: minimum 1,000 impressions per arm before declaring a winner (prevents the canonical "prematurely determining the winner due to small parameter values at the beginning of the test" anti-pattern per LotteON 2026).
7. **Hierarchical bandit rollup.** Per-cohort bandit → per-channel bandit → cross-channel rollup (Storytel 2025 hierarchical MAB pattern). Strategy-as-arm (cohort-prior / cohort-fit / cohort-AI / cohort-LTV-weighted / cohort-affinity) reduces the action space from 196-490 snippet arms to 5–7 strategy arms per channel, enabling faster learning + interpretability.
8. **Multi-armed bandit A/B test guardrails.** Per Kameleoon 2026 documentation: guardrails on margin (per-cohort per-channel margin floor), AOV (per-cohort per-channel AOV floor), frequency-cap compliance (per-cohort per-channel 1×/day cap), spam-filter precision (per-cohort per-channel ≥0.95), deliverability (per-cohort per-channel inbox-placement ≥0.85 for email / delivery-rate ≥0.95 for SMS / push delivery ≥0.85 / DPA delivery ≥0.85), consent-gate compliance (per-cohort per-channel consent-token propagation).
10. **Bandit-friendly vendor stack.** Eppo Contextual Bandits (Datadog-owned, warehouse-native bandits, single SDK for feature flagging + experimentation + bandits, ~$2k–$8k+/mo for $5M+ GMV), Kameleoon Enterprise (multi-armed and contextual bandits + CUPED + frequentist + Bayesian analysis, $0.65/user/mo with Enterprise-only statistics), Optimizely Web Experimentation + Bandits ($$), Monetate ($$), VWO ($$), Statsig (free up to 1M events, then $$), AB Tasty AI (€15k+/yr), Adobe Target ($$$), LaunchDynly (feature flags + bandit add-on, $$), GrowthBook (open-source bandits, free self-hosted / $$ cloud), Split.io feature flags + bandit add-on. Default Path B: Eppo Contextual Bandits + warehouse-native bandit + Triple Whale/Polar/Northbeam cohort-LTV readback.
11. **Per-cohort cross-channel cohort-LTV readback.** The bandit reward is shipped via Triple Whale / Polar / Northbeam / Move #6 dashboard unifies the PDP + email + SMS + push + DPA + affiliate + display bandit CTR into a single canonical per-cohort cross-channel review-highlight LTV dashboard × per-cohort per-channel LTV + per-cohort per-channel margin + per-cohort per-channel repeat-purchase + per-cohort per-channel cross-channel-trust-score. Weekly iteration on the per-cohort bandit.
12. **Cold-start + privacy + attribution guard.** Anonymous cross-channel visitors (no Klaviyo ID, no Postscript subscriber, no OneSignal push subscriber, no Meta CAPI persistent ID) get a cohort-proxy (geo + device + referrer + landing-page category) review snippet × cross-channel consistency scoring × Klaviyo browse-history + Triple Whale cohort-LTV proxy × GDPR/CCPA/TCPA consent gating × Triple Whale/Polar/Northbeam per-cohort cross-channel cohort-LTV readback + per-cohort per-channel returns-rate readback. ## Common pitfalls (15 from real builds)

1. **Pitfall — Prematurely determining the winner due to small parameter values at the beginning of the test.** LotteON 2026 documented this anti-pattern: Thompson sampling with small alpha + beta values at the start of the test causes the bandit to lock onto a suboptimal winner prematurely. **Fix:** enforce a minimum 1,000 impressions per arm before declaring a winner (warm-up floor); uniform 5–10% exploration for the first 7-day window to build the per-arm posterior; ε-greedy with ε=0.1 OR Thompson sampling with α=1.0 prior (Li et al. 2010 LinUCB alpha default) for subsequent windows.

2. **Pitfall — The bandit chooses the winning snippet per channel but loses cross-channel snippet consistency.** Move #47.5.1.1.1 / skill/529 ships cross-channel snippet consistency scoring as a guardrail; the bandit without cross-channel rollup can choose snippet A on email + snippet B on SMS + snippet C on DPA, breaking the cohort's cross-channel trust-score. **Fix:** add a hierarchical bandit rollup (per-cohort bandit → per-channel bandit → cross-channel rollup per Storytel 2025); encode cross-channel consistency as a constraint in the BanditLP multi-objective optimization; surface cross-channel consistency as a top-3 guardrail alongside snippet CTR + ATC CVR + 90-day LTV.

3. **Pitfall — The bandit reward optimizes snippet CTR but degrades AOV and 90-day LTV.** The canonical "metric seesaw" anti-pattern (snippet CTR up but AOV down, or ATC CVR up but 90-day LTV down) is documented in Amazon Personalize 2026 + Kameleoon 2026. **Fix:** encode all KPIs in the BanditLP reward (snippet CTR + ATC CVR + AOV + 90-day LTV + returns rate + spam-filter precision + cross-channel consistency + deliverability + frequency-cap + consent); per-cohort per-channel guardrails (margin floor, AOV floor, returns-rate ceiling); always-valid p-values via sequential testing (mSPRT / Always Valid Inference / anytime-valid confidence sequences per Howard et al. 2021).

4. **Pitfall — The bandit vendor does not support the cohort × channel matrix scale (196–490 arms).** Some vendors cap arm count at 50–100 per experiment; the 14-cohort × 7-channel matrix with 2–5 variants per cell exceeds the cap. **Fix:** use hierarchical bandit rollup (per-cohort bandit → per-channel bandit → cross-channel rollup) to reduce the action space; use Eppo Contextual Bandits (warehouse-native, supports 1000+ arms per experiment) OR Kameleoon Enterprise (multi-armed and contextual bandits at $0.65/user/mo Enterprise) OR custom Python bandit on SageMaker Multi-armed bandit (R/LinUCB/TS/UCB1/NeuralBandit, fully configurable arm count).

5. **Pitfall — The bandit reward attribution is incorrect due to multi-channel conversion paths.** A cohort sees a snippet on email (click) → DPA (impression) → PDP (purchase); the bandit credits the snippet CTR to email but the actual conversion is on DPA, biasing the reward attribution. **Fix:** use Meta CAPI / TikTok Events API / Google Enhanced Conversions / Pinterest Conversions API for deterministic cross-channel attribution; use Triple Whale / Polar / Northbeam cohort-LTV attribution for the 90-day LTV readback; use the canonical Move #47.5.1.1.1 cross-channel snippet picker identity (Klaviyo identify + Postscript identify + OneSignal identify + Meta CAPI persistent ID) to track the cohort across channels.

6. **Pitfall — The bandit bandit picks a winner per cohort per channel but the winning snippet is not in the arm space (e.g. a new LLM-generated snippet mid-test).** The bandit cannot pick an arm it doesn't have; the operator must add the new arm to the bandit pool and re-warm. **Fix:** add new arms dynamically via Eppo Contextual Bandits' "add or remove variations" feature OR Kameleoon Enterprise's bandit arm extension OR custom Python bandit on SageMaker Multi-armed bandit (configurable arm pool); always allow 1–2 new challengers per cohort per channel per week to keep the arm space fresh; warm-up the new arm with uniform 5–10% exploration for the first 1,000 impressions.

7. **Pitfall — The bandit cold-start for new cohorts (no Klaviyo ID, no Triple Whale cohort-LTV tier) cannot pick a winning snippet.** The bandit needs sufficient cohort-specific samples to learn the per-cohort per-channel snippet preference; new cohorts have < 1,000 samples per channel. **Fix:** fall back to a cohort-proxy (geo + device + referrer + landing-page category) review snippet × cross-channel consistency scoring × Klaviyo browse-history + Triple Whale cohort-LTV proxy × GDPR/CCPA/TCPA consent gating; warm-up the new cohort with uniform 5–10% exploration for the first 7-day window; minimum 1,000 impressions per cohort per channel before declaring a winner.

8. **Pitfall — The bandit reward function is too narrow (snippet CTR only) and ignores secondary KPIs.** The bandit picks a winning snippet based on CTR but ignores spam-filter precision (a 95%-precision snippet with 5% spam risk may damage sender reputation long-term), cross-channel consistency (a per-channel winner that breaks consistency damages cohort trust), and deliverability (a snippet with high CTR but high spam-complaint-rate damages inbox-placement). **Fix:** encode all KPIs in the BanditLP reward (snippet CTR + ATC CVR + AOV + 90-day LTV + returns rate + spam-filter precision + cross-channel consistency + deliverability + frequency-cap + consent); per-cohort per-channel guardrails (margin floor, AOV floor, returns-rate ceiling, spam-filter-precision floor, deliverability floor); always-valid p-values via sequential testing.

9. **Pitfall — The bandit A/B test does not have a sufficient exploration budget and locks onto a local optimum.** A bandit with insufficient exploration (ε=0.05 for too long) converges prematurely to a local optimum; the cohort's true winning snippet is never discovered. **Fix:** per Li et al. 2010 LinUCB α=1.0 default; per Kameleoon 2026 documentation, ε=0.1 is the recommended exploration floor; per Home Depot 2021 batch-updated MAB paper, ε=0.2 with 8h batch size showed best performance for delayed ecommerce rewards; tune ε via Bayesian optimization (Optuna + Ray Tune) on the operator's per-cohort per-channel historical reward data.

10. **Pitfall — The bandit per-cohort per-channel guardrails are too strict and prevent the bandit from picking any winner.** If the guardrails (margin floor + AOV floor + returns-rate ceiling + spam-filter-precision floor + deliverability floor) are too strict, the bandit cannot pick any arm without violating one or more guardrails, and the system defaults to the static Move #47.5.1.1.1 picker (defeating the purpose of Move #47.5.1.1.1.1). **Fix:** tune guardrails via Bayesian optimization on the Move #47.5.1.1.1 historical reward data; surface guardrail violations as warnings (not blockers) during the warm-up window; relax guardrails during the first 7-day window (warm-up floor) and tighten only after the bandit has converged.

11. **Pitfall — The bandit uses single-objective Thompson sampling but the cohort's experience needs multi-objective optimization (snippet CTR + ATC CVR + AOV + 90-day LTV).** Single-objective TS optimizes snippet CTR but ignores ATC CVR (a snippet with 80% CTR but 5% ATC CVR is worse than a snippet with 50% CTR but 30% ATC CVR). **Fix:** use BanditLP (LinkedIn 2026) for multi-stakeholder constrained bandit optimization; encode snippet CTR + ATC CVR + AOV + 90-day LTV as a weighted linear combination in the reward function; use hierarchical bandit rollup (per-cohort bandit → per-channel bandit → cross-channel rollup) to balance per-cohort per-channel snippet CTR with cross-channel consistency.

12. **Pitfall — The bandit per-cohort per-channel arm space is not aligned with the cohort's actual variant pool.** The bandit has 5 arms per cohort per channel but the cohort's actual variant pool has 50+ snippets (top-10 verified-buyer + top-10 photo/video + top-10 cohort-LTV-weighted + top-10 cohort-region + top-10 cohort-fit). The bandit picks among 5 arms that don't represent the cohort's actual preference distribution. **Fix:** use hierarchical bandit rollup (per-cohort bandit → per-channel bandit → cross-channel rollup) with strategy-as-arm (cohort-prior / cohort-fit / cohort-AI / cohort-LTV-weighted / cohort-affinity) to reduce the action space while preserving the cohort's variant pool diversity; OR use a 2-stage bandit (top-10 selection per strategy → bandit picks winning strategy → winner's top-3 snippets picked deterministically).

13. **Pitfall — The bandit per-cohort per-channel reward window is too short (24h) and the bandit converges on a snippet that performs well short-term but degrades long-term (e.g. a snippet with high 24h CTR but high 7-day returns rate).** A 24h reward window misses the cohort's actual long-term value (90-day LTV). **Fix:** use a 24h bTS window for snippet CTR + a 7-day window for ATC CVR + AOV + a 30-day window for returns rate + a 90-day window for cohort-LTV; encode all windows in the BanditLP reward function with appropriate weights (snippet CTR weight 0.1 + ATC CVR weight 0.3 + AOV weight 0.2 + 90d_LTV weight 0.4).

14. **Pitfall — The bandit is built without cross-channel cohort-level statistical significance testing, and the operator cannot declare a "winner" with confidence.** The bandit picks a winner per cohort per channel but the operator cannot run a hypothesis test across channels (e.g. "the cohort's email winner is identical to the cohort's SMS winner" — but the bandit has no mechanism to test this). **Fix:** use Eppo Contextual Bandits' "experiment analysis tools" feature OR Kameleoon Enterprise's "advanced statistics" (CUPED + frequentist + Bayesian analysis methods) to run cross-channel cohort-level significance testing; use sequential testing with always-valid p-values (mSPRT / Always Valid Inference / anytime-valid confidence sequences per Howard et al. 2021).

15. **Pitfall — The bandit ships but the operator does not have the engineering capacity to maintain it (per-vendor SDK updates, per-cohort per-channel arm refresh, per-channel context-vector refresh, per-vendor cost monitoring).** A bandit that is not maintained drifts: arms become stale, context vectors become stale, vendor SDK updates break the bandit, costs balloon. **Fix:** allocate a dedicated bandit engineer (or 0.5 FTE) for per-cohort per-channel bandit maintenance; set up per-vendor SDK update monitoring (Eppo SDK, Kameleoon SDK, Optimizely SDK, etc.); set up per-vendor cost monitoring ($/mo for per-cohort per-channel arm + per-channel context-vector + per-channel reward computation); set up weekly per-cohort per-channel arm refresh (1–2 new challengers per week); set up monthly per-channel context-vector refresh (cohort-LTP tier changes; cohort-region changes; cohort-fit changes; spam-rule changes).
