## Common pitfalls (18 from real builds)

1. **Overlay-window-bucket-assignment using Move-160-router-timestamp instead of Move-#159-trend-event-emission-pipeline-timestamp.** Pillar B's overlay-window-bucket-assignment buckets the per-discovery-decision-actor-resolution-time-trend event into the 5-resolution-time-overlay-windows using the Move #160 router's `Date.now()` timestamp, but the Move #160 router-timestamp is when Move #160 RECEIVED the Move #159 event, not when the underlying stream-processing-pipeline emitted it — so a 30-second-old Move-159-trend-event lands in the real-time-overlay-window incorrectly. **Fix:** use the canonical per-discovery-decision-actor-resolution-time-trend-event-emission-pipeline-timestamp from the Move #159 event payload (which itself is the canonical stream-processing-pipeline-emission-timestamp), NOT the Move #160 router-timestamp; compute `age = now - emission-pipeline-timestamp` and bucket into the 5-overlay-windows using canonical thresholds (real-time: age<2s / near-real-time: 2s≤age<30s / delayed: 30s≤age<5min / batched: 5min≤age<1h / historical: age≥1h).

2. **Per-discovery-decision-actor-resolution-time-overlay-p99 latency computed over wrong overlay-window.** Pillar B's overlay-window-freshness-staleness-computation computes p99 latency over the real-time-resolution-time-overlay-window using only the real-time-bucketed events, but the real-time-overlay-window has too few samples for a stable p99, so the per-discovery-decision-actor-resolution-time-overlay-p99 noise dominates the operator-UX-flow. **Fix:** compute per-discovery-decision-actor-resolution-time-overlay-p99 over the near-real-time-resolution-time-overlay-window minimum (canonical 30-second-stream-processing-latency-target), and surface a "low-sample-size" warning when the real-time-resolution-time-overlay-window has <100 events; the canonical real-time-resolution-time-overlay-window-p99 is a moving-target indicator, NOT a stable latency measurement.

3. **Per-discovery-decision-actor-resolution-time-overlay-freshness-floor not enforced.** Pillar B's overlay-window-freshness-staleness-computation computes freshness (time since last event) but does not enforce the canonical freshness-floor (real-time-window freshness <2s / near-real-time-window freshness <30s / delayed-window freshness <5min / batched-window freshness <1h / historical-window freshness <24h), so a stale stream-processing-pipeline that hasn't emitted an event in 10s can still report "freshness: 10s" as if it's within the real-time-overlay-window. **Fix:** enforce the canonical freshness-floor as a hard Pillar B gate; emit a `freshness-violation` event with the canonical `overlay-window: real-time` / `actual-freshness: 10s` / `freshness-floor: 2s` payload into the Move #159 + Move #158 event stream when the freshness-floor is breached.
